# Appendix: 仕様検討時の Q&A

この付録は、言語仕様を検討する過程で出た質問と、その回答・結論をまとめたものです。仕様の各規則が「なぜそうなっているのか」を確認するための資料として位置づけます。

本文中のコード例の構文は検討時点の仮のものです。最終的な構文は本編の仕様に従います。

対象CPUは 65C02 を基本とし、NMOS 6502 はターゲット定義で選択できるものとします。

---

## A. 全体方針

### Q A-1. ハードウェアの制約を、言語の制約で抑えることはできるか。たとえば、関数の呼び出しが深くなったらエラーにする、スタック変数を複数定義したらエラーにする、など。

**回答**

可能です。方針は「6502で高くつく操作は書けないようにするか、高くつくことが見える形でしか書けないようにし、その判定をすべてコンパイル時に行う」です。

関数の深さ制限は採用します。再帰を禁止すれば、呼び出し関係は閉路のないグラフになり、コンパイラは最も深い呼び出し経路のスタック使用量を正確に計算できます。予算を超えたらコンパイルエラーにします。

スタック変数の個数制限は、別の形にします。再帰を禁止すると、ローカル変数をスタックに置く必要自体がなくなるためです。コンパイラは呼び出しグラフを解析し、同時に使われない関数同士のローカル変数を同じ固定アドレスに重ねて配置します。制限すべきなのは変数の個数ではなく、重ね合わせた後の合計メモリ量で、これもコンパイル時に検査します。

**結論**：再帰禁止、深さ（スタック使用量）の予算検査、ローカル変数の静的な重ね合わせ、合計メモリ量の検査を採用。

### Q A-2. Rust のように、言語仕様でハードウェアの制約をカバーすることは可能か。

**回答**

可能です。しかも、この言語の対象は Rust よりも条件が良いと言えます。Rust が難しいのは、ヒープ、複数スレッド、分割コンパイルを相手に安全性を証明しなければならないためです。この言語は、プログラム全体が 64KB 以内、ヒープなし、スレッドなし（並行して動くのは割り込みだけ）、プログラム全体を一度に解析できる、という条件なので、徹底した静的検査が現実的です。

Rust の考え方を 6502 に当てはめたものは次のとおりです。

| Rust の考え方 | この言語での対応 |
|---|---|
| Send / Sync（スレッド間の共有の安全性） | 割り込みとメインで共有する変数を `shared` と宣言。16ビット以上の値は `atomic { }` の中でしか読み書きできない（`php` / `sei` / `plp` に変換） |
| ライフタイム | ローカル変数のアドレスは、呼び出し先には渡せるが、関数の外には持ち出せない |
| 組み込み向けの周辺機器の所有権・型状態 | I/O の所有モジュールの宣言や、入力に設定したポートへの書き込みの禁止 |
| const fn | 表（サイン波、画面の行アドレスなど）をコンパイル時に計算してROMに置く |
| （Rust にもない） | `cycles(n) { }` ブロックで、実行サイクル数をコンパイラが数えて保証する |

静的に検査できないものもあります。ループが必ず終わるかどうか（回数の上限を書かせれば検査可能）、外部機器の振る舞い、割り込みの頻度（ターゲット定義に書けば一部検査可能）などです。

**結論**：Rust 流の「危険な書き方はコンパイルを通さず、検査のコストは実行時に払わない」を言語の基本方針とする。

## B. 型と演算

### Q B-1. 負の数を使うのはどういう場面か。

**回答**

自作マシンの用途では、次のような場面です。

- 変化量や速度（左に1ドット動く dx = -1、跳ね返った後の速度など）
- 相対的な位置（マス目の隣、表の中の何個前など）
- 差の計算（2つの値のどちらが大きいか、基準より高いか低いか）
- 直線描画のアルゴリズム（ブレゼンハム法の誤差項）
- 音のデータ（0を中心に正負に振れる波形）
- 自作ツール（6502 の分岐命令の飛び先は -128〜+127 の相対値）

座標そのもの、個数、文字コード、アドレスには不要です。

6502 では、足し算と引き算は符号付きでも符号なしでも同じ命令で計算できます（2の補数表現のため）。符号によってコストが増えるのは、大小比較、8ビットから16ビットへの拡張、右シフト、割り算と表示の4つだけです。

**結論**：`i8` と `i16` を `u8`・`u16` とは別の型として用意する。符号付きと符号なしの混在は、明示的な変換がない限りエラー。例外として、`u8 + i8 → u8`（位置に変化量を足す）は明示的な変換なしで許可する。

### Q B-2. 8ビットの値があふれたときは、一周して戻る扱いで良いか（C もそうだったはず）。

**回答**

一周して戻る扱いにします。補足として、C で一周して戻るのは符号なしの型だけで、符号付きのあふれは未定義動作です。この言語では、符号付きも符号なしも一周して戻ると定義します。6502 の `ADC` / `SBC` はどちらでも同じ動作なので、ハードウェアの振る舞いをそのまま仕様として保証でき、C より単純になります。

**結論**：符号付き・符号なしとも、あふれは一周して戻る（定義された動作）。

## C. 変数と記憶域

### Q C-1. ゼロページに置く変数（ポインタ以外）の決め方は、オプションで指定し、デフォルトでは明示のみ、とするのはどうか。たとえば最適化オプションとして。

**回答**

採用します。普段は配置が完全に予測でき、速さが必要なときだけコンパイラに任せられます。オプションの有無で動作が変わらないよう、自動配置には次のルールを設けます。

- 自動配置は、`zp` と明示した変数とポインタを置いた後の残りの空きだけを使う（オプションを付けたことでゼロページ不足のエラーが出ることはない）
- `cycles()` ブロック内で使う変数は対象外（サイクル数が変わるため）
- `io` 変数は対象外。`shared` 変数は `fixed` 指定で除外できる
- どの変数を移したか、どれだけ節約できる見込みかをレポートに出す
- インラインアセンブリから参照される変数の扱いは、インラインアセンブリの議題で決める

**結論**：ポインタは自動でゼロページ。それ以外の変数は、既定では `zp` の明示のみ。最適化オプションを付けたときだけ自動配置する。

### Q C-2. グローバル変数の初期値と、プログラムの実行場所をどう扱うか。

**回答**

プログラムを RAM に読み込んで実行する場合、2回目の実行では前回書き換わった値が残ってしまいます。これを防ぐため、起動時に毎回初期値を設定し直します。

**結論**：グローバル変数は初期値の記述を必須とし、起動時に毎回設定する（`noinit` は例外）。ローカル変数は、代入前に読むとエラー。RAM に読み込んで実行する形と ROM から実行する形の両方に対応し、ターゲット定義で切り替える。

## D. 関数と呼び出し規約

### Q D-1. 引数3つを A・X・Y に入れて渡しても、関数内で処理する場合は退避処理が必要になってしまう。根本的に考え方を変える必要はないか。

**回答**

引数の使われ方は「受け取ってすぐ使う」と「後で使う」の2種類です。

すぐ使う場合（例：1文字出力の関数が、受け取った文字をそのまま I/O に書く）は、レジスタ渡しなら書き込みも読み込みも不要です。

後で使う場合は、呼び出し先の入口で自分の固定領域にしまう処理（ご指摘の「退避」）が必要です。ただし、固定領域で渡す方式でも、呼び出し元が同じ場所に書き込んでいます。書き込む場所は同じで、誰が書くかが違うだけです。

| 引数の使われ方 | 固定領域で渡す | レジスタで渡す |
|---|---|---|
| すぐ使う | 呼び出し元で書き、呼び出し先で読む | どちらも不要 |
| 後で使う | 呼び出し元で書く（呼び出し箇所ごとに） | 呼び出し先で1回書く |

どちらの場合もレジスタ渡しは損をせず、呼び出し箇所が多いほどコードが小さくなります。

考え方としては、「引数は呼び出し先が持つ、名前付きの固定アドレスの変数であり、レジスタはそこへ届けるための近道」と捉えます。

**結論**：引数は呼び出し先の固定アドレスの変数として扱う。先頭3バイトは A・X・Y で届け、後で使う値は呼び出し先がしまう。ポインタと4バイトめ以降は、呼び出し元が固定領域に直接書く。

### Q D-2. 複数の値を返す場合も、抜けた先で退避が必要になる。関数というものの定義を考えたほうがよいのでは。サブルーチンという考え方もあるが、関数のほうがよいのか。呼び出し先が壊すレジスタだけを退避する仕様があるから問題ないのか。

**回答**

一般に、関数は「入力を受け取って結果を返すもの」、サブルーチンは「状態の書き換えや I/O を行う処理のまとまり」と区別されます。6502 のプログラムではサブルーチン型が中心になります。

この言語では2つを分けず、「関数＝入口と出口のデータを宣言したサブルーチン」として1つにまとめます。引数のない関数はそのままサブルーチンとして使えます。状態を書き換えない関数には `pure` を付けられ、コンパイル時の計算に使えます。

「壊すレジスタだけを退避する仕様があるから問題ないか」については、半分はそのとおりです。この仕様が解決するのは、呼び出し元がレジスタに持っている値を、関数呼び出しをまたいで保つ問題です。一方、レジスタが本当に別の用途に必要になる場合は、どこかへの書き込みがどうしても必要で、これはどの方式でも消せません。前者の無駄な退避を消すのがこの仕様で、後者の本質的な書き込みを1回で済ませるのが結果領域（Q D-5）です。

**結論**：関数とサブルーチンを分けず、1つの仕組みにまとめる。状態を書き換えないものには `pure` を付けられる。

### Q D-3. スタックの深さの予算について、もう少し詳しく説明してほしい。

**回答**

ローカル変数をスタックに置かないため、スタックに積まれるのは次のものだけです。

- `jsr` の戻り番地（2バイト）
- 割り込み時に CPU が積む戻り番地とフラグ（3バイト）
- 割り込み処理の入口での A・X・Y の退避（3バイト）
- コンパイラが入れる一時的な退避と、`atomic` の `php`（各1バイト）

コンパイラは、メイン・IRQ処理・NMI処理それぞれのすべての呼び出し経路について最大の使用量を計算し、合計します（NMI は IRQ 処理の最中にも入るため、上に積み重なる）。再帰がないので、経路は有限で必ず計算できます。

予算が必要な理由は、6502 のスタックがページ $01 の 256 バイトしかなく、使い切るとスタックポインタが一周して最も古いデータ（戻り番地）を黙って上書きするためです。不具合はその場では出ず、後で戻り先を失って暴走します。予算を 256 バイト全部にしないのは、ROM ルーチンが使う分や、ページ $01 を他の用途に使う機種があるためで、使用可能な範囲はターゲット定義で指定します。

ローカル変数を積まないため、実際の使用量は小さく、呼び出しが20段深くても40バイト程度です。

**結論**：メイン・IRQ・NMI の最深経路の合計が予算を超えたら、原因の経路を示してエラーにする。割り込み処理の中での割り込み許可（`cli`）は禁止。

### Q D-4. ROM ルーチンの呼び出しについて、もう少し詳しく説明してほしい。

**回答**

モニタの ROM にあるルーチン（1文字出力、キー入力など）は、この言語のコンパイラが作ったものではないため、コンパイラには引数のレジスタ、壊すレジスタ、スタック使用量がわかりません。たとえば、X をループカウンタに使っているループの中で、X を壊す ROM ルーチンを呼ぶと、カウンタが狂います。

そこで、これらの性質を宣言させます。

```
extern fn rom_print(u8 c in A)  // 引数 c を A で渡す
    @ $FFEF                     // ルーチンのアドレス
    clobbers(A, X, flags)       // 壊すもの
    stack(4);                   // 使うスタック（戻り番地を含む）
```

宣言があれば、コンパイラはカウンタに別のレジスタを使うか、前後で退避するかを判断でき、スタックの予算にも反映できます。

宣言が実際の動作と違っていても、コンパイラは検出できません。ここはプログラマが正しさに責任を持つ部分で、Rust の `unsafe` と同じく、検査できない部分を1か所に閉じ込める仕組みです。将来の拡張として、エミュレータで実測して宣言と照合するツールが考えられます。

**結論**：ROM ルーチンは `extern` で、引数のレジスタ・アドレス・壊すもの・スタック使用量を宣言する。

### Q D-5. 戻り値は C のように1つ、というのはいまいちなのか。A に値を返すか、ゼロページにポインタを返すような形は。

**回答**

戻り値を1つにすること自体は問題ありません。ただし、複数の値を返すためにポインタを返す方式は、6502 ではいまいちです。

理由の1つめは、ポインタの指す先を用意する場所がないことです。毎回違う場所なら確保が必要ですが、ヒープはなく、ローカル変数のアドレスを返すことも禁止しています。毎回同じ場所なら、呼び出し元はそこを直接読めばよく、ポインタにする意味がありません。

理由の2つめは、遅いことです。ポインタ経由の読み込みは `(zp),Y` になり、読むたびに Y を使い、サイクルも余分にかかります。呼び出し先にもポインタを書き込む処理が毎回必要です。C で定番の「書き込み先のポインタを引数で渡す」方式も同じ理由で遅くなります。

代わりに、構造体を値として返せるようにします。構造体のフィールドは呼び出し先の結果領域（固定アドレス）に置かれ、呼び出し元はコピーせずに直接読みます。結果領域の値は、同じ関数をもう一度呼ぶまで変わりません。古い結果を使い終わる前に同じ関数を呼ぶ場合だけ、コンパイラが自動でコピーを入れます。

**結論**：戻り値は1つ。複数の値は構造体にまとめて返す。ポインタで結果を返す方式は採用しない。

### Q D-6. その構造体は2つまでしか値を持てないのか。正確には2つまではレジスタ、3つ以上はメモリ、ということか。

**回答**

いいえ。構造体で返す場合はレジスタを使わず、すべてのフィールドを結果領域に置きます。フィールドの数に制限はありません。

結果領域は固定アドレスなので、呼び出し元は普通の変数と同じように直接読めます（ポインタ経由ではないので、余分なレジスタも使いません）。レジスタで返す場合と比べて余分にかかるのは、呼び出し先での書き込み（1フィールドにつき3〜4サイクル）だけです。

最適化オプションを付けた場合は、最初のフィールドだけレジスタでも返す、といった改善をコンパイラに任せられます。

**結論**：構造体の戻り値は、全フィールドを結果領域に置く。個数の制限なし。

### Q D-7. 関数の戻り値は u8、i8、u16、i16、bool、構造体しか持てない、という理解で合っているか。

**回答**

ほぼ合っています。加えて、ポインタ、関数ポインタの候補一覧（`fnset`）の値、戻り値なしがあります。将来の型の追加に備え、型の一覧ではなく大きさで返し方を決めます。

| 戻り値 | 返し方 |
|---|---|
| なし | 何も返さない |
| bool | キャリー |
| 1バイトの型（u8、i8、fnset の値など） | A |
| 2バイトの型（u16、i16、ポインタ） | A（下位）と X（上位） |
| 構造体 | すべてのフィールドを結果領域に置く |

配列は直接は返せず、返したい場合は構造体に入れます。大きなデータを返していることが、構造体の宣言として目に見えるようにするためです。

**結論**：上の表のとおり、戻り値の返し方は大きさで決まる。

## E. 配列とポインタ

### Q E-1. 構造体の配列と u16 の配列の並べ方について、メリット・デメリットと仕組みを教えてほしい。

**回答**

6502 のインデックス付きの読み込み `lda 基点,x` は「命令に埋め込んだ定数の基点＋X」を読むので、X には「基点から何バイト先か」を入れる必要があります。C と同じく1要素を連続して並べると、X に入れる値が「番号×構造体の大きさ」になり、掛け算が毎回必要です。フィールドごとに別の配列にすると、番号がそのままバイト位置になります。

| | フィールドごとの配列 | C と同じ並べ方 |
|---|---|---|
| 1要素の読み書き | 番号を X に入れて1命令 | 番号×大きさの計算が毎回必要 |
| ループ | `inx` / `dex` で次へ | X に大きさを足す処理が必要 |
| 要素数の上限 | 256 | 256 ÷ 構造体の大きさ |
| メモリ使用量 | 同じ | 同じ |
| 1要素を指すポインタ | 作れない | 作れる |
| 1要素をバイト列として扱う | できない | できる |
| モニタでのメモリの見え方 | 1要素が散らばる | 1要素が並ぶ |

全要素の1フィールドを更新するループでは、1要素あたり 12 サイクル対 20 サイクル程度の差が出ます。

フィールドごとの配列のデメリットは、どれも「1要素が連続したバイト列でない」ことに起因します。困るのは、外部との受け渡し（ディスク、シリアル）、ハードウェアが決めた形式（ビデオチップのスプライト表など）、メモリダンプでのデバッグ（コンパイラがアドレスの一覧を出力することで補う）です。1要素を指すポインタが作れない点は、番号を X で渡すほうが `(zp),Y` より速いため、ほとんど不利になりません。

u16 とポインタの配列を下位バイトの配列と上位バイトの配列に分ける方式も、仕組み、メリット、デメリットは同じです。

**結論**：構造体の配列はフィールドごと、u16 とポインタの配列は下位・上位ごとに分けるのを標準とする。連続したバイト列が必要な場合だけ `packed` で明示する。

### Q E-2. 配列の添字の範囲を守る方法について、もう少し説明してほしい。

**回答**

6502 には範囲外のメモリアクセスを止める仕組みがなく、長さ16の配列に添字20を使うと、隣の配列のデータを黙って読み書きします。

方式は3つあります。毎回実行時に検査する方式は安全ですが、アクセスのたびに比較と分岐が入り遅くなります。検査しない方式は最速ですが、不具合を防げません。この言語では、範囲を型で保証する方式を採用します。

範囲型は「この値は決まった範囲に収まることが確かめ済み」という印の付いた u8 です。生成されるコードの中では普通の u8 で、印はコンパイル時にしか存在しないため、実行時のコストはありません。範囲型の値は、範囲を必ず守れる次の方法でしか作れません。

| 作り方 | 実行時のコスト |
|---|---|
| 配列を回す for | なし |
| 定数（範囲外ならコンパイルエラー） | なし |
| 範囲を確かめる変換（`check()`、結果は `?` 付き） | 比較と分岐の2命令 |
| 下位ビットだけを取る変換（長さが2のべき乗のとき） | `and` の1命令 |

範囲型の値に演算をすると、結果は印のない u8 に戻ります。外から来た値は入口で1回だけ確かめ、以降は範囲型として受け渡すため、検査は外とのつなぎ目に集まります。

**結論**：添字には範囲型を使う。

### Q E-3. 範囲型を受け取るはずの関数の引数を u8 にしたらどうなるのか。検査の要・不要の記述はプログラマの責任なのか。

```
fn damage(u8 e) {
    enemies[e].hp -= 1;
}
```

**回答**

関数の中の `enemies[e]` がコンパイルエラーになります。範囲型の値を u8 の引数に渡すこと自体は、安全な方向の変換なので許可されますが、関数の中では e は 0〜255 のどれかとしか扱えないため、配列に使う時点で止まります。

検査が必要かどうかを判断するのはコンパイラで、プログラマの責任ではありません。プログラマが決めるのは、検査をどこで行うか（引数を範囲型にして呼び出し元で検査するか、関数の中で検査するか）だけで、検査がどこにもない状態ではコンパイルが通りません。

例外として、検査なしで範囲型の印を付ける `unchecked()` を用意します。ハードウェアの仕様上、範囲内であることがわかっている値などに使うもので、ここだけはプログラマの責任になります（Rust の `unsafe` に相当）。名前で検索できるので、不具合の調査対象を絞り込めます。

**結論**：検査の要否はコンパイラが型で判断する。プログラマの責任になるのは `unchecked()` を使った箇所だけ。

### Q E-4. 「指していないかもしれないポインタ」なんて発生するのか。

**回答**

この言語では、ほとんど発生しません。

| 一般の言語でヌルが生まれる場面 | この言語では |
|---|---|
| 初期化していないポインタ変数 | 初期化前の使用はエラーなので発生しない |
| ヒープの確保に失敗した | ヒープがないので発生しない |
| リスト構造の最後 | ヒープがないのでまれ。配列と添字で書くのが普通 |
| 検索して見つからなかった | 発生しうる |

残る「見つからなかった」は、ポインタに限らず添字や数値でも起きる問題です。そこで、ヌルという特別な値は言語に入れず、「値があるかないか」を表す `?` 付きの型を、どの型にも使えるようにします。

**結論**：ヌルポインタは作らない。代わりに、どの型にも使える `?` 付きの型を用意する。

### Q E-5. `?` 付きの型を使うと、コストはどのくらい増えるのか。`?` を付けなければ追加のコストはかからないのか。

**回答**

`?` を付けなければ、追加のコストは一切かかりません。付けた場合のコストは次のとおりです。

| 使い方 | 追加のコスト |
|---|---|
| 戻り値をすぐ分岐に使う | 4〜5サイクル（呼び出し先の `sec` / `clc` と、呼び出し元の `bcc` / `bcs`） |
| 使われない値がある型（範囲型など）を変数に保存 | 追加のメモリなし（使われない値を「なし」に流用）。確認に5〜7サイクル |
| すべての値が有効な型（u8 など）を変数に保存 | 追加で1バイト。確認に5〜7サイクル |

戻り値の場合、昔ながらの「見つからなければ $FF を返す」方式（呼び出し元で比較と分岐が必要）と同じか安く済み、C のヌルポインタの確認（2バイトを調べる）より安く済みます。

**結論**：`?` は使った場所にだけコストがかかり、そのコストは従来の方法と同等以下。

### Q E-6. `?` 付きの型は、不定値（ユーザー入力など）を取りうる場合に使うイメージか。Optional のようなものか。

**回答**

Swift や Java の Optional、Rust の Option と同じものです。

ただし、使う場面は「どんな値でもありうる」ではなく、「値があるかないか」が問題になる場面です。範囲型とは役割が異なります。

| 仕組み | 表すこと | 例 |
|---|---|---|
| 範囲型 | 値が決まった範囲に収まっているか | 敵の番号は 0〜15 |
| `?` 付きの型 | 値があるか、ないか | 探したが見つからなかった |

ユーザー入力そのものは、値は必ずあるので普通の u8 で表します。`?` を使うのは、検索の結果、待たずに戻るキー入力の確認（押されていなければ「なし」）、文字から数値への変換（変換できない文字なら「なし」）、範囲の確認（`check()` の結果）などです。

**結論**：`?` 付きの型は Optional であり、「値の有無」を表す。値の範囲の保証は範囲型が担う。

### Q E-7. `let e = enemies.index(n)` の e は enemies.idx 型ということか。文法上どのように定義されたのかがピンと来ない。

**回答**

検討時点の書き方では、配列の宣言から添字の型が暗黙に作られ、`if let` の左辺の型も省略されていたため、型の出どころが見えにくくなっていました。

そこで、Pascal や Ada の範囲型にならい、添字の型を先に名前を付けて宣言し、それを添字にして配列を宣言する書き方を標準とします。

```
type eid = 0..15;               // 0〜15 の値だけを取る型
enemy enemies[eid];             // eid を添字に使う配列（長さ16）
u8 enemy_score[eid];            // 同じ eid を添字に使う別の配列

fn on_key() {
    u8 n = read_key();          // 0〜255 のどれでもありうる値
    eid? r = eid.check(n);      // 範囲内なら eid の値、範囲外なら「なし」
    if let e = r {              // 値があれば、e（eid 型）として受け取る
        enemies[e].hp -= 1;
    }
}
```

型の名前がソースに書かれるので、値の型を追えます。また、同じ添字を使う複数の配列で1つの型を共有できます。手軽さのため、`u8 table[16];` のように長さを数字で書く宣言も残し、その場合は `table.idx` という型が自動で作られます。

**結論**：範囲型を `type 名前 = 下限..上限;` で宣言し、配列の添字に使う。数字で長さを書いた配列には `配列名.idx` 型が自動で作られる。

### Q E-8. `type eid = table.idx;` は合法か。また、同じ範囲の型を2回宣言した場合はどうなるか。

**回答**

`type eid = table.idx;` は合法とし、「table.idx の別名」として同じ型を表します。

同じ範囲を書いて2回宣言した型（`type eid = 0..15;` と `type iid = 0..15;`）は、別の型として扱い、混用はエラーにします。範囲が同じでも意味が違う値はよくあり、同じ型とみなすと、後で片方の範囲を変えたときに、それまで通っていたコードの意味が黙って変わり、不具合になるためです（仕様検討者の判断による）。型の同一性を範囲ではなく宣言で決めておけば、そうした変更はコンパイルエラーとして表に出ます。

**結論**：範囲型は宣言ごとに別の型とする（名前による型の区別）。共有したい場合は別名で明示する。

### Q E-9. `?` を使うということは、255 は使えなくなるということか。

**回答**

いいえ。「ある・なし」の表し方はコンパイラが型ごとに選ぶため、プログラマが使える値は減りません。

| 場面 | 「ある・なし」の表し方 | 255 |
|---|---|---|
| 戻り値（`u8?`） | キャリーフラグ。値は A | 使える |
| 変数に保存（`u8?`） | 「ある・なし」用にもう1バイト使う | 使える |
| 変数に保存（範囲型 `eid?`） | 使われない値の $FF を「なし」にする | もともと eid の値ではない |

「なしを $FF で表すので 255 が使えない」というのは、`?` を使わない従来の方法の欠点で、`?` 付きの型はそれを解消する仕組みです。

**結論**：`?` を付けても、その型の値の範囲は狭まらない。

## F. I/O と割り込み

### Q F-1. 割り込み処理の中で `cli` を禁止するのはなぜか。

**回答**

IRQ が入ると、CPU は自動で I フラグを立て、割り込み処理が終わる（`rti` でフラグが戻る）まで次の IRQ を待たせます。割り込み処理の中で `cli` を実行すると、処理の途中で次の IRQ が入り、割り込み処理が入れ子で動きます。これを禁止する理由は3つあります。

1つめは、スタックの予算が計算できなくなることです。入れ子が何段重なるかは割り込みの頻度で決まり、コンパイル時にはわかりません。

2つめは、ローカル変数が壊れることです。ローカル変数は固定アドレスにあるため、入れ子で動いた内側の実行が、外側の実行のローカル変数を上書きします。入れ子の割り込みは実質的に再帰呼び出しであり、再帰を禁止したのと同じ理由で許可できません。

3つめは、無限の入れ子の危険です。6502 の IRQ は、信号が出ている間ずっと割り込みを要求し続けます。割り込みの原因になったチップのフラグを消す前に `cli` すると、すぐにまた割り込まれ、スタックが一周して暴走します。

長い割り込み処理の最中に急ぎの割り込みを受け付けたい場合は、割り込み処理を短くして時間のかかる処理をメインに任せるか（リングバッファなど）、急ぎの処理を NMI にします。NMI は1段しか重ならないため、スタックの予算も計算できます。

**結論**：割り込み処理の中での `cli` は禁止。

### Q F-2. `cycles()` で、周波数（時間）によるサイクル指定もあると便利か。なくてもよいなら不要。

**回答**

あると便利です。KIM-1 級から Apple II 級へ育てる過程でクロックを変える可能性があり、周辺チップのデータシートの待ち時間は「40 マイクロ秒以上」のように時間で書かれているためです。サイクル数だけで書いていると、クロックを上げたときに待ち時間が黙って短くなり、動かなくなります。時間で書いておけば、ターゲット定義のクロックを書き換えるだけで、コンパイラがサイクル数を計算し直します。

専用の文法は不要で、時間をサイクル数に変換するコンパイル時の関数 `us()` を標準で用意すれば済みます。時間がちょうどのサイクル数にならない場合は、警告を出したうえで切り上げます。

また、時間で考えると、データシートの待ち時間の多くは「ちょうど」でも「上限」でもなく「最低これだけ待つ」という下限であることから、サイクル数を扱う形を次の3つにします。

| 形 | 意味 | 主な用途 |
|---|---|---|
| `cycles(n) { }` | ちょうど n サイクル（足りない分は `nop` で埋める） | パルスの幅、ビデオ表示のタイミング |
| `max_cycles(n) { }` | n サイクル以内（超えたらエラー） | 時間内に終わらせたい処理 |
| `delay(n);` | 最低 n サイクル待つ（コンパイラが待ちループを作る） | 周辺チップの待ち時間 |

どれも `delay(us(40));` のように時間で書けます。

**結論**：`cycles`・`max_cycles`・`delay` の3つの形を用意し、時間指定はコンパイル時の関数 `us()` で行う。


### Q F-3. 割り込み処理の中で atomic を省略できる場面を、例で見たい。

**回答**

6502 では、IRQ でも NMI でも、割り込みが入るとすぐに CPU が I フラグを立てます。そのため、割り込み処理の実行中は、メインも IRQ も割り込みません。`atomic` が必要なのは割り込まれる側（メイン）だけで、割り込む側（割り込み処理）には不要です。

- 割り込み処理の中で 16 ビットの `TICKS` を増やす：省略できる（メインの側で読むときは `atomic` が必要）
- メインが書いた 16 ビットの値を、割り込み処理の中で読む：省略できる（メインの側で書くときは `atomic` が必要）
- NMI 処理の中で、メインや IRQ 処理と共有する変数を操作する：省略できる（NMI の実行中も I フラグが立っているため）
- NMI と共有する変数：省略できない。NMI は IRQ 処理の途中でも入り、`atomic` でも止められないため、1 命令の操作だけに限る（これまでの規則どおり）

**結論**：割り込み処理の中では `atomic` を省略できる（書いても何も生成せず、警告も出さない）。NMI と共有する変数は除く。あわせて、`atomic` はブロックの最後の式を値として返せるようにする（本編 8.5節、8.6節）。

## G. 列挙型と文字・文字列

### Q G-1. 何も付けない `""` は、長さも終端も付けない、という仕様はいまいちか。

**回答**

いまいちではなく、この言語の方針に合った良い仕様です。

何も付けない `"HELLO"` の型を、長さがコンパイル時に決まっている文字の配列 `char[5]` にします（Rust の `b"..."` と同じ考え方）。長さは型が持っているため、実行時に長さや終端を持たなくても、`for` で回すなどの処理は問題なく書けます。

長さ付きの文字列 `str` を受け取る関数に、何も付けない文字列を渡すとコンパイルエラーになります。形式を書き忘れても黙って別の形式になることはなく、型の不一致として必ず検出されます。代わりに、長さ付きの文字列を使うたびに `p` を書く手間が増えます。

| 書き方 | 中身（"HI" の場合） | 型 |
|---|---|---|
| `"HI"` | `48 49` | `char[2]`（長さは型が持つ） |
| `p"HI"` | `02 48 49` | `str`（長さ付き） |
| `z"HI"` | `48 49 00` | 0終端の文字列 |
| `hi"HI"` | `48 C9` | 最上位ビット終端の文字列 |

**結論**：何も付けない `""` は、長さも終端もない `char[N]` とする。長さ付きの文字列は `p""` で明示する。

### Q G-2. `@screen` を付けたときの仕様のイメージがつかない。

**回答**

`@screen` は、「この文字列を、画面メモリに直接書き込めるバイトに、コンパイル時に変換しておく」という指定です。

たとえば Apple II 級の画面では、画面メモリに $C1 を書くと普通の `A` が表示され、ASCII の `A`（$41）を書くと点滅する `A` になります。ASCII のままの文字列を画面メモリにコピーすると、表示がおかしくなります。

変換表は、ターゲット定義の中で文字の範囲と値の範囲の対応として書きます。

```
encoding screen {
    ' '..='?' => $A0..=$BF;     // 空白から '?' まで：ASCII に $80 を足した値
    '@'..='_' => $C0..=$DF;     // '@' から '_' まで（大文字を含む）：同上
}
```

ソースに `p"HI"@screen` と書くと、コンパイラはこの表で変換し、プログラムに `02 C8 C9` を置きます。表にない文字（この例では小文字）はコンパイルエラーです。実行時には変換の処理はなく、画面メモリへのコピーだけで正しく表示されます。

変換表は自由に定義できるため、7セグメント LED の点灯パターン（`'0' => $3F` など）のように、文字以外のバイトへの変換にも使えます。

さらに、変換表ごとに文字と文字列を別の型（`char@screen`、`str@screen`）にします。ASCII の文字列を受け取る関数に画面用の文字列を渡すとコンパイルエラーになり、取り違えを防げます。

**結論**：`@変換表` は、ターゲット定義の変換表によるコンパイル時の変換。変換表ごとに別の型とする。指定がなければ ASCII。

## H. モジュールとライブラリ

### Q H-1. インターフェースと実装を分けて bind で選ぶなら、ターゲット定義の機能の一覧（screen、keyboard など）も bind にまとめてよいのではないか。困ることはあるか。

**回答**

まとめるのが良い案です。「機能がある」を「その機能のインターフェースに実装が bind されている」と定義すれば、機能の一覧と bind の食い違い（一覧に書いたのに実装がない、など）が原理的に起きなくなります。`target.has(screen)` は「screen が bind されているか」を意味します。

困る点は、コードを伴わない性質（拡張 RAM の有無、画面の幅など）を bind で表せないことです。これらはターゲット定義に名前付きの定数として書き、`target.名前` で読めるようにします。

その結果、ターゲット定義に書くのは、CPU とクロック、bind、定数の3種類になり、`features = [...]` の一覧は廃止します。

**結論**：機能の有無は bind で表す。コードを伴わない性質はターゲット定義の定数で表す。

### Q H-2. 機能を bind で表す方式について、コンパイル引数、設定ファイル、ソースの書き方を詳しく説明してほしい。

**回答**

関わるファイルは、プロジェクトファイル（`ax65.proj`：入口、import の探索場所、対応ターゲットの一覧、既定のターゲット）、ターゲット定義ファイル（`*.target`：CPU、クロック、メモリ、bind、定数）、ソースの3種類です。

ターゲット定義は ax65 と同じ文法で書き、式や bind のモジュール名を検査できるようにします。マシンの成長に合わせて `target v3 extends v2 { ... }` のように前の構成を引き継げます。

コマンドラインでは、`-t` でターゲットを、`-D` でビルドの設定を、`--bind` で bind の一時的な差し替え（エミュレータでの試験など）を指定できます。`ax65 check --all-targets` で、プロジェクトのすべてのターゲットについて型まで検査します。

ソースでは、標準ライブラリなどがインターフェース（`interface screen { ... }`）を宣言し、マシンごとの実装（`impl screen { ... }`）を別のファイルに書きます。使う側はインターフェースの名前で `import` し、bind されていないターゲットで使う部分は `const if target.has(screen)` で囲みます。囲まずに使うとエラーです。

具体的な書き方は本編 2章と 11章を参照してください。

**結論**：プロジェクトファイル、`extends` 付きのターゲット定義、`interface` / `impl` / `bind` の組み合わせで機種の違いを表す。

### Q H-3. init がないモジュールのコストは0と考えてよいか。

**回答**

はい。`init` を書かなければ、起動時のコードは何も作られません。書いた場合も、`init` は1回しか実行されないため、起動の手順の中に中身を直接展開し、`jsr` / `rts` のコストはかかりません。

**結論**：`init` がなければコストは0。ある場合も中身の命令の分だけ。

### Q H-4. 使っていないモジュールの init が実行されることについて、警告を出したり、明示的に抑制したりする方法がほしい。

**回答**

import したモジュールの公開されたものを1つも使っていない場合に警告を出し、そのモジュールに `init` があれば起動時に実行されることも示します。`init` だけが目的の場合は `import hw.via for init;` と書くと警告が出ません。`for init` を付けたモジュールの関数を使った場合は、意図とコードの食い違いとして警告を出します。

一方、import したモジュールの `init` を実行させない方法は用意しません。モジュールの関数は `init` が済んでいることを前提に書かれているため、飛ばすと誤動作の原因になるからです。

**結論**：使っていない import には警告を出し、`for init` で抑制できる。`init` を止める方法は用意しない。

## I. 最適化（サンプル meteor の性能比較から）

### Q I-1. 比較で示された「コード量」は、アセンブリのソースの量か。

**回答**

いいえ。アセンブルした後の機械語のバイト数で、6502 のメモリに実際に読み込まれる大きさです。たとえば `lda M_WAIT,x` は機械語の `BD 9F 05` の 3 バイトになります。6502 の命令は 1〜3 バイトなので、バイト数と命令の数は比例しません。変数をゼロページに置くと、3 バイトの命令の多くが 2 バイトになります。

**結論**：コードの大きさは、機械語のバイト数で比べる。

### Q I-2. 関数のインライン化を明示する仕組みはあったか。

**回答**

`inline` の明示（議題13 の清書案では `#[inline]`）がありました。比較の結果、めったに通らない枝で呼ばれる関数を展開すると、ループが大きくなってページ境界をまたぎ、かえって遅くなることがわかったため、「展開しない」指定も加えます。

| 属性 | 意味 |
|---|---|
| `#[inline]` | 展開してよい。最適化オプションがなくても展開する |
| `#[inline(always)]` | 必ず展開する。できなければコンパイルエラー |
| `#[inline(never)]` | 決して展開しない |
| `#[cold]` | めったに呼ばれない関数。`-O speed` でも展開せず、ループの外に置く |

**結論**：インライン化の指定は上の 4 つの属性とする（本編 5.8節）。

### Q I-3. -O は大きさ優先を既定にしてよいのではないか。それが大きさと速さの両方に最も効くのだから。

**回答**

そのとおりです。meteor の比較では、大きさを優先した版が、-O より 10 % 小さく、速さも最も速い版とほぼ同じでした。6502 では、命令を小さくすること（ゼロページの使用、呼び出しの削減、ループを小さく保つこと）が、そのまま速さにつながるためです。

そこで、`-O` を大きさ優先の標準の最適化とし、コードが大きくなっても速さを優先したい場合のために `-O speed` を残します。`-O size` という別のオプションは作りません。

あわせて、ポインタの引数も A と X で渡すことを標準の規則にしました（呼び出しのたびに 4 バイト小さくなる）。文字列の表、文字列の後ろの共有、データの圧縮は、プログラマが必要に応じて行うものとし、言語の仕様には入れません。中間コードによる圧縮は、将来の拡張として余地だけを残します。

**結論**：最適化オプションは、なし／`-O`（大きさ優先）／`-O speed`（速さ優先）の 3 段階とする（本編 15章）。（Q I-4 で段階の名前と既定を変更）

### Q I-4. 最適化の段階を -O0、-O1（初期仕様）、-O2（今回仕様）、-Os（速度優先）とし、既定を -O2 にしてほしい。

**回答**

そのように変更します。

| 段階 | 内容 |
|---|---|
| `-O0` | 最適化をしない |
| `-O1` | 版0.1 の最適化（小さな関数も展開する） |
| `-O2` | 大きさを優先する最適化（**既定**） |
| `-Os` | `-O2` に加えて速さを優先する |

既定が `-O2` になったため、ゼロページへの自動配置は、何も指定しなければ行われることになります（Q C-1 では「既定は明示のみ、最適化オプションで自動配置」としていた）。配置を完全に予測したい場合は `-O0` を使います。サイクル数を保証するブロックとインラインアセンブリが参照する変数は、どの段階でも自動配置の対象外のままです。

なお、GCC などでは `-Os` は大きさ優先を意味しますが、ax65 では速さ優先の意味になる点を、仕様書に明記しました。

**結論**：最適化は `-O0`／`-O1`／`-O2`（既定）／`-Os` の 4 段階とする（本編 15章）。

## J. 古い版で書いたソースから見つかった点

古い版の仕様でソースを書いたときに見つかった、仕様の抜けと、その決定です。

### Q J-1. 書き込む側が1つの shared は、更新にも atomic が必要か。

**回答**：書き込む側が1つしかなければ、書き込む側が読む途中で値が変わることはありません。また、1バイトの書き込みは1命令で終わるので、読む側は古い値か新しい値のどちらかを読みます。そこで、書き込む側の読み込みと、1バイトの書き込み（読んで計算して書き戻す場合も含む）には `atomic` を不要とします。2バイト以上の書き込みと、読む側の2バイト以上の読み込みには、これまでどおり必要です。

**結論**：書き込む側が1つの `shared` に例外を設ける（本編 8.5節）。

### Q J-2. cycles(n) は、ブロックの外の命令（I/O への書き込みなど）を含めて数えるのか。

**回答**：6502 の書き込みは命令の最後のサイクルに行われるため、パルスの幅と、ブロックの中の命令の合計は一致しません。そこで2つの形に分けます。`cycles(n)` はブロックの中の命令の合計だけを数えます。パルスの幅のような I/O の間隔は、新しく設ける `io_span(n)` で、ブロックの中の最初と最後の I/O の読み書きの間隔として書きます。

**結論**：`cycles(n)` はブロックの中の合計、I/O の間隔は `io_span(n)`（本編 9章）。

### Q J-3. 配列や構造体の初期値はどう書くか。

**回答**：Rust と揃えます。配列は `[1, 2, 3]`、`[v; N]`、構造体は `name { field: value, ... }`（すべてのフィールドを書く）と、構造体更新構文 `name { hp: 3, ..BASE }` です。「全バイトが 0」を表す特別な値は用意しません。値がすべて 0 の部分は、コンパイラが `stz` で初期化します。

**結論**：配列と構造体の値は Rust と同じ書き方とする（本編 3.8節）。

### Q J-4. u8 から char へは変換できるか。

**結論**：`n as char` で変換できる。`char` は1バイトで 0〜255 のどの値も持てる。変換表付きの文字型への変換（`as char@screen`）も同様（本編 3.6節）。

### Q J-5. for の範囲の終わりに変数を書けるか。

**結論**：書ける。ループ変数の型は両端の型と同じ。u8 なら上限が 256 回と型から決まるので、割り込み処理の中などでも使える。範囲型のまま一部を回すときは `eid::range(a, b)` を使う（本編 6.2節）。

### Q J-6. ページ単位の配列の &buf は何を指すか。

**結論**：配列全体の先頭（＝最初のページの先頭）。`&buf[k]` は k 番目のページの先頭。型はどちらも `ptr<u8>`（本編 3.9節）。

### Q J-7. match の腕の右辺には、式とブロックのどちらを書くのか。

**結論**：Rust と同じく両方書ける。式の後ろにはカンマが必要で、ブロックの後ろでは省略できる（本編 6.4節）。

### Q J-8. 変換表の「1文字 → 1値」はどう書くか。

**回答**：「1文字 => 1値」（`'\r' => $8D;`）と「文字の範囲 => 値の範囲」（`'A'..='Z' => $C1..=$DA;`）の2つの形にします。範囲は、`..` の規則（終わりを含まない）と食い違わないように `..=` で書きます（これまでの例の `' '..'?'` も直しました）。あわせて、文字のエスケープ（`'\n'`、`'\r'`、`'\x41'` など）を言語全体で使えるようにします。

**結論**：変換表は2つの形で書き、範囲は `..=`（本編 3.6節）。

### A. 全体方針

<a id="qa-a1"></a>
#### A-1. ハードウェアの制約を、言語の制約で抑えられるか

- **質問**：たとえば、関数の呼び出しが深くなったらエラーにする、スタック変数を複数定義したらエラーにする、といった形で、6502 の制約を言語の制約にできないか。
- **回答**：可能です。関数の深さの制限は採用しました。再帰を禁止すれば、呼び出し関係は輪のないグラフになり、最も深い経路のスタック使用量を正確に計算できます。一方、「スタック変数の個数の制限」は別の形にしました。再帰がなければローカル変数をスタックに置く必要がなく、同時に使われない関数同士のローカル変数を同じ固定アドレスに重ねられるからです。制限すべきは個数ではなく、重ねた後の合計のメモリ量です。
- **結論**：再帰の禁止、スタックの予算の検査、ローカル変数の重ね合わせ、合計のメモリ量の検査を採用した。
- **1.1 での仕様**：[7.5節](#s7-5)、[15.5節](#s15-5)、[4.8節](#s4-8)

<a id="qa-a2"></a>
#### A-2. Rust のように、言語仕様でハードウェアの制約をカバーできるか

- **質問**：Rust のように、言語の仕様で安全性を保証できるか。
- **回答**：可能で、条件は Rust より有利です。Rust が難しいのは、ヒープ、複数のスレッド、分割コンパイルを相手にするためです。AX65 は、64KB 以内、ヒープなし、スレッドなし（並行するのは割り込みだけ）、プログラム全体を一度に解析できる、という条件なので、徹底した静的な検査が現実的です。Rust の考え方を次のように当てはめました。

| Rust の考え方 | AX65 での対応 |
|---|---|
| Send / Sync（スレッド間の共有の安全性） | `shared` と `atomic`（[10.4節](#s10-4)、[10.5節](#s10-5)） |
| ライフタイム | ローカル変数のアドレスの規則（[4.9節](#s4-9)） |
| 組み込み向けの周辺機器の所有権 | I/O の所有者（[11.4節](#s11-4)） |
| `const fn` | `const fn`、`comptime fn`（[13.2節](#s13-2)） |
| （Rust にはない） | サイクル数の保証（[12.1節](#s12-1)） |

- **結論**：「危険な書き方はコンパイルを通さず、検査のコストは実行時に払わない」を基本方針とした。
- **1.1 での仕様**：[1.2節](#s1-2)

<a id="qa-sec-b"></a>
### B. 型と演算

<a id="qa-b1"></a>
#### B-1. 負の数を使うのはどういう場面か

- **質問**：符号付きの型は必要か。負の数を使うのはどういう場面か。
- **回答**：変化量や速度（`dx = -1`）、相対的な位置、差の計算、直線を描くアルゴリズムの誤差、音の波形、分岐命令の相対アドレスなどです。足し算と引き算は符号の有無にかかわらず同じ命令で、コストが増えるのは大小比較、16 ビットへの拡張、右シフト、割り算と表示だけです。
- **結論**：`i8`・`i16` を別の型として用意する。符号の混在はエラー。例外として「位置（`u8`）に変化量（`i8`）を足す」操作は変換なしで許す。
- **1.1 での仕様**：[3.1節](#s3-1)（1.0 では `u8 - i8` も同じ扱いにした）

<a id="qa-b2"></a>
#### B-2. あふれたときは一周して戻る扱いでよいか

- **質問**：8 ビットの値があふれたときは、一周して戻る扱いでよいか（C もそうだったはず）。
- **回答**：一周して戻る扱いにしました。ただし C で一周して戻るのは符号なしだけで、符号付きのあふれは未定義動作です。AX65 では、`adc`・`sbc` がどちらでも同じ動作なので、符号付きも符号なしも一周して戻ると定義しました。
- **結論**：あふれは常に一周して戻る（定義された動作）。検出したいときは `checked_add`、止めたいときは `saturating_add` を使う。
- **1.1 での仕様**：[5.2節](#s5-2)。メソッドの名前は、当時の `sat_add` から、Rust と同じ `saturating_add` に変えた（[K-13](#qa-k13)）

<a id="qa-sec-c"></a>
### C. 変数と記憶域

<a id="qa-c1"></a>
#### C-1. ゼロページの配置は、既定では明示だけにし、最適化で自動にできないか

- **質問**：ポインタ以外の変数をゼロページに置くかどうかは、既定では明示したものだけにし、最適化オプションで自動にする、という形はどうか。
- **当時の前提**：最適化オプションは「なし」と「`-O`」の 2 つで、既定は「なし」だった。
- **回答**：採用しました。普段は配置が完全に予測でき、速さが必要なときだけコンパイラに任せられます。自動の配置は、明示した変数を置いた後の空きだけを使う、サイクル数を保証するブロックとインラインアセンブリから参照される変数は対象外にする、などの規則を付けました。
- **結論**：既定は明示（当時の `zp`）だけ。最適化オプションを付けたときだけ自動で配置する。
- **1.1 での仕様**：その後、最適化の既定が `-O2` になったため（[I-4](#qa-i4)）、**何も指定しなければ自動で配置する**に変わった。配置を完全に予測したい場合は `-O0` を使う。明示は `#[zp]` 属性（[4.7節](#s4-7)）。

<a id="qa-c2"></a>
#### C-2. グローバル変数の初期値と、プログラムの実行場所

- **質問**：グローバル変数の初期値をどう扱うか。プログラムは RAM で実行するのか ROM で実行するのか。
- **回答**：RAM に読み込んで実行する場合、2 回目の実行で前回の値が残ってしまうので、起動時に毎回設定し直すことにしました。実行場所は両方に対応し、ターゲット定義で切り替えます。
- **結論**：グローバル変数は初期値を必須とし、起動時に毎回設定する（初期化しない変数は例外）。RAM と ROM の両方の実行に対応する。
- **1.1 での仕様**：[4.6節](#s4-6)、[16.4節](#s16-4)。その後、比較の結果から「初期値が 0 の変数は元データを持たずに `stz` で初期化する」規則を加えた（[19.5節](#s19-5)）。初期化しない変数は `#[noinit]` で示す。

<a id="qa-sec-d"></a>
### D. 関数と呼び出し規約

<a id="qa-d1"></a>
#### D-1. 引数を A・X・Y で渡すと、関数の中で退避が必要になるのでは

- **質問**：引数を A・X・Y に入れて渡しても、関数の中で処理するならレジスタを空けるための退避が必要になる。考え方を変える必要はないか。
- **回答**：引数の使われ方は「すぐ使う」と「後で使う」に分かれます。すぐ使う場合、レジスタ渡しなら書き込みも読み込みも不要です。後で使う場合は、呼び出し先が入口で自分の固定領域にしまいますが、固定領域で渡す方式でも、呼び出し元が同じ場所に書いています。書き込みの場所は同じで、誰が書くかが違うだけです。レジスタ渡しは損をせず、呼び出す場所が多いほどコードが小さくなります。
- **結論**：引数は「呼び出し先が持つ固定アドレスの変数」で、レジスタはそこへ届ける近道と考える。先頭 3 バイトを A・X・Y で渡す。
- **1.1 での仕様**：[15.2節](#s15-2)。当時はポインタの引数だけ「呼び出し元が呼び出し先のゼロページに直接書く」規則だったが、比較の結果、ポインタも A・X で渡すように変えた（呼び出しのたびに 4 バイト小さくなる）。

<a id="qa-d2"></a>
#### D-2. 関数とサブルーチンの違い、複数の戻り値

- **質問**：複数の値を返すと、呼び出し元で退避が必要になる。関数とサブルーチンのどちらの考え方がよいか。壊すレジスタだけを退避する仕様があれば問題ないのか。
- **回答**：関数とサブルーチンは分けず、「入口と出口のデータを宣言したサブルーチン」として 1 つにまとめました。壊すレジスタだけを退避する仕様は、レジスタに持っている値を呼び出しをまたいで保つ問題を解決します。レジスタが本当に別の用途に必要な場合の書き込みは、どの方式でも消せないので、それを 1 回で済ませるのが構造体の結果領域です（[D-5](#qa-d5)）。
- **結論**：関数とサブルーチンを 1 つの仕組みにする。状態を書き換えない関数には `pure` を付けられる。
- **1.1 での仕様**：[7.1節](#s7-1)、[7.2節](#s7-2)、[15.4節](#s15-4)。状態を書き換えない関数の印は、その後 `pure` から `const fn` に変わった（[K-17](#qa-k17)）。

<a id="qa-d3"></a>
#### D-3. スタックの予算の詳しい説明

- **質問**：スタックの深さの予算について、詳しく知りたい。
- **回答**：ローカル変数をスタックに置かないので、積まれるのは戻り番地、割り込みで CPU が積むもの、割り込み処理のレジスタの退避、`atomic` の `php` などだけです。メイン・IRQ・NMI のすべての経路の最大を合計して予算と比べます。6502 のスタックは 256 バイトで、使い切ると黙って一周し、古い戻り番地を壊して暴走します。予算の検査があれば、この暴走はコンパイルが通った時点で起こりえません。実際の使用量は小さく、20 段の呼び出しでも 40 バイト程度です。
- **結論**：メイン・IRQ・NMI の最深経路の合計が予算を超えたら、経路を示してエラーにする。
- **1.1 での仕様**：[15.5節](#s15-5)。予算はターゲット定義の `stack`（[16.2節](#s16-2)）。

<a id="qa-d4"></a>
#### D-4. ROM ルーチンの呼び出し

- **質問**：ROM ルーチンの宣言について詳しく知りたい。
- **回答**：ROM のルーチンはコンパイラが作ったものではないので、引数のレジスタ、壊すレジスタ、スタックの使用量がわかりません。たとえば X をループの番号に使っている途中で、X を壊す ROM ルーチンを呼ぶと、番号が狂います。そこで、これらを宣言させます。宣言が実際と違ってもコンパイラは見抜けないので、Rust の `unsafe` と同じく、検査できない部分を宣言の 1 か所に閉じ込める仕組みです。
- **結論**：ROM ルーチンは、引数のレジスタ、アドレス、壊すもの、スタックの使用量を宣言する。
- **1.1 での仕様**：[7.6節](#s7-6)

<a id="qa-d5"></a>
#### D-5. 戻り値を 1 つにして、ポインタで返すのはどうか

- **質問**：戻り値は C のように 1 つでよいのでは。A に値を返すか、ゼロページにポインタを返すような形は。
- **回答**：戻り値を 1 つにすること自体はよいですが、ポインタで返す方式は 6502 ではよくありません。指す先を用意する場所がなく（ヒープがなく、ローカル変数のアドレスも返せない）、毎回同じ場所ならポインタにする意味がありません。また `(zp),Y` で読むたびに Y を使い、サイクルも余分にかかります。代わりに構造体を値で返し、フィールドを呼び出し先の結果領域に置いて、呼び出し元が直接読む形にしました。
- **結論**：戻り値は 1 つ。複数の値は構造体にまとめて返す。
- **1.1 での仕様**：[15.3節](#s15-3)

<a id="qa-d6"></a>
#### D-6. 構造体の戻り値は 2 つまでしか値を持てないのか

- **質問**：2 つまではレジスタ、3 つ以上はメモリ、ということか。
- **当時の前提**：その前の案では、構造体を使わずに複数の値を返す書き方で、「1 つめはレジスタ、2 つめ以降はメモリ」としていた。
- **回答**：構造体で返す場合はレジスタを使わず、すべてのフィールドを結果領域に置きます。フィールドの数に制限はありません。結果領域は固定アドレスなので、呼び出し元は普通の変数と同じように読めます。
- **結論**：構造体の戻り値は、すべてのフィールドを結果領域に置く。
- **1.1 での仕様**：[15.3節](#s15-3)

<a id="qa-d7"></a>
#### D-7. 戻り値に使える型

- **質問**：戻り値は u8、i8、u16、i16、bool、構造体しか持てない、という理解で合っているか。
- **回答**：ほぼ合っています。ほかに、ポインタ、関数集合の値、戻り値なしがあります。将来の型の追加に備えて、型の一覧ではなく大きさで返し方を決めました。配列は直接返せず、構造体に入れます。
- **結論**：返し方は大きさで決める（なし／bool はキャリー／1 バイトは A／2 バイトは A と X／構造体は結果領域）。
- **1.1 での仕様**：[15.3節](#s15-3)。その後 `Option<T>`（有無をキャリーで返す）が加わり、1.0 で 3 バイトの型（A・X・Y）と 4 バイト以上の型（結果領域）を表に加えた（[M-15](#qa-m15)）。

<a id="qa-sec-e"></a>
### E. 配列・範囲型・Option

<a id="qa-e1"></a>
#### E-1. 構造体の配列の並べ方

- **質問**：構造体の配列の並べ方について、メリット・デメリットと仕組みを知りたい。
- **回答**：6502 の `lda 基点,x` は「命令に埋め込んだ基点＋X」を読むので、X には基点からのバイト数を入れます。C と同じく 1 要素を連続して並べると、X に「番号×構造体の大きさ」を入れる必要があり、掛け算が毎回要ります。フィールドごとに別の配列にすると、番号がそのままバイトの位置になります。全員の体力を減らすループでは 1 要素あたり 12 対 20 サイクルの差が出て、要素数の上限も 64 から 256 に増えます。デメリットは 1 要素が連続したバイト列でないことで、ファイルや通信の形式、ハードウェアが決めた表に合わせる場合に困ります。
- **結論**：フィールドごとの配列を標準にし、連続して並べる必要があるときだけ明示する。u16 の配列も下位・上位に分ける。
- **1.1 での仕様**：[3.8節](#s3-8)。明示の書き方は、当時の `packed enemy received[16];`（配列に付ける）から、`#[packed]` を構造体に付ける形に変わった。

<a id="qa-e2"></a>
#### E-2. 配列の添字の範囲を守る方法

- **質問**：添字の範囲を守る方法について、もう少し説明がほしい。
- **当時の書き方**：範囲型は `type eid = 0..15;`（`..` が終わりを含む扱いだった）、範囲を確かめる変換は `eid.check(n)`、結果の型は `eid?` と書いていた。
- **回答**：6502 には範囲外のアクセスを止める仕組みがなく、長さ 16 の配列に 20 を使うと隣の配列を黙って壊します。実行時に毎回検査すると遅く、検査しなければ不具合を防げません。そこで「範囲に収まることを確かめ済み」という印の付いた型（範囲型）を用意しました。印はコンパイル時にしかないので、実行時のコストはありません。範囲型の値は、for で回す、定数、範囲の確認、下位ビットだけを取る、の方法でしか作れません。
- **結論**：添字に範囲型を使う。検査は外から来た値を受け取る入口で 1 回だけ行う。
- **1.1 での仕様**：[3.4節](#s3-4)。1.1 の書き方は `range Eid = 0..16;`、`Eid::check(n)`、`Option<Eid>`。

<a id="qa-e3"></a>
#### E-3. 範囲型を受け取るはずの引数を u8 にしたらどうなるか

- **質問**：`fn damage(e: u8) { ENEMIES[e].hp -= 1; }` と書いたらどうなるか。検査の要・不要の記述はプログラマの責任か。
- **回答**：関数の中の `ENEMIES[e]` がエラーになります（呼び出し側で範囲型を u8 として渡すこと自体は安全なので許される）。検査が必要かどうかはコンパイラが型で判断し、プログラマが決めるのは検査をどこで行うかだけです。検査がどこにもなければコンパイルは通りません。例外として、検査なしで印を付ける `unchecked()` を用意し、ここだけはプログラマの責任にしました。
- **結論**：検査の要否はコンパイラが判断する。プログラマの責任になるのは `unchecked()` だけ。
- **1.1 での仕様**：[3.4節](#s3-4)（`Eid::unchecked(n)`）。1.0 では、保証の対象外の部分を [1.2節](#s1-2) に一覧で示した（[M-1](#qa-m1)）。

<a id="qa-e4"></a>
#### E-4. 「指していないかもしれないポインタ」は発生するのか

- **質問**：ヌルポインタのような、指していないかもしれないポインタは、この言語で発生するのか。
- **回答**：ほとんど発生しません。初期化していないポインタは代入前の読み込みとしてエラーになり、ヒープがないので確保の失敗もリスト構造の終わりもありません。残るのは「探したが見つからなかった」くらいで、これはポインタに限らない問題です。そこでヌルという値は入れず、「値があるか、ないか」を表す型をどの型にも使えるようにしました。
- **結論**：ヌルポインタは作らない。値の有無を表す型を用意する。
- **1.1 での仕様**：[3.10節](#s3-10)、[3.11節](#s3-11)。当時は `u8?` と書いていたが、文法の統一で Rust と同じ `Option<u8>` になった（[K-13](#qa-k13)）。

<a id="qa-e5"></a>
#### E-5. 値の有無を表す型のコスト

- **質問**：値の有無を表す型を使うと、コストはどのくらい増えるか。使わなければコストはかからないのか。
- **回答**：使わなければコストはかかりません。戻り値では、キャリーで有無を返し（呼び出し先の `sec`・`clc` と、呼び出し元の分岐で 4〜5 サイクル）、昔ながらの「見つからなければ $FF を返す」方式や、C のヌルの確認と同じか安く済みます。変数に置く場合、範囲型のように使われない値がある型は、その値を「なし」に流用するので追加のメモリは要りません。u8 のように全部の値が有効な型だけ、1 バイト増えます。
- **結論**：コストは使った場所にだけかかり、従来の方法と同等以下。
- **1.1 での仕様**：[3.11節](#s3-11)

<a id="qa-e6"></a>
#### E-6. 値の有無を表す型は、ユーザー入力のような不定値に使うのか

- **質問**：不定値（ユーザー入力など）を取りうる場合に使うイメージか。Optional のようなものか。
- **回答**：Swift や Java の Optional、Rust の Option と同じものです。ただし表すのは「値があるか、ないか」で、「どんな値でもありうる」ではありません。ユーザー入力そのものは値が必ずあるので普通の u8 です。使うのは、検索の結果、待たずに戻るキー入力（押されていなければ「なし」）、文字から数値への変換（変換できなければ「なし」）、範囲の確認の結果などです。値の範囲の保証は範囲型の役割です。
- **結論**：値の有無は Option、値の範囲は範囲型が担う。
- **1.1 での仕様**：[3.11節](#s3-11)

<a id="qa-e7"></a>
#### E-7. 範囲を確かめた結果の型は、どこで決まるのか

- **質問**：`if let e = enemies.index(n)` の `e` は `enemies.idx` 型ということか。文法上どう定義されたのかがピンと来ない。
- **当時の書き方**：配列 `enemy enemies[16];` を宣言すると、その添字の型 `enemies.idx` が自動で作られ、`enemies.index(n)` で範囲を確かめる案だった。型が配列の宣言から暗黙に作られ、`e` の型も書かれていないため、型の出どころが見えにくかった。
- **回答**：Pascal や Ada の範囲型にならい、添字の型を先に名前を付けて宣言し、それを添字にして配列を宣言する書き方に変えました。型の名前がソースに書かれるので値の型を追え、同じ添字を複数の配列で共有できます。
- **結論**：範囲型を先に宣言し、配列の添字に使う。
- **1.1 での仕様**：[3.4節](#s3-4)。`range Eid = 0..16;`、`static ENEMIES: [Enemy; Eid] = ...;`、`if let Some(e) = Eid::check(n)`。配列から自動で作る添字の型（`table.idx`）は、文法の統一のときに廃止した（`.` は値のフィールドとメソッドだけに使うため）。長さを数字で書いた配列は、変数の添字で読むときに `a.get(n)` を使う（[3.8節](#s3-8)）。

<a id="qa-e8"></a>
#### E-8. 同じ範囲の型は同じ型か。別名は書けるか

- **質問**：`type eid = table.idx;` は合法か。同じ範囲の型を 2 回宣言したらどうなるか。
- **当時の書き方**：範囲型の宣言にも別名にも `type` を使っていた。
- **回答**：別名は合法とし、同じ型として扱います。一方、同じ範囲で 2 回宣言した型（敵の番号とアイテムの番号など）は、別の型にしてエラーにすべき、というご判断をいただきました。範囲が同じでも意味が違う値はよくあり、同じ型とみなすと、後で片方の範囲を変えたときに、それまで通っていたコードの意味が黙って変わってしまうためです。
- **結論**：範囲型は宣言ごとに別の型（名前による区別）。共有するなら別名で明示する。
- **1.1 での仕様**：[3.4節](#s3-4)、[3.13節](#s3-13)。文法の統一で、新しい範囲型は `range`、別名は `type`（Rust と同じく別名だけ）に分けた。

<a id="qa-e9"></a>
#### E-9. 値の有無を表す型を使うと、255 は使えなくなるのか

- **質問**：「なし」を $FF で表すなら、255 は使えなくなるのか。
- **回答**：いいえ。表し方はコンパイラが型ごとに選びます。戻り値ではキャリーで有無を返すので 255 も使え、u8 の変数では有無のための 1 バイトを足します。$FF を「なし」に流用するのは、範囲型のように $FF がもともと値として使われない型だけです。
- **結論**：値の有無を表す型にしても、元の型の値の範囲は狭まらない。
- **1.1 での仕様**：[3.11節](#s3-11)

<a id="qa-sec-f"></a>
### F. 割り込み・I/O・タイミング

<a id="qa-f1"></a>
#### F-1. 割り込み処理の中で割り込みの許可（cli）を禁止するのはなぜか

- **質問**：なぜ `cli` は禁止なのか。
- **回答**：割り込み処理の中で許可すると、処理の途中で次の IRQ が入り、割り込み処理が入れ子で動きます。理由は 3 つです。入れ子の段数は割り込みの頻度で決まり、スタックの予算が計算できなくなる。ローカル変数は固定アドレスにあるので、入れ子の実行が外側の変数を壊す（入れ子の割り込みは実質的に再帰）。6502 の IRQ は信号が出ている間ずっと要求し続けるので、原因を消す前に許可すると無限に入れ子になる。急ぎの処理は、割り込み処理を短くするか NMI にします。
- **結論**：割り込み処理の中での割り込みの許可は禁止。
- **1.1 での仕様**：[10.2節](#s10-2)。当時の `cli` は、1.0 では組み込み関数 `irq_enable()` で書く（[F-4](#qa-f4)）。

<a id="qa-f2"></a>
#### F-2. 周波数（時間）でサイクル数を指定できると便利か

- **質問**：`cycles(n)` で、周波数によるサイクルの指定もあると便利か（なくてもよいなら不要）。
- **回答**：あると便利です。マシンを育てる途中でクロックを変える可能性があり、周辺チップの待ち時間はデータシートに「40 マイクロ秒以上」のように時間で書かれているからです。サイクル数で書いていると、クロックを上げたときに待ち時間が黙って短くなります。専用の文法は要らず、時間をサイクル数に変える `comptime fn` の `us()` を用意すれば済みます。また、待ち時間の多くは「最低これだけ待つ」という下限なので、`delay()` も加えました。
- **結論**：`cycles`・`max_cycles`・`delay` の 3 つの形を用意し、時間は `us()` で指定する。
- **1.1 での仕様**：[12.1節](#s12-1)、[12.2節](#s12-2)。その後、パルスの幅のための `io_span` が加わった（[F-8](#qa-f8)）。

<a id="qa-f3"></a>
#### F-3. 割り込み処理の中で atomic を省略できる場面の例

- **質問**：割り込み処理の中で `atomic` を省略できるところについて、例を見たい。
- **回答**：6502 では、IRQ でも NMI でも、割り込みが入るとすぐに I フラグが立つので、割り込み処理の実行中はメインも IRQ も割り込みません。`atomic` が必要なのは割り込まれる側（メイン）だけです。割り込み処理の中で 16 ビットの `TICKS` を増やす、メインが書いた 16 ビットの値を読む、といった操作は省略できます。ただし NMI は IRQ 処理の途中でも入り、`atomic` でも止められないので、NMI と共有する変数は 1 命令の操作に限ります。

```
shared(irq) TICKS: u16 = 0;
#[interrupt(irq)]
fn on_irq() { TICKS += 1; }             // 割り込み処理の中なので atomic は不要
fn ticks() -> u16 { atomic { TICKS } }  // メインの側では必要
```

- **結論**：割り込み処理の中では `atomic` を省略できる（書いても何も生成せず、警告も出さない）。NMI と共有する変数は除く。
- **1.1 での仕様**：[10.4節](#s10-4)。「1 命令の操作」の定義と NMI の規則は [M-2](#qa-m2) で定めた。

<a id="qa-f4"></a>
#### F-4. 割り込みの許可の方法

- **質問**：（サンプルを書いたときに見つかった、決まっていなかった仕様）`main` で割り込みを許可する方法をどうするか。
- **当時の前提**：起動時は `init` が終わるまで割り込みが止まっているが、許可する方法が決まっておらず、サンプルでは仮に `irq_enable()` と書いていた。
- **回答**：候補は、組み込み関数で許可・禁止する、すべての `init` の後に自動で許可する、許可だけを用意する、の 3 つでした。組み込み関数 `irq_enable()`・`irq_disable()` を選び、割り込み処理の中と `atomic` の中での `irq_enable()` をエラーにしました。
- **結論**：組み込み関数 `irq_enable()`・`irq_disable()` を用意する。
- **1.1 での仕様**：[10.3節](#s10-3)。1.0 では、`cycles()`・`io_span()` の中と、そこから呼ぶ関数の中もエラーにした（[M-17](#qa-m17)）。

<a id="qa-f5"></a>
#### F-5. atomic で値を返せるか

- **質問**：（サンプルで見つかった点）`atomic { TICKS }` のように、`atomic` で値を返せるようにするか。
- **当時の前提**：返せない場合は `let t: u16; atomic { t = TICKS; }` と書く必要があった。生成されるコードは同じ。
- **結論**：返せるようにする（ブロックの最後の式が値。Rust のブロック式と同じ）。
- **1.1 での仕様**：[10.5節](#s10-5)、[5.7節](#s5-7)

<a id="qa-f6"></a>
#### F-6. 読むだけの I/O の書き方

- **質問**：（サンプルで見つかった点）値を使わずに I/O を読むだけ（読むと状態が変わるレジスタ）の書き方をどうするか。
- **当時の前提**：生成するコード（`bit` 命令。A を壊さない）は、その前の比較で決まっていた。書き方は、`_ = X;`、`let _ = X;`、`X;` の 3 つの候補があり、私は文法の統一の結論に関係なく使える `_ = X;` を勧めた。
- **結論**：Rust と同じ `let _ = X;` にする（ご判断による）。
- **1.1 での仕様**：[11.3節](#s11-3)

<a id="qa-f7"></a>
#### F-7. 書き込む側が 1 つの shared も、更新に atomic が必要か

- **質問**：（古い版の仕様でソースを書いたときの指摘）仕様を文字どおり読むと、`shared(main)` の `TAIL` を更新するのにも `atomic` が必要になる。IRQ 側は読むだけなので、本来は不要なはず。
- **当時の前提**：「メインの側の 2 命令以上の操作は `atomic` が必要」という規則だけがあった。
- **回答**：書き込む側が 1 つなら、書き込む側が読む途中で値が変わることはなく、1 バイトの書き込みは 1 命令で終わるので、読む側は古い値か新しい値のどちらかを読みます。そこで、書き込む側の読み込みと 1 バイトの書き込み（読んで計算して書き戻す場合も含む）には `atomic` を不要にしました。2 バイト以上の書き込みと、読む側の 2 バイト以上の読み込みには、引き続き必要です。
- **結論**：書き込む側を指定した `shared` に例外を設ける。
- **1.1 での仕様**：[10.4節](#s10-4)。NMI と共有する変数には、この例外を使わない（[M-2](#qa-m2)）。

<a id="qa-f8"></a>
#### F-8. cycles(n) は、ブロックの外の命令も数えるのか

- **質問**：（古い版の指摘）例のようにブロックの外に書いた `PORTB = ...` の `sta` の 4 サイクルをパルスの幅に含めるのか、ブロックの中だけなのかが決まっていない。
- **回答**：6502 の書き込みは命令の最後のサイクルに行われるので、パルスの幅とブロックの中の命令の合計は一致しません（`sta`、`nop`、`nop`、`sta` のパルスの幅は 8 サイクル）。そこで 2 つに分けました。`cycles(n)` はブロックの中の命令の合計だけを数え、I/O の間隔は新しい `io_span(n)` で書きます。
- **結論**：`cycles(n)` はブロックの中の合計。I/O の間隔は `io_span(n)`。
- **1.1 での仕様**：[12.1節](#s12-1)

<a id="qa-sec-g"></a>
### G. 文字と文字列

<a id="qa-g1"></a>
#### G-1. 何も付けない "" は、長さも終端もない形でよいか

- **質問**：何も付けない `""` は長さも終端も付けない、という仕様はいまいちか。
- **当時の前提**：その前の案では、何も付けない `""` を長さ付きの文字列にしていた。
- **回答**：よい仕様です。何も付けない `"HELLO"` の型を `[char; 5]` にすれば、長さは型が持っているので困りません（Rust の `b"..."` と同じ考え方）。長さ付きの文字列を受け取る関数に渡すとエラーになるので、形式を書き忘れても黙って別の形式になることはありません。
- **結論**：何も付けない `""` は `[char; N]`。長さ付きは `p""`。
- **1.1 での仕様**：[2.7節](#s2-7)、[3.9節](#s3-9)

<a id="qa-g2"></a>
#### G-2. @screen を付けたときの仕様のイメージ

- **質問**：`@screen` の仕様のイメージがつかない。
- **回答**：`@screen` は、「この文字・文字列を、画面メモリに直接書けるバイトに、コンパイル時に変換しておく」という指定です。Apple II 級の画面では、画面メモリに $C1 を書くと普通の `A`、ASCII の $41 を書くと点滅する `A` になります。変換表はターゲット定義に書き、ソースの `p"HI"@screen` はプログラムに `02 C8 C9` として置かれます。実行時の変換はありません。7 セグメント LED の点灯パターンのように、文字以外のバイトにも使えます。さらに、変換表ごとに別の型にして、取り違えをエラーにします。
- **結論**：`@変換表` はコンパイル時の変換で、変換表ごとに別の型。指定がなければ ASCII。
- **1.1 での仕様**：[3.3節](#s3-3)、[16.5節](#s16-5)。変換表の範囲の書き方は、当時の `' '..'?'` から `' '..='?'` に直した（[G-3](#qa-g3)）。

<a id="qa-g3"></a>
#### G-3. 変換表の「1 文字 → 1 値」の書き方

- **質問**：（古い版の指摘）`'\n' => $8D;` のような書き方は、ターゲット定義の書式で決める必要がある。
- **当時の前提**：変換表の例は範囲だけ（`' '..'?' => $A0..$BF;`）で、しかもこの `..` は、後に決めた「`..` は終わりを含まない」という規則と食い違っていた。文字のエスケープも定義されていなかった。
- **回答**：「1 文字 => 1 値」と「文字の範囲 => 値の範囲」の 2 つの形にし、範囲は `..=` で書きます。同じ文字の重複と、範囲の両側の個数の違いはエラーです。あわせて、文字のエスケープを言語全体で使えるようにしました。
- **結論**：変換表は 2 つの形。範囲は `..=`。エスケープを定義する。
- **1.1 での仕様**：[16.5節](#s16-5)、[2.6節](#s2-6)

<a id="qa-g4"></a>
#### G-4. u8 から char への変換

- **質問**：（古い版の指摘）`char` から `u8` へは `as` で変換できるが、逆向きの記述がない。
- **結論**：`n as char` で変換できる。`char` は 1 バイトで 0〜255 のどの値も持てる。変換表付きの文字型への変換も同様。
- **1.1 での仕様**：[3.3節](#s3-3)、[3.14節](#s3-14)

<a id="qa-sec-h"></a>
### H. モジュールとターゲット

<a id="qa-h1"></a>
#### H-1. 機能の一覧も bind にまとめてよいのでは

- **質問**：インターフェースの実装を bind で選ぶなら、ターゲット定義の機能の一覧（screen、keyboard など）も bind でよいのでは。困ることがあれば教えてほしい。
- **当時の前提**：ターゲット定義に `features = [screen, serial, keyboard];` という機能の一覧を書き、`target.has(screen)` で調べる案だった。
- **回答**：まとめるのがよい案です。「機能がある」を「その機能のインターフェースに実装が bind されている」と定義すれば、一覧と bind の食い違い（一覧に書いたのに実装がない、など）が起きなくなります。困るのは、コードを伴わない性質（画面の幅、拡張 RAM の有無など）を bind で表せないことで、これはターゲット定義の名前付きの定数で表します。
- **結論**：機能の有無は bind で表す。コードを伴わない性質は定数で表す。機能の一覧は廃止する。
- **1.1 での仕様**：[16.6節](#s16-6)、[13.6節](#s13-6)

<a id="qa-h2"></a>
#### H-2. bind の仕組みの、ファイル・コマンドライン・ソースでの書き方

- **質問**：機能を bind で表す案について、コンパイル引数、設定ファイル、ソースの書き方を詳しく。
- **当時の書き方**：モジュールは `import hw.via;`、パスの区切りは `.`、ターゲット定義の定数は `const screen_width = 40;` だった。
- **回答**：関わるのは、プロジェクトファイル（入口、探す場所、対応するターゲット、既定のターゲット）、ターゲット定義（CPU、クロック、メモリ、bind、定数。`extends` で前の構成を引き継ぐ）、ソース（インターフェースと実装、使う側）の 3 種類です。コマンドラインでは `-t` でターゲット、`-D` でビルドの設定、`--bind` で bind の一時的な差し替えを指定し、`ax65 check --all-targets` で全ターゲットを検査します。
- **結論**：プロジェクトファイル、`extends` 付きのターゲット定義、`interface`・`impl`・`bind` の組み合わせで機種の違いを表す。
- **1.1 での仕様**：[16章](#s16)、[17章](#s17)、[8.4節](#s8-4)。1.1 の書き方は `use hw::via;`、`bind console = hw::acia_console;`、`const SCREEN_WIDTH: u8 = 40;`。

<a id="qa-h3"></a>
#### H-3. init がないモジュールのコストは 0 か

- **結論**：0。`init` を書かなければ起動時のコードは作られない。書いた場合も起動の手順に直接展開されるので、`jsr`・`rts` のコストはかからない。
- **1.1 での仕様**：[8.5節](#s8-5)

<a id="qa-h4"></a>
#### H-4. 使っていないモジュールの init について、警告と抑制の方法がほしい

- **質問**：`import` したが使っていないモジュールの `init` も実行される。警告を出したり、明示的に抑制したりする方法がほしい。
- **当時の書き方**：`init` だけが目的の読み込みは `import hw.via for init;` と書く案だった。
- **回答**：使っていないモジュールの読み込みに警告を出し、`init` があれば起動時に実行されることも示します。`init` だけが目的なら、それを明示する書き方で警告を止めます。一方、`init` を実行させない方法は用意しません。モジュールの関数は `init` が済んでいることを前提に書かれているからです。
- **結論**：使っていない読み込みには警告。`init` だけが目的なら明示して抑制する。`init` を止める方法はない。
- **1.1 での仕様**：[8.5節](#s8-5)。文法の統一で、明示の書き方は Rust と同じ `use hw::via as _;` になった。

<a id="qa-sec-i"></a>
### I. 最適化

<a id="qa-i1"></a>
#### I-1. 比較の「コード量」はアセンブリのソースの量か

- **回答**：いいえ。アセンブルした後の機械語のバイト数で、メモリに読み込まれる大きさです（`lda M_WAIT,x` は `BD 9F 05` の 3 バイト）。6502 の命令は 1〜3 バイトなので、命令の数とは比例しません。変数をゼロページに置くと、3 バイトの命令の多くが 2 バイトになります。
- **結論**：コードの大きさは機械語のバイト数で比べる。
- **1.1 での仕様**：[19.1節](#s19-1)。測定は『サンプルと効果測定 1.1』。

<a id="qa-i2"></a>
#### I-2. 関数のインライン化を明示する仕組みはあるか

- **当時の前提**：展開を許す指定（当時の `inline`）だけがあった。
- **回答**：比較の結果、めったに通らない枝で呼ばれる関数（meteor の `respawn`）を展開すると、ループが大きくなってページ境界をまたぎ、かえって遅くなることがわかりました。そこで「展開しない」指定と、「めったに呼ばれない」ことを示す指定を加えました。
- **結論**：`#[inline]`、`#[inline(always)]`、`#[inline(never)]`、`#[cold]` の 4 つ。
- **1.1 での仕様**：[7.7節](#s7-7)

<a id="qa-i3"></a>
#### I-3. -O は大きさ優先を既定にしてよいのでは

- **質問**：大きさ優先の最適化が、大きさと速さの両方に最も効くのだから、それを既定にしてよいのでは。
- **当時の前提**：最適化オプションは「なし」「`-O`（速さと大きさの釣り合い）」「`-O speed`（速さ優先）」の案で、大きさ優先は別のオプション（`-O size`）として試していた。
- **回答**：そのとおりです。meteor の比較では、大きさ優先の版が `-O` より 10 % 小さく、速さも最も速い版とほぼ同じでした。6502 では命令を小さくすることがそのまま速さにつながるためです。あわせて、ポインタの引数を A・X で渡すことを標準の規則にしました。文字列の表、文字列の後ろの共有、データの圧縮はプログラマが行うものとし、中間コードによる圧縮は将来の拡張としました。
- **結論**：大きさ優先を標準の最適化にする。
- **1.1 での仕様**：[19.3節](#s19-3)、[21章](#s21)。段階の名前は [I-4](#qa-i4) で決めた。

<a id="qa-i4"></a>
#### I-4. 最適化の段階の名前と既定

- **質問**：最適化は `-O0`、`-O1`（初期の仕様）、`-O2`（今回の仕様）、`-Os`（速度優先）とし、既定は `-O2` にしてほしい。
- **回答**：そのように決めました。既定が `-O2` になったので、ゼロページへの自動の配置は何も指定しなければ行われることになり、[C-1](#qa-c1) の「既定は明示だけ」から変わりました。配置を完全に予測したい場合は `-O0` を使います。なお、GCC などでは `-Os` は大きさ優先の意味なので、ax65 では速さ優先であることを仕様書に明記しました。
- **結論**：`-O0`／`-O1`／`-O2`（既定）／`-Os` の 4 段階。
- **1.1 での仕様**：[19.1節](#s19-1)、[17.5節](#s17-5)

<a id="qa-sec-k"></a>
### K. 文法

<a id="qa-k1"></a>
#### K-1. 宣言の語順

- **質問**：（文法の清書）`u8 x`（C 風）と `x: u8`（名前の後ろに型）のどちらにするか。
- **回答**：`shared`、`ptr<u8>`、`char@screen` のように型の前後に修飾が付くことが多いので、名前が先のほうが読みやすく、配列の長さも型にまとまります。また、`eid e;` のような C 風の書き方は、`eid` が型か変数かを知っていないと解析できず、コンパイラが複雑になります。
- **結論**：名前の後ろに型を書く。当時は `var x: u8` とし、その後の Rust 寄せで `let x: u8`・`static mut X: u8` になり（[K-13](#qa-k13)）、最後に `mut` を廃止して `let x: u8`・`static X: u8` になった（[K-15](#qa-k15)、[K-16](#qa-k16)）。
- **1.1 での仕様**：[4.3節](#s4-3)、[4.4節](#s4-4)

<a id="qa-k2"></a>
#### K-2. 16進の 0xFF も許すか

- **質問**：16進は `$FF` だが、`0xFF` の形も許容できるか。
- **回答**：文法上の問題はありません。ただ同じプログラムで混ざると読みにくいので、整形ツールで統一できるようにし、コンパイラの出力は 6502 の慣習の `$` で表示します。2 進は、6502 の伝統の `%1010` が余りの演算子と紛れるので `0b` にしました。
- **結論**：`$FF` と `0xFF` の両方を許す。2 進は `0b`。
- **1.1 での仕様**：[2.5節](#s2-5)、[17.2節](#s17-2)（`fmt { hex = ...; }`）

<a id="qa-k3"></a>
#### K-3. 文法を Rust に近づけると、構文解析は重くなるか

- **質問**：Rust に近くと言ったが、`::` などで構文解析が重くなるなら、今までと同じでもかまわない。
- **回答**：重くなりません。`::` はむしろ、モジュールと変数を記号だけで区別できるので解析を楽にします。Rust の解析が難しい点は 2 つで、`<` の意味の区別（AX65 にはジェネリクスがなく、型は `:` や `->` の後ろにしか現れない）と、`if` の条件の中の構造体の値（Rust と同じく禁止する）です。どちらも起きません。
- **結論**：Rust に近い文法でも、1〜2 文字先を見るだけで解析できる。
- **1.1 での仕様**：[1.4節](#s1-4)、[6.2節](#s6-2)

<a id="qa-k4"></a>
#### K-4. 配列の従来の書き方も使いたい

- **質問**：配列は従来の書き方（`enemy[5]`）も使いたい。
- **結論**：`[T; N]` と `T[N]` の両方を許し、同じ型とする。2 次元は `u8[4][256]` のほうが読みやすい。整形ツールで一方にそろえられる。
- **1.1 での仕様**：[3.8節](#s3-8)、[17.2節](#s17-2)（`fmt { array = ...; }`）

<a id="qa-k5"></a>
#### K-5. 構造体の名前が大文字なのはなぜか

- **回答**：Rust の名前の慣習に合わせたためです。型は `CamelCase`、変数と関数は `snake_case` なので、`let enemy: Enemy` のように同じ単語を使っても見分けられます。`static` の名前を大文字で書くのも Rust の慣習です。AX65 ではグローバル変数をよく使うので、慣習は警告だけにし、プロジェクトファイルで止められるようにしました。
- **結論**：名前の慣習は Rust と同じ。守らない場合は警告。
- **1.1 での仕様**：[2.3節](#s2-3)

<a id="qa-k6"></a>
#### K-6. pure を const fn に変えると、前の方針と矛盾しないか

- **質問**：Rust に合わせて `pure fn` を `const fn` にすると、ひとつ前の方針と矛盾しないか。
- **当時の前提**：その直前に「`const` は値の宣言だけに使い、コンパイル時に実行されるものは `comptime` にそろえる」と決めていた。私が Rust に合わせて `const fn` を提案した。
- **回答**：ご指摘のとおり矛盾します（私の提案の誤り）。`const fn` は値ではなく関数に `const` を使い、かつ実行時にも呼べるので `comptime` でもありません。
- **結論**：`pure fn` のまま残す。
- **1.1 での仕様**：その後、`const` の意味を定め直して `const fn` に変えた（[K-17](#qa-k17)、[7.2節](#s7-2)）。

<a id="qa-k7"></a>
#### K-7. 独自の概念の名前は、命名の規則として一貫しているか

- **質問**：独自の概念も、命名の規則として合っているか確認してほしい。
- **当時の書き方**：範囲型 `type eid = 0..15;`（`..` が終わりを含む）、`eid.check(n)`、`shared<irq>`、`io in`、`import ... for init`、`#[allow(W0301)]` などだった。
- **回答**：見直して、次の点を直しました。範囲型の `..` が for の範囲（終わりを含まない）と食い違っていたので、どこでも `..` は含まない、`..=` は含むに統一した。`type` が新しい型と別名の両方に使われていたので、新しい範囲型は `range`、別名は `type` に分けた。型に付いた関数は `Eid::check(n)` のように `::` で呼ぶ。割り込みの種類の指定を Rust の `pub(crate)` と同じ形の `shared(irq)`、`io(in)` にそろえた。`init` だけの読み込みを Rust の `use x as _;` にした。警告の抑制は名前で書く。組み込みの型は小文字、ライブラリの型は大文字で始める。
- **結論**：上の点を直した。
- **1.1 での仕様**：[3.4節](#s3-4)、[10.4節](#s10-4)、[11.1節](#s11-1)、[8.5節](#s8-5)、[18.2節](#s18-2)

<a id="qa-k8"></a>
#### K-8. BCD のリテラル

- **質問**：（サンプルで見つかった点）`SCORE += 1;` の `1` を BCD の $01 として扱うか。
- **回答**：BCD の型のところに書いた 10進のリテラルは、10進の値として BCD に変換するのが自然です。16進のリテラルは、`$25` が「25」なのか「37」なのかが紛らわしいのでエラーにします。
- **結論**：10進のリテラルだけを BCD に変換する。16進と範囲外のリテラルはエラー。
- **1.1 での仕様**：[5.5節](#s5-5)、[2.5節](#s2-5)

#### K-9. 配列や構造体の初期値の書き方

- **質問**：（古い版の指摘）グローバル変数に初期値が必須なのに、配列や構造体の初期値の書き方がない。サンプルでは仮に `zero` と書いた。
- **回答**：配列の並び・繰り返し・構造体の値の書き方に加えて、どの型にも使える `zero` を提案しましたが、「Rust と揃えたい」とのご判断で、特別な値は入れず、Rust と同じ書き方（構造体更新構文 `..BASE` を含む）にしました。
- **結論**：配列と構造体の値は Rust と同じ書き方。`zero` は入れない。
- **1.1 での仕様**：[4.5節](#s4-5)

<a id="qa-k10"></a>
#### K-10. for の範囲の終わりに変数を書けるか

- **質問**：（古い版の指摘）`for i in 0..n` が許されるかが書かれていない。
- **結論**：書ける。ループ変数の型は両端の型と同じ。u8 なら上限が型から 256 回と決まるので、割り込み処理の中でも使える。範囲型のまま一部を回すときは `Eid::range(a, b)`。

#### K-11. ページ単位の配列のアドレス

- **結論**：配列全体の先頭（＝最初のページの先頭）。`&BUF[k]` は k 番目のページの先頭。型はどちらも `ptr<u8>`。

#### K-13. 文法の統一

- **質問**：文法は基本的に Rust 寄りで統一し、全体を見直してほしい。
- **当時の前提**：仕様書のコード例は、検討の途中で使った仮の書き方（C 風の宣言、`u8?`、`import`、`interrupt(irq) fn` など）のままで、サンプルの `meteor.ax65` だけが Rust に寄せた書き方で書かれていた。

<a id="qa-k14"></a>
#### K-14. static mut は何を表しているか。なぜ let ではないのか

- **質問**：`static mut` とは何を表しているか。なぜ `let` に入っていないのか。
- **当時の前提**：グローバル変数は `static mut`、書き換えないグローバルは `static`、ローカル変数は `let`／`let mut` と書いていた（Rust と同じ）。
- **回答**：`static mut` は、プログラムが動いている間ずっと存在し、専用の固定アドレスを持ち、書き換えられる変数です。`let` と分けているのは、AX65 では両者のメモリの扱いが違うからです。`let` の変数は、同時に動かない関数同士で同じ番地を使い回すので（[4.8節](#s4-8)）、関数を抜けると別の関数に上書きされます。`static` は専用の番地を持ち、値はプログラムの終わりまで残り、どの関数からも使え、起動時に毎回初期化されます。この区別は Rust の真似ではなく、AX65 のメモリ配置に由来するので、残す意味があります。
- **結論**：`static` と `let` の区別は残す（`mut` の扱いは [K-15](#qa-k15)、[K-16](#qa-k16)）。
- **1.1 での仕様**：[4.3節](#s4-3)、[4.4節](#s4-4)

<a id="qa-k15"></a>
#### K-15. let mut と let を区別する意味はあるか

- **質問**：このシステムで `let mut` と `let` を区別する意味はあるか。コンパイル時に再代入を検査し、抑制する仕様になっていたか。Rust の考え方を借りているが、意味のない仕様ならやめてほしい。
- **当時の前提**：再代入の検査はあった。`mut` のない変数・引数への代入はエラー、書き換えていない `let mut` は警告（`unused_mut`）だった。
- **回答**：効果は小さいと判断しました。コンパイラはプログラム全体を解析するので、`mut` がなくても、どの変数が書き換えられるかは自分でわかり、生成されるコードは変わりません。また、AX65 が保証の中心にしている、スタック、添字の範囲、割り込みとの競合のどれにも関わりません。残る効果は、うっかり書き換えた誤りの検出と、意図の表示だけです。Rust では借用（参照の共有）の安全性と `mut` が結び付いているので本質的な意味がありますが、AX65 には借用がないので、その理由は持ち込めません。関数の引数の `mut` も同じです。
- **結論**：`let mut` と引数の `mut` を廃止する（ご判断による）。ローカル変数と引数は常に書き換えられる。`mut` は予約語とし、書くとエラーにする。警告 `unused_mut` もなくなった。
- **1.1 での仕様**：[4.4節](#s4-4)、[7.1節](#s7-1)、[2.4節](#s2-4)

<a id="qa-k16"></a>
#### K-16. const と、書き換えない static の重なり

- **質問**：（K-14・K-15 の検討の中で見つかった点）書き換えない `static` と `const` は、何が違うのか。
- **当時の前提**：`const` は「アドレスを持たない」、書き換えない `static` は「アドレスを持つ」と書いていた。ところが `print(TITLE)` は `str` の定数をポインタで渡すので、実際には `const` の文字列にもアドレスが要り、仕様が食い違っていた。
- **回答**：AX65 では、読み取り専用のデータは `const` も `static` も ROM（またはプログラム本体）に置かれるので、2 つを分ける意味がほとんどありません。そこで、読み取り専用のものはすべて `const` にし、配列・文字列・構造体の `const` はアドレスを持つことにしました。書き換えない `static` は廃止したので、`static mut` の `mut` は何の情報も持たなくなり、これも省きました。
- **結論**：読み取り専用は `const`（数値は埋め込み、配列・文字列・構造体はアドレスを持つ）。`static` は書き換えられるグローバル変数だけで、`mut` は書かない。
- **1.1 での仕様**：[4.2節](#s4-2)、[4.3節](#s4-3)

<a id="qa-k17"></a>
#### K-17. pure fn より const fn の方がわかりやすいのでは

- **質問**：K-6 の経緯があるが、`pure fn` より `const fn` の方がわかりやすくないか。矛盾がなければその方針でもよい。
- **当時の前提**：「`const` は値の宣言だけに使い、コンパイル時にだけ行うものは `comptime` にそろえる」という規則で、状態を書き換えない関数は `pure fn` と書いていた（[K-6](#qa-k6)）。
- **回答**：K-6 の矛盾は、「`const` は値の宣言だけ」という規則から生じたものです。`const` の意味を「コンパイル時に値が決まる・コンパイル時に計算できる」と定め直すと、`const X: T = …`（コンパイル時に値が決まる）と `const fn`（コンパイル時に計算できる。実行時にも呼べる）は同じ意味で一貫します。Rust の `const` と `const fn` の関係と同じです。`comptime` は「コンパイル時だけ」を表すので、`comptime fn`・`comptime if` との区別も保たれます。見直しの中では、条件（`static`・`shared`・I/O に触れない）を満たすかどうかはコンパイラが判断できるので、印を付けずに推論する案も出ました。推論にすると、関数の中身を少し変えただけで、それを使う定数の計算が離れた場所でエラーになります。呼ぶ側から見える印として、`const fn` を明示する形を選びました（ご判断による）。
- **結論**：`pure fn` を `const fn` にする。`const` は「コンパイル時に値が決まる・計算できる」、`comptime` は「コンパイル時だけ」を表す。
- **1.1 での仕様**：[7.2節](#s7-2)、[13.2節](#s13-2)、[2.4節](#s2-4)

<a id="qa-sec-l"></a>
### L. 仕様の補足


<a id="qa-l1"></a>
#### L-1. I/O 変数に RMW 命令を使わないのはなぜか

- **回答**：`inc`・`asl`・`tsb` などの読み・変更・書き込み命令は、1 命令に見えても内部でアクセスが 2 回以上起きます（NMOS は書き込みが 2 回、65C02 は読み込みが 2 回）。読むだけで状態が変わるレジスタが 2 回読まれたり、出力のピンに一瞬古い値が出たりするので、標準では `lda` と `sta` だけを使います。2 回アクセスしても問題のないレジスタだけ、`io(rmw)` で許可します。
- **1.1 での仕様**：[11.2節](#s11-2)

<a id="qa-l2"></a>
#### L-2. 割り込み処理とメインの両方から呼ばれる関数を禁止するのはなぜか

- **回答**：ローカル変数は固定アドレスに置かれるので、メインがその関数を実行している途中で割り込み処理が同じ関数を呼ぶと、ローカル変数が上書きされます。再帰を禁止しているのと同じ理由です。
- **1.1 での仕様**：[10.2節](#s10-2)、[4.8節](#s4-8)。1.0 では、メイン・IRQ 処理・NMI 処理の 3 つの文脈のうち、1 つからだけ呼べる規則にした（[M-3](#qa-m3)）。

<a id="qa-l3"></a>
#### L-3. インラインアセンブリで言語の名前を {名前} と書くのはなぜか

- **回答**：アセンブリのラベルや、16進の数値（`$FF`）と、言語の変数の名前を確実に区別するためです。
- **1.1 での仕様**：[14.2節](#s14-2)

<a id="qa-l4"></a>
#### L-4. 自己書き換えでオペコードを書き換えられないのはなぜか

- **回答**：オペランドだけなら、命令の種類が変わらないので、コンパイラはサイクル数とスタックの使用量の解析を続けられます。オペコードを書き換えると、その解析ができなくなります。
- **1.1 での仕様**：[14.5節](#s14-5)

<a id="qa-l5"></a>
#### L-5. -Os で共通部分のくくり出しを行わないのはなぜか

- **回答**：くくり出した部分は `jsr` と `rts` で呼ぶことになり、1 回あたり 12 サイクルかかります。大きさは減りますが速さは落ちるので、速さ優先の `-Os` では行いません。
- **1.1 での仕様**：[19.4節](#s19-4)

<a id="qa-l6"></a>
#### L-6. 末尾呼び出しの置き換えなどを、最適化の段階にかかわらず行うのはなぜか

- **回答**：末尾呼び出しの `jmp` への置き換え、読み捨ての I/O の `bit`、初期値 0 の `stz` は、どれもコードが大きくならず、配置や命令の予測しやすさも損なわないためです。`-O0` でも行います。
- **1.1 での仕様**：[19.5節](#s19-5)

<a id="qa-l7"></a>
#### L-7. 使っていない bool や Option の値を警告にするのはなぜか

- **回答**：`checked_add` の結果や、`poll()` の結果のように、確かめるべき値を捨ててしまう誤りを見つけるためです。
- **1.1 での仕様**：[6.1節](#s6-1)、[18.2節](#s18-2)

<a id="qa-l8"></a>
#### L-8. サイクル数のブロックとインラインアセンブリで使う変数を、ゼロページの自動の配置から外すのはなぜか

- **回答**：ゼロページに移すと、その変数を使う命令の長さとサイクル数が変わります（絶対アドレスの 3 バイト・4 サイクルが、2 バイト・3 サイクルになる）。最適化の段階によって、サイクル数の保証やアセンブリの命令の長さが変わらないようにするためです。
- **1.1 での仕様**：[4.7節](#s4-7)。1.0 では `max_cycles()` の中で使う変数も対象外にした（[M-7](#qa-m7)）。

<a id="qa-sec-m"></a>
### M. 1.0 の見直し

<a id="qa-m1"></a>
#### M-1. 1.2 節の安全の保証に、書かれていない例外があるのでは

- **質問**：1.2 節は「スタックがあふれず、範囲外のアクセスをせず、データ競合を起こさない」と保証しているが、ポインタの指す先は検査しない（3.10 節）、`const` をポインタで書き換えられる（4.2 節）など、保証の外にあるものが各節に散らばっているのでは。
- **回答**：そのとおりです。保証の外にあるのは、ポインタの指す先の読み書き、`unchecked()`、`extern fn`、`unsafe asm`、`smc` の 5 つで、どれもプログラマが正しさに責任を持つ部分です。これを 1.2 節に一覧で示し、すべてをレポートの unsafe の項目に出すことにしました。`const` を指すポインタを通した書き込みは、プログラム全体の解析で見つけられるので、例外にせずエラーにしました。
- **結論**：保証の対象外を 5 つに限って明示し、レポートに一覧で出す。`const` を指すポインタを通した書き込みはエラー。
- **1.1 での仕様**：[1.2節](#s1-2)、[4.2節](#s4-2)、[18.4節](#s18-4)

<a id="qa-m2"></a>
#### M-2. shared の「1 命令の操作」は CPU によって変わるのでは

- **質問**：10.4 節の「1 命令で済む操作」は、生成する命令で決まるので、CPU や最適化によって変わるのでは。NMI の規則も、表と本文で違うことが書かれている。
- **回答**：「1 命令の操作」を、生成する命令ではなくソースの形で定めました。1 バイトの型の読み込み、右辺に自分を含まない書き込み、`+= 1`・`-= 1` の 3 つです。どれも 6502 のどの品種でも 1 命令で書けるので、コンパイラはこれらを必ず 1 命令にします。NMI の規則は「1 バイトの型に限る、書き込む側の指定が必須、NMI 処理の中ではどの操作も使える、それ以外の側では 1 命令の操作だけ」の 1 つにまとめました。NMI は `atomic` でも止められないので、NMI 以外の側では、書き込む側が 1 つの場合の例外も使いません。あわせて、`shared` の読み書きは省略しないことを明記しました（[M-9](#qa-m9)）。
- **結論**：1 命令の操作はソースの形で決める。NMI の規則を 1 つにまとめる。
- **1.1 での仕様**：[10.4節](#s10-4)

<a id="qa-m3"></a>
#### M-3. IRQ 処理と NMI 処理の両方から呼ばれる関数は安全か

- **質問**：10.2 節は、割り込み処理とメインの両方から呼ばれる関数を禁止しているが、IRQ 処理と NMI 処理の両方から呼ばれる関数については書かれていない。
- **回答**：NMI は IRQ 処理の途中でも入るので、IRQ 処理と NMI 処理の両方から呼ばれる関数も、メインと IRQ 処理の場合と同じくローカル変数を壊します（[L-2](#qa-l2)）。そこで、メイン、IRQ 処理（`brk` を含む）、NMI 処理を 3 つの文脈とし、1 つの関数は 1 つの文脈からだけ呼べる規則にしました。IRQ と BRK は同じベクタを使い、互いに割り込まないので、同じ文脈です。
- **結論**：関数を呼べるのは 1 つの文脈からだけ。ローカル変数は文脈ごとに別の領域に置く。
- **1.1 での仕様**：[10.2節](#s10-2)、[4.8節](#s4-8)

<a id="qa-m4"></a>
#### M-4. ローカル変数のアドレスは、呼び出し先を通して持ち出せるのでは

- **質問**：4.9 節は、ローカル変数のアドレスを呼び出し先に渡すことを許しているが、呼び出し先がそれを `static` に保存すれば、関数の外に持ち出せてしまうのでは。
- **回答**：そのとおりです。プログラム全体を解析するので、ポインタがどこに保存され、どこから返されるかは追跡できます。呼び出し先（さらに先の関数を含む）が、受け取ったポインタを `static`・`shared` に保存したり返したりする場合をエラーにしました。
- **結論**：呼び出し先を通した持ち出しもエラー。
- **1.1 での仕様**：[4.9節](#s4-9)

<a id="qa-m5"></a>
#### M-5. 割り算の結果を Option にするのは重いのでは

- **質問**：`divmod8` の結果が `Option` なので、`divmod8(x, 10)` のように 0 でないことが明らかな場合も、毎回 `if let` が要る。
- **回答**：0 で割らないことを、結果ではなく引数の型で保証する形にしました。割る数の型を 0 でない値の範囲型 `Nz8`（`1..256`）にすれば、定数はコンパイル時に確かめられ、変数は `Nz8::check(n)` で 1 回だけ確かめればよくなります。範囲型の考え方（[E-2](#qa-e2)）と同じで、確かめる場所をプログラマが選べます。
- **結論**：割る数は `Nz8`・`Nz16`。結果は `Option` ではなく商と余りの構造体。
- **1.1 での仕様**：[5.6節](#s5-6)、[20.2節](#s20-2)

<a id="qa-m6"></a>
#### M-6. BCD と整数の変換を as で書くと、コストが見えないのでは

- **質問**：`SCORE as u16` は割り算に近いコストがかかるのに、他の `as`（コストがないか数命令）と同じ書き方になっている。
- **回答**：1.2 節の方針 1（高くつく操作は、高くつくことが見える形でしか書けない）に合わせ、`as` はコストがないか数命令の変換だけにしました。BCD と整数の変換は `bcd::to_u16(x)` などの関数で書きます。同じ考え方で、定数の掛け算の展開、結果領域の自動コピー、`digits()` の結果領域はレポートに出します。
- **結論**：BCD と整数の間の `as` はエラー。変換は `bcd` の関数で行う。
- **1.1 での仕様**：[3.14節](#s3-14)、[5.5節](#s5-5)、[20.3節](#s20-3)、[18.4節](#s18-4)

<a id="qa-m7"></a>
#### M-7. 最適化の段階によって、検査の結果が変わるのでは

- **質問**：1.2 節は「最適化は意味を変えない」としているが、スタックの使用量やサイクル数は生成したコードで決まるので、`-O0` では通るが `-Os` ではスタックの予算を超える、ということが起こりうるのでは。
- **回答**：起こりえます。資源とタイミングの検査（スタックの予算、RAM・ゼロページの容量、`max_cycles()`、`irq_interval`、`#[reg]`）は、選んだ段階で生成したコードに対して行うものと定めました。プログラムの意味は変わりませんが、検査が通るかどうかは段階によって変わります。すべての段階で確かめるために `ax65 check --all-levels` を加えました。また、`max_cycles()` の中で使う変数も、`cycles()`・`io_span()` と同じく、ゼロページへの自動の配置から外しました。
- **結論**：資源とタイミングの検査は段階ごと。`--all-levels` で全段階を検査できる。
- **1.1 での仕様**：[19.1節](#s19-1)、[1.2節](#s1-2)、[4.7節](#s4-7)、[17.5節](#s17-5)

<a id="qa-m8"></a>
#### M-8. 自動の逆順化の条件が足りないのでは

- **質問**：6.4 節の自動の逆順化の条件では、`break` で途中から抜けるループや、ループの外の変数に最後の値を代入するループも逆順にされ、結果が変わってしまう。
- **回答**：そのとおりです。順番に依存しないことを保証するため、`break`・`return`・`?` を含まないこと、ループの外の変数への書き込みは `+=`・`-=`・`|=`・`&=`・`^=` の積み重ね（順番を入れ替えても結果が同じ）だけであること、を条件に加えました。
- **結論**：条件を 2 つ加える。
- **1.1 での仕様**：[6.4節](#s6-4)

<a id="qa-m9"></a>
#### M-9. 不要な書き込みの削除で、shared への書き込みが消えるのでは

- **質問**：19.3 節の不要な書き込みの削除は、割り込み処理が読む `shared` 変数への書き込みも消してしまうのでは。
- **回答**：`shared` 変数、`io` 変数、アドレスを取った変数（ポインタを通して読まれる）、アセンブリから参照される変数は、コンパイラが追っている読み込みの外で読まれることがあります。これらへの書き込みを削除の対象から外し、`shared` の読み書きは回数と順序をソースどおりにすると定めました（I/O は [11.2節](#s11-2) で同じ規則）。
- **結論**：削除の対象外を明示する。`shared` の読み書きは省略しない。
- **1.1 での仕様**：[19.3節](#s19-3)、[10.4節](#s10-4)

<a id="qa-m10"></a>
#### M-10. 予約語と bits() の整理

- **質問**：Rust から借りて、AX65 では意味の薄いものがまだ残っていないか。
- **回答**：予約語の `async`・`await`・`dyn`・`trait`・`where`・`yield` は、AX65 に対応する機能を入れる予定がないので外し、`mut` だけを残しました（[K-15](#qa-k15)）。ビットフラグの `bits()`・`from_bits()` は `as` と同じ働きの別の書き方なので廃止し、整数との変換は両方向とも `as` にしました。ビットフラグの値はどのビットの組み合わせも有効なので、`as` で作っても問題ありません。
- **結論**：予約語は `mut` だけ。ビットフラグと整数の変換は `as`。
- **1.1 での仕様**：[2.4節](#s2-4)、[3.6節](#s3-6)、[3.14節](#s3-14)

<a id="qa-m11"></a>
#### M-11. impl の中の pub に意味はあるか

- **質問**：インターフェースの実装の関数に `pub` を書いているが、インターフェースの関数は必ず公開されるのだから、`pub` は情報を持たないのでは。
- **回答**：そのとおりです。インターフェースの関数と定数は自動で公開することにし、`pub` を書くとエラーにしました。`impl` の中で、インターフェースにない関数は、そのモジュールの中だけの補助の関数になります。
- **結論**：`impl` の中のインターフェースの関数と定数は自動で公開。`pub` は書かない。
- **1.1 での仕様**：[8.4節](#s8-4)、[8.3節](#s8-3)

<a id="qa-m12"></a>
#### M-12. 標準ライブラリの std:: と、掛け算の実装の切り替え

- **質問**：17.3 節では標準ライブラリを `std::ps2_keyboard` と書いているが、`use console;` は何も付けずに標準ライブラリを使っている。20.2 節の `bind core_mul = std::mul_table;` も、bind するインターフェースがない。
- **回答**：どのモジュールを使うかは探す順（プロジェクトの `paths`、次に標準ライブラリ）だけで決まるので、`std::` は付けないことにしました。掛け算の切り替えは、標準のインターフェース `mul` と、2 つの実装 `mul_shift`・`mul_table` で表します。どのターゲットでも掛け算は使えるべきなので、bind しなければ `mul_shift` を使います。
- **結論**：標準ライブラリは名前だけで書く。掛け算は `mul` インターフェースで切り替える。
- **1.1 での仕様**：[17.3節](#s17-3)、[20.2節](#s20-2)、[20.4節](#s20-4)

<a id="qa-m13"></a>
#### M-13. 型を書かない let の整数リテラルの型

- **質問**：`let a = 255;` の型は「使われた場所の型で決まる」とあるが、`let` の右辺だけでは決まらないのでは。
- **回答**：型を書かない `let` の初期値が整数リテラルだけの場合は `u8` と決めました。6502 で最も安い型で、ほとんどの変数に足ります。`u8` に収まらない値は、黙って広い型にせず、エラーにして型を書かせます（暗黙の変換をしない [3.1節](#s3-1) と同じ考え方）。
- **結論**：`u8`。収まらなければエラー。
- **1.1 での仕様**：[2.5節](#s2-5)、[4.4節](#s4-4)

<a id="qa-m14"></a>
#### M-14. as の範囲の検査

- **質問**：`comptime fn` の結果の変換は範囲外ならエラーだが、`const fn` をコンパイル時に計算したときの `as` はどうなるのか。
- **回答**：コンパイル時と実行時で結果が一致するよう、実行時の整数型同士の `as` は、どちらで計算しても下位のバイトを取ります。範囲を検査するのは、コンパイル時だけの型 `int`・`real` から実行時の型への変換だけです。
- **結論**：`int`・`real` からは範囲を検査する。実行時の型同士は下位のバイトを取る。
- **1.1 での仕様**：[3.14節](#s3-14)、[13.2節](#s13-2)

<a id="qa-m15"></a>
#### M-15. 戻り値の返し方の表に、ない型があるのでは

- **質問**：15.3 節の表に、`u24`・`u32`・BCD・`str`・16 ビットのビットフラグ・`strbuf` がない。20.3 節は `strbuf` を返している。
- **回答**：[D-7](#qa-d7) の「大きさで決める」方針に従って、3 バイト（A・X・Y）と 4 バイト以上（結果領域）を加え、表にすべての型を並べました。`strbuf` は結果領域で返します。`Option<bool>` は有無にキャリーを使うので、値は A に 0 か 1 で返します。
- **結論**：大きさごとの表にする。
- **1.1 での仕様**：[15.3節](#s15-3)

#### M-16. 警告をすべてエラーにする -W error は、警告ごとの -W と紛らわしい

#### M-20. 表の生成の添字の型

- **質問**：`[for i in 0..256 => sine_at(i)]` の `i` は、`comptime fn sine_at(i: int)` に渡しているので `int` のはずだが、型が決まっていない。

### N. 1.1：実機への対応

<a id="qa-n1"></a>
#### N-1. rts でモニタへ戻る終わり方

- **質問**：実機の HEXMON は、JMP キーで $0200 からプログラムを実行し、プログラムが `rts` を実行するとモニタに戻る。`exit = monitor(番地)` で書けるか。
- **当時の前提**：1.0 の `exit` は `monitor(番地)`、`halt`、`never` の 3 つで、起動処理は必ずスタックポインタを設定していた。
- **回答**：`monitor(番地)` は、起動処理がスタックポインタを設定し直したうえでモニタの入口へ `jmp` するので、モニタが積んだ戻り番地が失われます。`exit = rts` を加え、このときは起動処理がスタックポインタを設定しないことにしました。`main` の呼び出しは末尾呼び出しになるので `jmp` で済み、`main` の `rts` がそのままモニタへ戻ります。モニタとスタックを共用するので、`stack` にはプログラムが使える量を書きます。
- **結論**：`exit = rts` を追加。スタックポインタは設定しない。
- **1.1 での仕様**：[16.4節](#s16-4)、[15.1節](#s15-1)

<a id="qa-n2"></a>
#### N-2. 割り込みのないターゲット

- **質問**：HEXMON は IRQ ベクタを設定していないので、`cli` を実行すると暴走する。言語でこれを防げるか。
- **当時の前提**：1.0 では `irq`・`nmi` を省略した場合の扱いが決まっておらず、`irq_enable()` は割り込み処理がないときに警告を出すだけだった。
- **回答**：`irq`・`nmi` に `none` を加え、省略したときの値にしました。`irq = none` のターゲットでは、割り込み処理の宣言、`irq_enable()`、`wait_interrupt()`、`shared(irq)`、`irq_interval` をエラーにします。割り込みがなければ排他制御は要らないので、`irq` と `nmi` がどちらも `none` なら `atomic` は命令を生成しません。割り込みのあるターゲットとないターゲットの両方で使うプログラムは、`target.has_irq` で書き分けます。
- **結論**：`none` を追加し、省略時の値にする。割り込みの機能はエラー。
- **1.1 での仕様**：[16.4節](#s16-4)、[10.1節](#s10-1)、[10.3節](#s10-3)、[10.4節](#s10-4)、[10.5節](#s10-5)、[12.3節](#s12-3)、[13.5節](#s13-5)

<a id="qa-n3"></a>
#### N-3. モニタが使う I/O レジスタ

- **質問**：HEXMON の時間待ちは 6522 のタイマー T1 と ACR を使っていて、プログラムが変えると時間待ちが狂う。触らないようにできるか。
- **当時の前提**：1.0 の `reserve` はメモリの使用禁止の範囲で、I/O の区画の中に書けるかは決まっていなかった。継承したときの `reserve` の扱いも決まっていなかった。
- **回答**：`reserve` をどの区画の中にも書けるようにし、`io` の区画の中の `reserve` には I/O 変数を宣言できないことにしました。宣言の時点でエラーになるので、間違って書き込む命令は作られません。継承では、子が親の予約を外せないように、`reserve` だけは親の範囲に足すことにしました。
- **結論**：`reserve` は I/O にも使える。継承では足される。
- **1.1 での仕様**：[16.3節](#s16-3)、[16.1節](#s16-1)

<a id="qa-n4"></a>
#### N-4. モニタ API の宣言

- **質問**：HEXMON の POLL_KEY は、キーの有無をキャリーで、キーコードを A で返す。`extern fn` で宣言できるか。また、API を呼ぶ前に `cld` が必要とされている。
- **当時の前提**：1.0 の `extern fn` の戻り値は `-> u8 in A` の形だけが例示され、`clobbers` に書ける名前も決まっていなかった。
- **回答**：`extern fn` の戻り値に、`-> bool in C` と `-> Option<u8> in A`（有無はキャリー）を加えました。どちらも AX65 の関数の戻り値の返し方（[15.3節](#s15-3)）と同じなので、そのまま `if let` や `?` で使えます。`clobbers` には `A`、`X`、`Y`、`flags` を書きます。AX65 は 10進モードを BCD の演算の中だけで使い、`asm` ブロックにも出口で解除することを求めるので、`extern fn` は常に 10進モードを解除した状態で呼ばれます。
- **結論**：上のとおり。
- **1.1 での仕様**：[7.6節](#s7-6)、[14.3節](#s14-3)、[付録A](#appA)

<a id="qa-n7"></a>
#### N-7. サイクル数の埋め方

- **質問**：`cycles()` と `io_span()` は足りない分を `nop` で埋めるが、`nop` は 2 サイクルなので、奇数のサイクルを埋められない。約 1.8425MHz のクロックでは、`us()` で求めたサイクル数が奇数になることが多い。
- **当時の前提**：1.0 では、埋める命令は `nop` だけだった。
- **回答**：奇数の場合は、次の命令への `jmp`（3 サイクル。レジスタもフラグも変えない）を 1 つ使うことにしました。これで 2 サイクル以上なら、どのサイクル数でも埋められます。1 サイクルだけはどの命令でも埋められないので、エラーにします。
- **結論**：`nop` と、奇数のときは `jmp` 1 つ。1 サイクルはエラー。
- **1.1 での仕様**：[12.1節](#s12-1)

<a id="qa-n9"></a>
#### N-9. -O2 での digits() の展開

- **質問**：サンプルの `-O2` の想定出力は、`for d in SCORE.digits()` を結果領域なしで展開し、共通部分をくくり出している。1.0 の仕様では、この展開は `-Os` だけだった。
- **当時の前提**：1.0 では、`for` で直接回す `digits()` の展開は `-Os` の項目だった。
- **回答**：結果領域なしの展開は、結果領域（4 バイト）と、それを回すループの命令がなくなるので、コードも小さくなります。大きさを優先する `-O2` の方針に合うので、`-O2` でも行うことにしました。`-O2` では、展開した 4 桁の同じ形の命令の並びを、共通部分のくくり出しで小さなサブルーチンにまとめます。あわせて、くくり出しの対象外を「何度も回るループの本体に直接ある命令の並び」とはっきりさせました。
- **結論**：`for` で直接回す `digits()` の展開は `-O2` と `-Os` で行う。
- **1.1 での仕様**：[5.5節](#s5-5)、[19.3節](#s19-3)

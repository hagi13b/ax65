## 1. この資料について

- ax65 のコンパイラはまだ存在しません。「コンパイル結果」は、仕様書 1.0 の規則に従って手で生成した**想定出力**です。実際のコンパイラの出力とは、細部が違う可能性があります。
- 測定には、作業用に作った 65C02 のアセンブラとエミュレータを使いました（`tools/`）。サイクル数は W65C02S のデータシートの値で、ページ境界をまたぐ場合の +1、分岐の +1／+2、10進モードの `adc`・`sbc` の +1 を含みます。
- コード例と仕様の参照は、すべて仕様書 1.0 の書き方と章番号です。

## 2. パッケージの構成と再現の手順

```
ax65_meteor_1.0/
├── ax65_meteor_report_1.0.md     この資料
├── ax65_spec_1.0.md              仕様書 1.0（写し）
├── project/                      ax65 のプロジェクト（4章）
│   ├── ax65.proj
│   ├── targets/
│   │   ├── v2.target             シリアル端末の構成（測定に使ったターゲット）
│   │   └── v3.target             画面を追加した構成
│   ├── src/
│   │   └── meteor.ax65           ゲームの本体
│   └── hw/
│       ├── acia_console.ax65     impl console（ACIA）
│       └── v3_screen.ax65        impl screen（v3 だけ）
├── stdlib/                       標準ライブラリのインターフェース（抜粋。本来は <ax65>/std/）
│   ├── console.ax65
│   └── screen.ax65
├── asm/                          コンパイル結果と手書き版（.s が原本。.bin .lst .sym.json は組み立てで作る）
│   ├── meteor_O0.s  meteor_O1.s  meteor_O2.s  meteor_Os.s
│   └── meteor_hand.s
├── tools/
│   ├── asm65.py                  65C02 のアセンブラ（2 パス、リスティングにサイクル数を出す）
│   ├── sim65c02.py               W65C02S のエミュレータ（VIA のタイマー1、ACIA）
│   └── run_bench.py              5 つの版を組み立てて実行し、測定と出力の照合を行う
└── results/
    └── bench_result.json         測定結果
```

再現の手順（Python 3.8 以上。外部のパッケージは使いません）：

```
cd ax65_meteor_1.0
python3 -I tools/run_bench.py
```

`asm/` に `.bin`・`.lst`・`.sym.json` を作り、`results/bench_result.json` に結果を書き、要約を表示します。

ax65 のコンパイラができた後は、次のコマンドで同じものを作る想定です。

```
cd ax65_meteor_1.0/project
ax65 build -t v2 -O0 -o build/O0
ax65 build -t v2 -O1 -o build/O1
ax65 build -t v2            -o build/O2      # 既定（-O2）
ax65 build -t v2 -Os -o build/Os
ax65 check --all-targets                     # v2 と v3 の両方で検査
```

## 5. ソースの解説（使っている仕様）

`src/meteor.ax65` が使っている仕様と、仕様書 1.0 の該当箇所です。

| ソースの箇所 | 使っている仕様 | 仕様書 |
|---|---|---|
| `use console::{putc, poll};`、`use screen;` | モジュールの読み込み。`console`・`screen` は標準ライブラリのインターフェースで、実装はターゲットの bind で決まる。v2 では `screen` が bind されていないが、`use` はできる | [8.2](ax65_spec_1.0.md#s8-2)、[8.4](ax65_spec_1.0.md#s8-4) |
| `const FIELD_W: u8 = 20;` | 定数。使った場所に値が埋め込まれ、メモリを使わない | [4.2](ax65_spec_1.0.md#s4-2) |
| `comptime assert(target.clock / 60 <= 65535, …)` | コンパイル時の検査。`target.clock` はターゲット定義のクロック。v2（1MHz）で 16666、v3（2MHz）で 33333 | [13.5](ax65_spec_1.0.md#s13-5) |
| `const T1_PERIOD: u16 = (target.clock / 60 - 2) as u16;` | コンパイル時の計算（`int` で計算し、`u16` に変換。範囲外ならエラー） | [13.1](ax65_spec_1.0.md#s13-1)、[3.14](ax65_spec_1.0.md#s3-14) |
| `const TITLE: str = p"METEOR DODGE";` | 長さ付きの文字列 | [2.7](ax65_spec_1.0.md#s2-7)、[3.9](ax65_spec_1.0.md#s3-9) |
| `range Mid = 0..8;` | 範囲型（隕石の番号 0〜7）。`METEORS[m]` の範囲の検査が不要になる | [3.4](ax65_spec_1.0.md#s3-4) |
| `enum Key { Left, Right, Quit }` | 列挙型。`match` で網羅性が検査される | [3.5](ax65_spec_1.0.md#s3-5) |
| `flags Ifr { …, T1, Any }` | ビットフラグ型。`IFR.contains(Ifr::T1)` はビット 6 なので `bit` 命令になる | [3.6](ax65_spec_1.0.md#s3-6) |
| `struct Meteor { x: u8, y: u8, wait: u8 }` | 構造体。配列はフィールドごとに並ぶ | [3.7](ax65_spec_1.0.md#s3-7)、[3.8](ax65_spec_1.0.md#s3-8) |
| `comptime fn spawn_x(i: int) -> u8` と `[for i in 0..8 => spawn_x(i)]` | コンパイル時専用の関数と、表の生成。結果は 3, 10, 17, 4, 11, 18, 5, 12 | [7.3](ax65_spec_1.0.md#s7-3)、[13.3](ax65_spec_1.0.md#s13-3) |
| `const SPAWN_X: u8[Mid]`、`static mut METEORS: Meteor[Mid]` | 配列の従来の書き方（`[u8; Mid]` と同じ） | [3.8](ax65_spec_1.0.md#s3-8) |
| `[Meteor { x: 0, y: 0, wait: 0 }; Mid]` | 配列の値（繰り返し）と構造体の値。すべて 0 なので `stz` で初期化される | [4.5](ax65_spec_1.0.md#s4-5)、[4.6](ax65_spec_1.0.md#s4-6) |
| `static mut SCORE: bcd16 = 0;` | BCD の型 | [5.5](ax65_spec_1.0.md#s5-5) |
| `shared(irq) TICKS: u16 = 0;` | 割り込み処理と共有する変数（書き込むのは IRQ だけ） | [10.4](ax65_spec_1.0.md#s10-4) |
| `io(in) IFR: Ifr @ $600D;` など | I/O 変数。読み書きの回数と順序が守られる | [11.1](ax65_spec_1.0.md#s11-1)、[11.2](ax65_spec_1.0.md#s11-2) |
| `init { … }` | 起動時に 1 回だけ実行される。タイマーの下位を先に書く順序はソースどおり | [8.5](ax65_spec_1.0.md#s8-5) |
| `#[interrupt(irq)] fn on_irq()` | 割り込み処理。使うレジスタだけを退避する（この処理は退避なし） | [10.1](ax65_spec_1.0.md#s10-1) |
| `let _ = T1C_L;` | I/O の読み捨て。`bit` 命令で読むので、A を壊さない | [11.3](ax65_spec_1.0.md#s11-3) |
| `TICKS += 1;`（割り込み処理の中） | 割り込み処理の中では `atomic` が不要 | [10.4](ax65_spec_1.0.md#s10-4) |
| `atomic { TICKS }` | 値を返す `atomic`（メインの側で 16 ビットを読む） | [10.5](ax65_spec_1.0.md#s10-5) |
| `comptime if target.cpu == Cpu::W65C02S { wait_interrupt(); }` | 条件コンパイルと割り込み待ち | [13.6](ax65_spec_1.0.md#s13-6)、[12.3](ax65_spec_1.0.md#s12-3) |
| `asm fn rand_step(r: u8) -> u8` | 関数全体のアセンブリ（A で受け取り、A で返す） | [7.4](ax65_spec_1.0.md#s7-4)、[14章](ax65_spec_1.0.md#s14) |
| `SEED` の最後の式 | `return` を省略した戻り値 | [7.1](ax65_spec_1.0.md#s7-1) |
| `fn read_key() -> Option<Key>`、`poll()?` | Option と `?`。戻り値の有無はキャリーで返る | [3.11](ax65_spec_1.0.md#s3-11)、[15.3](ax65_spec_1.0.md#s15-3) |
| `match c { 'A' \| 'a' => …, _ => None }` | `match`。`char` は値が多いので `_` が必須 | [6.6](ax65_spec_1.0.md#s6-6) |
| `PLAYER_X.saturating_sub(1)` | 0 で止まる引き算 | [5.2](ax65_spec_1.0.md#s5-2) |
| `#[reg(x)] for m in Mid` | ループ変数のレジスタの指定 | [6.4](ax65_spec_1.0.md#s6-4) |
| `Mid::wrap(r)` | 下位ビットだけを取って範囲型にする（`and #7`） | [3.4](ax65_spec_1.0.md#s3-4) |
| `continue`、`'game: loop`、`break 'game` | ループの制御とラベル | [6.5](ax65_spec_1.0.md#s6-5) |
| `SCORE += 1;` | BCD の足し算（`sed`・`cld` はコンパイラが入れる。`1` は $01） | [5.5](ax65_spec_1.0.md#s5-5) |
| `for c in s { putc(c); }` | 長さ付きの文字列を回す。`str` の引数はポインタで、A と X で渡る | [3.9](ax65_spec_1.0.md#s3-9)、[15.2](ax65_spec_1.0.md#s15-2) |
| `for d in SCORE.digits()` | BCD の桁の取り出し | [5.5](ax65_spec_1.0.md#s5-5) |
| `('0' as u8 + d) as char` | 型の変換（`u8` ↔ `char`） | [3.14](ax65_spec_1.0.md#s3-14) |
| `comptime if target.has(screen) { … } else { … }` | bind の有無による条件コンパイル。v2 では else 側だけが残る | [13.6](ax65_spec_1.0.md#s13-6)、[16.6](ax65_spec_1.0.md#s16-6) |
| `(0..FIELD_W).rev()` | 逆順のループ | [6.4](ax65_spec_1.0.md#s6-4) |
| `'-'@screen` | 画面の変換表で変換した文字（v3 の `encoding screen`） | [3.3](ax65_spec_1.0.md#s3-3)、[16.5](ax65_spec_1.0.md#s16-5) |
| `irq_enable();` | 割り込みの許可（`main` で明示する） | [10.3](ax65_spec_1.0.md#s10-3) |
| `main` の終わり | ターゲット定義の `exit = monitor($FF1F)` に従ってモニタへ戻る | [15.1](ax65_spec_1.0.md#s15-1)、[16.4](ax65_spec_1.0.md#s16-4) |

コンパイラがこのプログラムについて確かめること：

| 検査 | このプログラムでの内容 |
|---|---|
| 再帰がない | すべての呼び出し関係に輪がない |
| スタックの予算 | 最も深い経路は start → main → update_meteors → respawn → rand → rand_step の 10 バイトに、割り込みの分を足したもの（予算 128 バイト） |
| 範囲外の添字がない | `METEORS` と `SPAWN_X` の添字は、すべて `Mid` 型 |
| 値を入れる前の読み込みがない | すべてのローカル変数は、宣言と同時に値が入っている |
| 割り込みとの共有 | `TICKS` は割り込み処理だけが書き、メインは `atomic` の中で読む |
| I/O の向き | `io(in)` の `IFR` には書かず、`io(out)` のレジスタは読んでいない |
| match の網羅性 | `move_player` の `match` は `Key` のすべての値を書いている |
| Option の確認 | `read_key()`・`poll()` の結果は、`if let` と `?` で確かめてから使っている |
| ターゲットにない機能 | `wait_interrupt()` は `comptime if target.cpu == Cpu::W65C02S` の中だけ |
| bind の確認 | `screen` は `comptime if target.has(screen)` の中だけで使っている |

## 6. コンパイル結果（想定出力）

どの段階にも、段階にかかわらず行う規則（[仕様書 19.5](ax65_spec_1.0.md#s19-5)）が入っています。読み捨ての I/O に `bit`、初期値 0 は `stz`、末尾呼び出しは `jmp`、ポインタの引数は A と X です。

| ファイル | 段階 | 主な最適化 |
|---|---|---|
| `asm/meteor_O0.s` | -O0 | なし。変数は通常の RAM、ゼロページはポインタだけ。関数は展開しない |
| `asm/meteor_O1.s` | -O1 | ゼロページへの自動配置。1 か所からしか呼ばれない関数と、小さな `respawn` を展開。`clear_meteors` のループを逆順にした |
| `asm/meteor_O2.s` | -O2（既定） | ゼロページへの自動配置。展開は 1 か所からしか呼ばれない関数だけ（`respawn` は関数のまま、番号を X で渡す）。`clear_meteors` の不要な書き込みを削除。`print_score` の共通部分をくくり出し |
| `asm/meteor_Os.s` | -Os | -O2 に加えて `respawn` と `digits()` を展開。更新のループがページ境界をまたがないように、サブルーチンを起動処理の前に移した |

段階による違いが最も大きいのは、隕石の更新のループです。

```asm
; -O0：respawn が X と Y を壊すので、隕石の番号 m をメモリ（um_m）に置く
@loop:  ldx um_m                ; m を X に読む（毎回）
        lda M_WAIT,x            ; METEORS[m].wait を読む（通常の RAM なので 4 サイクル、3 バイト）
        ...
@next:  inc um_m                ; m を 1 増やす（メモリ上で）
        lda um_m                ; m を読む
        cmp #8                  ; 8 に達したか
        bne @loop               ; 1 回あたりの管理のコストは 19 サイクル

; -O2：respawn に m を X で渡し、respawn は X を変えないので、m を X に置いたまま回せる
upd_loop:
        lda M_WAIT,x            ; METEORS[m].wait（ゼロページなので 2 バイト）
        ...
upd_next:
        inx                     ; 次の m へ
        cpx #8                  ; 8 に達したか
        bne upd_loop            ; 1 回あたりの管理のコストは 7 サイクル
```

<a id="r7"></a>
## 7. 手書きのアセンブリ

`asm/meteor_hand.s` は、[3章](#r3) のゲームの仕様から、最初からアセンブリで書いたものです。端末への出力が、コンパイル版とまったく同じになるように書いています。

手書きならではの工夫は次のとおりです。

- **変数の置き場所**：よく使う変数と隕石の配列を、すべてゼロページに置く
- **呼び出しの展開**：乱数、出し直し、入力の判定などを、呼び出さずにその場に書く
- **割り込み処理**：レジスタを使わない（`bit` で調べて、`bit` で読み捨てる）
- **プログラムの書き方**：TICKS を 8 ビットにする、大文字と小文字を `ora #$20` でまとめて判定する、文字列を 0 終端で 1 つの表にまとめ、表の中の位置（X）で渡す

最後の 3 つはゲームの仕様を変えない範囲の書き方の違いで、ax65 のソースでも同じように書けます。

## 8. 測定の方法

| 項目 | 内容 |
|---|---|
| 実行 | `tools/run_bench.py` が 5 つの版を `tools/asm65.py` で組み立て、`tools/sim65c02.py` で実行する |
| ハードウェアのモデル | W65C02S（1MHz）、VIA のタイマー1（連続モード、16666 サイクルごとに IRQ）、ACIA（送信と受信）。IRQ は ROM の `jmp ($0280)` を経由する |
| 入力 | 5 つの版に、同じキー操作を同じフレームで与える（左右の移動、無関係なキー、600 フレーム目に Q） |
| 条件 1：理想 | ACIA は常に送信可能（CPU の処理だけを比べる） |
| 条件 2：シリアル | ACIA は 1 文字ごとに 1042 サイクル送信中になる（1MHz で 9600bps）。送信待ちの時間も含めて測る |
| 条件 3：衝突 | 隕石に当たって終わる別のキー操作（57 フレームで終わる） |
| 測る範囲 | 計測用のラベル `bench_frame_begin`・`bench_upd`・`bench_draw`・`bench_frame_end` の間のサイクル数。途中で入った割り込みの分は差し引く |
| 動作の確認 | 端末への出力が、すべての版・すべての条件で一致すること |

## 10. 考察

### 10.1 既定の -O2 で、速さは手書きとほぼ同じ

-O2 の 1 フレームは 740 サイクルで、手書き（724 サイクル）との差は 2 % です。-O0 からは 27 % 短くなりました。コードは手書きの 1.23 倍で、4 つの段階の中で最も小さくなっています。

差が最も大きく縮んだのは隕石の更新（360 → 233 サイクル）です。[6章](#r6) のとおり、-O0 では `respawn` が X を壊すためにループの番号をメモリに置くしかなく、1 回あたり 12 サイクル余分にかかっていました。-O2 は `respawn` を展開せずに、番号を X で渡すように渡し方を変えたので、番号を X に置いたまま回せます。

### 10.2 -O1 は -O2 より遅く、大きい

-O1 は `respawn` を 2 か所に展開したため、コードが大きくなり、更新のループが $0400 のページ境界をまたぎました。6502 では、分岐がページ境界をまたぐと 1 サイクル余分にかかるので、ループの 1 回ごとに 2 サイクル、8 個の隕石で 16 サイクル遅くなっています（更新 246 対 233 サイクル）。`respawn` が呼ばれるのは隕石が下まで落ちたときだけ（600 フレームで 72 回）なので、展開しても速くなりません。-O2 を既定にした理由の 1 つです（[仕様書 Q&A I-3](ax65_spec_1.0.md#qa-i3)）。

### 10.3 -Os は -O2 より 1.5 % 速く、10 % 大きい

-Os は 729 サイクルで、手書きとの差は 0.6 % です。速くなった分の大部分は、表示の `digits()` の展開（498 → 487 サイクル）と起動です。`respawn` も展開しましたが、更新はほとんど変わりません（233 → 231 サイクル）。meteor.ax65 の `respawn` に `#[cold]` を付ければ、-Os でも展開されず、速さはほぼそのままで、コードは 20 バイトほど小さくなる見込みです（[仕様書 7.7](ax65_spec_1.0.md#s7-7)）。

-Os では、ループの配置のためにサブルーチンを起動処理の前に移しました。その結果、キーがないときの分岐（$03F1 → $0428）がページ境界をまたぐようになり、入力の処理が 1 サイクル遅くなっています。何度も回るループを優先して配置した結果です。

### 10.4 実際のシリアル速度では、差はほとんど見えない

9600bps のシリアルでは、1 フレームの表示の 11 文字だけで約 11000 サイクルの送信待ちが生じます。そのため、1 フレームの時間は -O0 の 11042 サイクルから手書きの 10828 サイクルまで、差は 2 % にとどまりました。どの版も 1 フレーム（16666 サイクル）に収まり、ゲームとしての動作は同じです。CPU の処理の差が効いてくるのは、表示を画面メモリに直接書く v3 のような構成や、処理の多いゲームです。

### 10.5 どの段階でも縮まらない差

手書きとの差のうち、TICKS の大きさ（16 ビットと 8 ビット）、大文字と小文字の判定、文字列の渡し方は、プログラムの書き方の違いで、最適化の段階では縮まりません。どれも ax65 のソースでも同じように書けます。コードの大きさの差（-O2 で 1.23 倍）の多くも、これらと、起動処理のポインタの設定などから来ています。

# meteor：最適化の段階ごとの比較（-O0／-O1／-O2／-Os／手書き）

仕様 版0.2 の最適化の段階（仕様書 12章）で meteor.ax65 をコンパイルした場合と、同じゲームを手書きしたアセンブリとを比べた結果です。

## 1. 比べたもの

| 版 | ファイル | 内容 |
|---|---|---|
| -O0 | `meteor_O0.s` | 最適化なし |
| -O1 | `meteor_O1.s` | 版0.1 の最適化（小さな関数は、複数の場所から呼ばれていても展開する） |
| -O2（既定） | `meteor_O2.s` | 大きさ優先の最適化 |
| -Os | `meteor_Os.s` | -O2 に加えて速さ優先 |
| 手書き | `meteor_hand.s` | ゲームの仕様（`meteor_game_spec.md`）から、最初からアセンブリで書いたもの |

-O0〜-Os は、ax65 のコンパイラがまだないため、仕様の規則に従って私が手で生成した「想定出力」です。実際のコンパイラの出力とは、細部が違う可能性があります。

どの段階にも、段階にかかわらず常に行う規則が入っています。具体的には、読み捨ての I/O に `bit` を使う、初期値が 0 の変数は `stz` で初期化する、ポインタの引数を A と X で渡す、末尾呼び出しを `jmp` にする、の4つです。

### 各段階で行ったこと

| 最適化 | -O0 | -O1 | -O2 | -Os |
|---|---|---|---|---|
| ゼロページへの自動配置 | | ○ | ○ | ○ |
| 1か所からしか呼ばれない関数の展開 | | ○ | ○ | ○ |
| 2か所から呼ばれる小さな関数（respawn）の展開 | | ○ | | ○（ループの中で呼ばれ、`#[cold]` がないため） |
| 引数の渡し方の変更（respawn の番号を X で渡す） | | | ○ | ― |
| ループをまたぐ不要な書き込みの削除（clear_meteors） | | | ○ | ○ |
| 共通部分のくくり出し（print_score） | | | ○ | |
| 順番に依存しないループの逆順化（clear_meteors） | | ○ | ―（ループごと削除） | ―（同左） |
| `digits()` の展開 | | | | ○ |
| ループの配置（ページ境界をまたがないようにする） | | | ○（またいでいなかった） | ○（サブルーチンを前に移して調整） |

## 2. 計測の方法

| 項目 | 内容 |
|---|---|
| ターゲット | v2：W65C02S、1MHz、RAM の $0300 に読み込んで実行、端末は ACIA、タイマーは VIA |
| 実行環境 | 作業用に作った 65C02 のアセンブラ（`asm65.py`）とエミュレータ（`sim65c02.py`）。サイクル数は W65C02S のデータシートの値（ページ境界をまたぐ場合の +1 なども含む） |
| 入力 | 5 つの版に、同じキー操作を同じフレームで与えた（600 フレーム目に Q で終了） |
| 計測 | 計測用のラベル（bench_）の間のサイクル数。途中で割り込みが入った場合は、その分を差し引いた |
| 動作の確認 | 5 つの版の端末への出力（6625 バイト、最終スコア 72）が、すべて一致した。隕石に当たって終わる別の入力（57 フレーム）でも一致した |

エミュレータの ACIA は常に送信可能として扱っています（実際の通信速度による待ちは含みません）。

## 4. わかったこと

### (1) 既定の -O2 で、速さは手書きとほぼ同じになる

-O2 の 1 フレームは 740 サイクルで、手書き（724 サイクル）との差は 2 % です。-O0 からは 27 % 短くなりました。コードは手書きの 1.23 倍で、4 つの段階の中で最も小さくなっています。速さと大きさの両方で、既定にする段階として妥当だと言えます。

### (2) -Os は、-O2 より 1.5 % 速く、10 % 大きい

-Os は 728.6 サイクルで、手書きとの差は 0.6 % まで縮みました。差が出たのは主に表示（`digits()` の展開で 11 サイクル短縮）と起動です。

一方、コードは -O2 より 40 バイト大きくなりました。`respawn` をループの中に展開したことと、`digits()` を展開したことによるものです。隕石の更新は、`respawn` を展開しても 232.6 → 231.1 サイクルとほとんど変わりません。`respawn` が呼ばれるのは隕石が下まで落ちたときだけ（600 フレームで 72 回）だからです。meteor.ax65 の `respawn` に `#[cold]` を付ければ、-Os でも展開されず、速さはほぼそのままで、コードは 20 バイトほど小さくなるはずです。

-Os ではループの配置も試しました。`respawn` を展開するとループが大きくなり、そのままでは $0400 のページ境界をまたぎます（版0.1 の -O で起きていた現象）。サブルーチンを起動処理の前に移すことで、ループを 1 つのページに収めました。入力が 1 サイクル遅くなっているのは、この並べ替えで、キーがないときの分岐（$03F1 → $0428）がページ境界をまたぐようになったためです。ループの配置を、何度も回るループを優先して行った結果です。

### (3) -O1 と -O2 の差

-O1 と -O2 の差（68 サイクル、47 バイト）は、主に次の 3 つから来ています。

- **respawn の扱い**：-O1 は 2 か所に展開し、ループが大きくなってページ境界をまたいだ（更新が 13 サイクル遅い）
- **共通部分のくくり出し**：-O2 は print_score の同じ形の処理をサブルーチンにまとめた。サイクルは少し増えるが、14 バイト小さい
- **不要な書き込みの削除**：-O2 は clear_meteors のループを削除した（約 10 バイト、起動時に約 130 サイクル）

### (4) どの段階でも縮まらない差

手書きとの差のうち、次のものは最適化の段階では縮まりません。どれも、ゲームの仕様を変えない範囲でのプログラムの書き方の違いで、ax65 のソースでも同じように書けます。

- **TICKS の大きさ**：手書きは 8 ビット、meteor.ax65 は 16 ビット。割り込み処理の 3 サイクルと、フレームを待つ処理の `atomic` の差になる
- **大文字と小文字の判定**：手書きは `ora #$20` でまとめて判定し、比較を 6 回から 3 回に減らしている
- **文字列の渡し方**：手書きは文字列を 1 つの表にまとめ、表の中の位置（1 バイト）で渡している

## 5. まとめ

| 段階 | 1 フレーム | 手書きとの比 | コード | 位置づけ |
|---|---|---|---|---|
| -O0 | 1016 サイクル | 1.40 倍 | 581 バイト | 生成されたコードを確かめたいとき |
| -O1 | 808 サイクル | 1.12 倍 | 433 バイト | 初期の仕様 |
| **-O2（既定）** | **740 サイクル** | **1.02 倍** | **386 バイト** | 大きさと速さの両方で最もよい |
| -Os | 729 サイクル | 1.006 倍 | 426 バイト | あと少し速さが欲しいとき |
| 手書き | 724 サイクル | 1 | 313 バイト | ― |

既定の -O2 で、速さは手書きとほぼ同じ（2 % の差）になり、コードも 4 つの段階の中で最も小さくなりました。-Os はさらに 1.5 % 速くなりますが、コードは 10 % 大きくなります。

どの版も 1 フレームの 1 割未満しか使っていないので、このゲームの規模ではどれでも十分に間に合います。実際のシリアル通信（9600bps）では、1 文字の送信に約 1000 サイクルかかり、表示の 11 文字だけで約 11000 サイクル待つので、段階による差は、フレーム全体の時間から見ればごくわずかです。

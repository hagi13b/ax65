# ax65 言語仕様書（第2版）

ax65 は、自作 6502 マシン専用のプログラミング言語およびそのコンパイラの名前です。

- 版：第2版（2026-10-29）

## 1. 目的と設計方針

### 1.1 目的

自作の 6502 マシン専用のプログラミング言語です。KIM-1 級（RAM 1KB 前後）から Apple I 級、Apple II 級（RAM 48KB 程度）へと拡張していくマシンを対象とします。既存のマシンとの互換性は求めません。汎用性は目標とせず、6502 で効率よく、安全に動くプログラムを書けることだけを目標とします。

### 1.2 設計方針

1. **ハードウェアの制約を、言語の制約で抑える。** 6502 で高くつく操作は、書けないようにするか、高くつくことが見える形でしか書けないようにします。
2. **検査はすべてコンパイル時に行う。** 実行時の検査のコストは、プログラマが明示した場所でしか払いません（Rust の方針と同じ）。
3. **コンパイラはプログラム全体を一度に解析する。** プログラムは 64KB 以内、ヒープなし、スレッドなし（並行して動くのは割り込みだけ）という前提により、呼び出しグラフ、スタック使用量、レジスタの使用状況などをすべて静的に求めます。
4. **最適化はプログラムの意味を変えない。** 最適化の段階（`-O0`〜`-O2`、`-Os`）によって、生成されるコードの大きさと速さは変わりますが、プログラムの意味は変わりません。既定は `-O2` です。配置と命令を最も予測しやすくしたい場合は `-O0` を使います（15章）。サイクル数を保証するブロック（`cycles()` など）とインラインアセンブリが参照する変数は、どの段階でも配置が変わりません。
5. **コンパイラが行った判断は、レポートで見えるようにする。** 変数の配置、レジスタの割り当て、`match` の実装方法、スタック使用量などをレポートに出力します。
6. **検査できない部分は、1か所に閉じ込める。** ROM ルーチンの宣言（`extern`）、範囲検査の省略（`unchecked()`）、`unsafe asm` など、プログラマが正しさに責任を持つ部分は、名前で検索できる形にします（Rust の `unsafe` に相当）。

「コンパイルが通ったプログラムは、スタックがあふれず、範囲外のアクセスをせず、割り込みとのデータ競合を起こさない」ことを目指します。

### 1.3 対象 CPU

| CPU | 扱い |
|---|---|
| 65C02（W65C02S を含む） | 基本の対象。65C02 の追加命令を前提にしたコードを生成する |
| NMOS 6502 | ターゲット定義で選択できる。コンパイラが命令を選び直し、NMOS 固有の落とし穴を避ける（13章） |

言語の意味は CPU によって変わりません。CPU によって変わるのは、生成されるコードの速さと大きさだけです。

### 1.4 コンパイラの形態

コンパイラは、まず PC 上で動くクロスコンパイラとして作ります。将来、Apple II 級のマシンでのセルフホストを検討できるよう、文法は小さく保ちます。Rust に寄せた文法でも、利用者が型の引数を定義する機能（ジェネリクス）を持たず、型は `:`・`->`・`as` の後ろにしか現れないため、1〜2 文字先を見るだけで構文を解析できます。

## 文法の方針

### 基本の書き方

| 項目 | 書き方 |
|---|---|
| コメント | `//`（行末まで）、`/* */`（複数行）。インラインアセンブリの中だけは `;` |
| 文の区切り | `;` が必須 |
| 変数 | `let x: u8 = 0;`（書き換えない）、`let mut x: u8 = 0;`（書き換える）。型は右辺から決まる場合は省略できる |
| グローバル変数 | `static X: u8 = 0;`（書き換えない）、`static mut X: u8 = 0;`（書き換える） |
| 定数 | `const LIMIT: u8 = 200;` |
| 関数 | `fn damage(e: Eid, n: u8) -> u8 { ... }`。最後の式（`;` のない式）が戻り値になる |
| 引数 | 既定では書き換えられない。書き換える引数は `mut x: u8` と書く |
| モジュールのパス | `::`（`hw::via`、`console::putc`、`Dir::Up`） |
| フィールドとメソッド | `.`（`e.hp`、`x.saturating_add(1)`） |
| 型の変換 | `x as u16` |
| 属性 | `#[...]`（`#[inline]`、`#[zp]`、`#[interrupt(irq)]` など） |
| 型の別名 | `type EnemyId = Eid;`（同じ型になる） |

### 数値

| 種類 | 書き方 |
|---|---|
| 16進 | `$FF` または `0xFF`（どちらも書ける。`ax65 fmt` でプロジェクトごとに一方へそろえられる。コンパイラの出力は `$` で表示する） |
| 2進 | `0b1010_0101` |
| 10進 | `255`、`1_000_000`（`_` で桁を区切れる） |
| 文字 | `'A'`、`'\n'`、`'\x41'`、`'A'@screen`（3.6節） |

### 名前の慣習

Rust と同じく、型・列挙型の値・ビットフラグの名前は `CamelCase`、関数・変数・モジュール・インターフェースは `snake_case`、定数・`static`・I/O 変数は `UPPER_CASE` とします。守らない場合は警告で、プロジェクトファイルで止められます。言語に組み込みの型（`u8`、`bool`、`char`、`str`、`bcd16`、`ptr<T>`、`strbuf<N>`）は小文字、ライブラリの型（`Option<T>`）は大文字で始まります。名前には ASCII の英数字と `_` だけを使えます。ソースファイルは UTF-8 で、文字列の中にだけ ASCII 以外の文字を書けます（変換表が必要）。

### Rust と違うところ

| 項目 | ax65 | 理由 |
|---|---|---|
| `char` | 1 バイト（Rust は 4 バイトの Unicode） | 6502 の文字は 1 バイト |
| 整数のあふれ | 常に一周して戻る（Rust はデバッグ時にパニック） | 6502 の `adc` の動作そのまま。検出したい場合は `checked_add` |
| ジェネリクス、トレイト、クロージャ、マクロ | なし | 構文解析とコード生成を小さく保つため |
| 参照とライフタイム | なし。ポインタ `ptr<T>` と、ローカル変数のアドレスの規則（4.5節）で代える | 6502 のポインタはゼロページの 2 バイト |
| 独自の機能 | `range`、`flags`、`io`、`shared`、`atomic`、`cycles`、`comptime`、`interface` など | 6502 と自作マシンのための機能 |

## 2. ターゲット定義

マシンごとの違いは、ターゲット定義ファイルに閉じ込めます。同じソースでも、ターゲット定義を替えればコンパイル結果が変わります（例：Apple II 級では通り、KIM-1 級では「RAM が 300 バイト足りない」というエラーになる）。

| 項目 | 内容 |
|---|---|
| CPU | `Cpu::Nmos6502`、`Cpu::C65C02`、`Cpu::W65C02S` など（品種まで区別する） |
| クロック周波数 | `us()` による時間指定に使う |
| メモリの区画 | RAM、ROM、I/O、ゼロページのアドレス範囲と、使用禁止の範囲 |
| スタック予算 | ページ $01 のうち、プログラムが使ってよいバイト数 |
| 実行の形 | RAM に読み込んで実行するか、ROM から実行するか |
| 割り込みベクタ | ハードウェアのベクタに直接書くか、モニタが用意する RAM 上のベクタに書くか |
| 割り込みの間隔 | 指定すれば、割り込み処理の時間の検査に使う |
| 文字の変換表 | `@変換表` で使う変換表（3.6節） |
| bind | インターフェースの実装の選択。bind されていることが「その機能がある」ことを意味する（11.4節） |
| 定数 | コードを伴わない性質。`target.名前` で読める |

I/O レジスタのアドレスは、ターゲット定義ではなく、bind される実装モジュールの中で宣言します。

### 2.1 ターゲット定義の書き方

ターゲット定義は ax65 と同じ文法で書きます。マシンの成長に合わせ、`extends` で前の構成を引き継いで差分だけを書けます。

```
// targets/kim.target
target kim {
    cpu   = Cpu::W65C02S;
    clock = 1_000_000;
    stack = 64;
    run   = ram;
    load  = $0200;
    region zp  = $00..=$EF;
    region ram = $0200..=$03FF;
    region io  = $1700..=$17FF;
    bind console = hw::led_console;
    const LED_DIGITS: u8 = 6;
}

// targets/v3.target
target v3 extends v2 {
    clock = 2_000_000;
    bind screen   = hw::v3_screen;
    bind keyboard = std::ps2_keyboard;
    const SCREEN_WIDTH: u8 = 40;
}
```

### 2.2 メモリの区画

```
region zp    = $00..=$FF;
region stack = $0100..=$01FF;
region ram   = $0200..=$1FFF;
region io    = $8000..=$8FFF;
region rom   = $E000..=$FFFF;
reserve $24..=$2B;                // モニタが使う場所（使用禁止）
place const in $F000..=$F7FF;     // 必要なら種類ごとの置き場所を指定
```

- 範囲は、言語の他の部分と同じく `..=`（終わりを含む）と `..`（含まない）で書きます。
- `@` で指定したアドレスが区画の外や `reserve` の中ならエラーです。I/O 変数のアドレスは `io` 区画の中でなければなりません。
- コンパイラが作るものは、コード、定数、初期値（起動時にコピーする元データ）、変数の4種類です。

| | コード・定数・初期値 | 変数 |
|---|---|---|
| `run = ram` | `ram` 区画（`load` のアドレスから） | `ram` 区画 |
| `run = rom` | `rom` 区画 | `ram` 区画 |

- 区画ごとの使用量をレポートに出します。

### 2.3 起動と終了

- `run = ram` では `load = $0300;` で読み込み先を指定し、モニタからそのアドレスを実行します。`run = rom` では、リセットベクタ（$FFFC）に起動処理のアドレスを書きます。
- `main` が終わったときの動作を `exit` で指定します。

| 指定 | 動作 |
|---|---|
| `exit = monitor($FF1F);` | モニタの入口へ `jmp` する |
| `exit = halt;` | その場で止まる（無限ループ） |
| `exit = never;` | `main` は終わってはならない。終わりうる場合はコンパイルエラー |

### 2.4 割り込みベクタ

| 指定 | 意味 |
|---|---|
| `irq = hw;` | ROM のベクタに直接書く（`run = rom` のとき） |
| `irq = indirect($0300);` | ROM が `jmp ($0300)` で飛ぶ形。$0300 に処理のアドレスを書く |
| `irq = jump($0300);` | ROM が `jmp $0300` で飛ぶ形。$0300 に `jmp` 命令ごと書く |

- `nmi` も同じ形で指定します。`indirect` と `jump` は起動処理の中で、割り込みを止めた状態で書き込みます。

### 2.5 出力形式の既定

```
output = [woz, sym, lst];
```

### 2.6 プロジェクトファイル

```
// ax65.proj
project mygame {
    main    = "src/main.ax65";
    paths   = ["src", "hw"];
    targets = [kim, v2, v3];      // --all-targets の検査対象
    default = v3;
}
```

### 2.7 コマンドライン

```
ax65 build                                   # 既定のターゲット、既定の最適化（-O2）でコンパイル
ax65 build -t v2                             # ターゲットを指定
ax65 build -t v3 -O0                         # 最適化をしない（-O1、-Os も指定できる）
ax65 build -t v3 -D debug                    # build.debug を true にする
ax65 build -t v3 --bind console=sim::console # bind を一時的に差し替える（エミュレータでの試験など）
ax65 check --all-targets                     # プロジェクトの全ターゲットで型まで検査
ax65 fmt                                     # ソースの書き方をそろえる
ax65 explain E0412                           # エラーの詳しい説明
```

## 3. 型

### 3.1 整数型

| 型 | 大きさ | 範囲 |
|---|---|---|
| `u8` | 1バイト | 0〜255 |
| `i8` | 1バイト | -128〜127 |
| `u16` | 2バイト | 0〜65535 |
| `i16` | 2バイト | -32768〜32767 |
| `u24` / `i24` | 3バイト | 0〜16777215 / -8388608〜8388607 |
| `u32` / `i32` | 4バイト | 0〜4294967295 / -2147483648〜2147483647 |
| `bcd8` / `bcd16` / `bcd32` | 1 / 2 / 4バイト | 10進 2 / 4 / 8 桁（3.12節） |

- **暗黙の変換をしない。** 8 ビットの値を自動で 16 ビットに広げることはしません。`u8` と `u16` を混ぜた式は、`as` での変換がなければエラーです。16 ビットの計算は、必ずソース上で見えます。
- **符号の混在をしない。** 符号付きと符号なしを混ぜた比較や代入は、`as` での変換がなければエラーです。
- **例外：`u8 + i8 → u8`。** 位置（`u8`）に変化量（`i8`）を足す操作だけは、変換なしで許可します。命令は `adc` 1つで済みます。
- **あふれは一周して戻る。** 符号付き・符号なしのどちらも、あふれた場合は一周して戻ると定義します。

符号付きで追加のコストがかかるのは、大小比較、8 ビットから 16 ビットへの拡張、右シフト、割り算と表示だけです。足し算と引き算は、符号の有無にかかわらず同じ命令です。

### 3.2 bool

`bool` は真偽値の型で、値は `true` と `false` です。`if` や `while` の条件には `bool` だけを書けます。比較の結果はフラグに入り、分岐命令に直接つながるため、値として 0 や 1 をしまうことは通常ありません。関数の戻り値としてはキャリーフラグで返します。

### 3.3 範囲型

決まった範囲の値だけを取る型です。中身は `u8` です。

```
range Eid = 0..16;              // 0〜15 の値だけを取る型（0..=15 と書いても同じ）
range Iid = 0..16;              // 範囲は同じだが、Eid とは別の型
type EnemyId = Eid;             // 別名（Eid と同じ型）
```

- **名前による型の区別**：同じ範囲でも、`range` の宣言ごとに別の型です。共有したいときは `type` で別名を付けます。
- **値の作り方**：範囲型の値は、範囲を必ず守れる方法でしか作れません。

| 作り方 | 例 | 実行時のコスト |
|---|---|---|
| for で回す | `for e in Eid { }`、`for e in Eid::range(a, b) { }` | なし |
| 定数 | `ENEMIES[3]`（範囲外ならコンパイルエラー） | なし |
| 範囲を確かめる変換 | `Eid::check(n)`（結果は `Option<Eid>`） | 比較と分岐 |
| 下位ビットだけを取る変換 | `Eid::wrap(n)`（範囲の個数が 2 のべき乗のとき） | `and` 1命令 |
| 検査の省略 | `Eid::unchecked(n)` | なし（プログラマの責任） |

- **演算**：範囲型の値に演算すると、結果は `u8` に戻ります。`e as u8` で明示的に `u8` にできます。
- **検査の要否**：範囲の検査が必要かどうかはコンパイラが型で判断します。プログラマが決めるのは、検査をどこで行うか（引数を範囲型にして呼び出し元で行うか、関数の中で行うか）だけです。

### 3.4 列挙型

```
enum Dir { Up, Down, Left, Right }                      // Up=0、Down=1、Left=2、Right=3
enum Cmd { Reset = $FF, Read = $10, Write = $11 }       // 値の明示もできる
```

- 値は `Dir::Up` のように書きます。中身は `u8` です。
- 範囲型と同じく、宣言ごとに別の型で、`for d in Dir` で回せ、`match` で網羅性が検査され、`Dir::check(n)` で `u8` から変換できます（結果は `Option<Dir>`）。列挙型から `u8` へは `d as u8` で変換します。
- 0 から連続した値の列挙型だけが、配列の添字に使えます。
- 値ごとに別のデータを持つ列挙型（Rust の enum のようなもの）は採用しません。必要な場合は、列挙型と構造体を組み合わせます。`Option<T>` だけは組み込みの例外です（3.11節）。

### 3.5 ビットフラグ型

```
flags Joy { Up, Down, Left, Right, Fire }   // Up=ビット0 … Fire=ビット4
```

- 各ビットに名前を付けた型です。8 ビットまでは `u8`、16 ビットまでは `u16` が中身になります。
- ビットの値は `Joy::Fire` のように書き、`|` で組み合わせます（`Joy::Up | Joy::Left`）。
- 操作の名前は、Rust の `bitflags` ライブラリと同じです。

| 操作 | 書き方 | 対応する命令 |
|---|---|---|
| 調べる | `j.contains(Joy::Fire)`、`j.contains(Joy::Up \| Joy::Left)` | `and`（ビット 6・7 は `bit`） |
| 立てる | `j.insert(Joy::Fire)` | `ora` |
| 消す | `j.remove(Joy::Fire)` | `and` |
| 反転する | `j.toggle(Joy::Fire)` | `eor` |

- I/O 変数の型にも使えます（`io(in) JOYPORT: Joy @ $6001;`）。`io(rmw)` のレジスタでは `tsb` と `trb` を使います。

### 3.6 文字型と文字の変換表

- `char` は文字の型で、`u8` とは別の型です。大きさは 1 バイトで、0〜255 のどの値も持てます（0〜127 が ASCII。128 以上の意味は、端末などの相手によって決まる）。
- `c as u8` で数値に、`n as char` で文字に変換できます。どちらもコストはかかりません。変換表付きの文字型への変換（`n as char@screen`）も同様に書けます。
- 文字の定数には、次のエスケープを使えます：`'\n'`（$0A）、`'\r'`（$0D）、`'\t'`（$09）、`'\0'`（$00）、`'\\'`（`\`）、`'\''`（`'`）、`'\x41'`（16進で指定）。文字列の中でも同じです。
- 何も指定しない文字・文字列は ASCII です。ソースの意味がターゲットによって変わることはありません。ASCII 以外の文字を変換表なしで書くとエラーです。
- `@変換表` を付けると、ターゲット定義の変換表で、コンパイル時に機種の文字コードに変換します。実行時の変換処理はありません。

```
// ターゲット定義の中の変換表の例（Apple II 級の画面）
encoding screen {
    ' '..='?' => $A0..=$BF;     // 範囲 → 範囲
    '@'..='_' => $C0..=$DF;
    '\r'      => $8D;           // 1文字 → 1値
}
```

- 変換表の項目は、「1文字 => 1値」か「文字の範囲 => 値の範囲」のどちらかです。範囲の両側の個数が違う場合はコンパイルエラーです。
- 同じ文字を2回書くとコンパイルエラーです。
- 変換表にない文字を使うとコンパイルエラーです。
- 変換表は文字以外のバイトにも使えます（7セグメント LED の点灯パターンなど）。
- 変換表ごとに別の型になります（`char@screen`、`str@screen`）。ASCII の文字列を受け取る関数に画面用の文字列を渡すとエラーです。

### 3.7 文字列

| 書き方 | 中身（"HI" の場合） | 型 |
|---|---|---|
| `"HI"` | `48 49` | `[char; 2]`（長さは型が持つ。長さも終端もない） |
| `p"HI"` | `02 48 49` | `str`（長さ付き、最大255文字） |
| `z"HI"` | `48 49 00` | 0終端の文字列 |
| `hi"HI"` | `48 C9` | 最上位ビット終端の文字列 |

- 接頭辞の考え方は Rust の `b"..."` と同じです。変換表の指定と組み合わせられます（`p"SCORE"@screen`、`z"OK"@serial`）。
- 標準の文字列型 `str` は長さ付きです。長さ付きは 0終端と同じ速さで出力でき、長さがすぐわかり、終端の書き忘れによる読みすぎが起きません。
- `z` と `hi` は、モニタの ROM ルーチンなど、その形式を要求する相手とのやり取りに使います。
- 書き換える文字列には、容量を決めた文字列バッファ `strbuf<N>`（N は 255 以下）を使います。`push(c)` は満杯のとき `false` を返し、あふれは起きません。
- ヒープがないため、文字列をつなげて新しい文字列を作る操作はありません。

### 3.8 構造体

```
struct Enemy { x: u8, y: u8, dir: Dir, hp: u8 }
```

- 構造体の配列の並べ方は 3.9 節のとおりです。
- 関数の戻り値として、構造体を値で返せます（5.3節）。
- 1要素を連続したバイト列として並べる必要がある構造体には、`#[packed]` を付けます（3.9節）。

#### 配列と構造体の値の書き方

| 書き方 | 意味 |
|---|---|
| `[1, 2, 3]` | 配列の要素を並べる。個数が配列の長さと違えばエラー |
| `[0; 16]`、`[v; Eid]` | 同じ値を、長さ（または範囲型・列挙型の個数）だけ繰り返す |
| `[for i in 0..8 => f(i)]` | 添字から計算する（10.4節） |
| `Enemy { x: 0, y: 0, dir: Dir::Up, hp: 3 }` | 構造体の値。すべてのフィールドを書く（書き忘れはエラー） |
| `Enemy { hp: 3, ..BASE }` | 書いたフィールド以外を、定数 `BASE` から取る（構造体更新構文） |

```
const ENEMY0: Enemy = Enemy { x: 0, y: 0, dir: Dir::Up, hp: 3 };
static mut ENEMIES: [Enemy; Eid] = [ENEMY0; Eid];
static TABLE: [u8; 4] = [1, 2, 4, 8];
```

- 「全バイトが 0」を表す特別な値は用意しません（Rust と同じく、値を具体的に書く）。値がすべて 0 の部分は、コンパイラが `stz` で初期化します（4.4節）。

### 3.9 配列

#### 型の書き方と添字

- 配列の型は `[T; N]` と書きます。従来の書き方 `T[N]` も同じ意味で書けます（2次元は `[[u8; 256]; 4]` または `u8[4][256]`）。`ax65 fmt` で一方にそろえられます。
- `N` には、長さ（256 以下の定数）か、範囲型・列挙型の名前を書きます。
- 添字に使える型は次のとおりです。

| 配列の型 | 添字に使える型 |
|---|---|
| `[u8; 256]` | `u8`（どの値でも範囲内なので検査不要） |
| `[Enemy; Eid]` | `Eid`（範囲型または列挙型） |
| `[u8; 16]` | 定数の添字だけ。変数で読むときは `a.get(n)`（結果は `Option<T>`）を使う |

- 範囲外になりうる値（ただの `u8` など）を、長さ 256 未満の配列の添字に使うとコンパイルエラーです。長さを数字で書いた配列を変数の添字で何度も使う場合は、範囲型を宣言して `[T; R]` にするのが基本です。
- `a.len()` で長さ（コンパイル時の定数）を得られます。

#### メモリ上の並べ方

- **構造体の配列は、フィールドごとの配列にするのが標準**です。`ENEMIES[i].y` と書けば、`y` だけを並べた配列の i 番目を読みます。番号をそのまま X に入れて1命令で読め、要素数も 256 まで扱えます。
- **u16 とポインタの配列は、下位バイトの配列と上位バイトの配列に分けるのが標準**です。
- `#[packed]` を付けた構造体の配列は、1要素を連続したバイト列として並べます（ディスクや通信のデータ形式、ハードウェアが決めた表など）。全体で 256 バイト以下です。
- フィールドごとの配列では、1要素を指すポインタは作れません。代わりに添字を渡します。

#### 256バイトを超えるデータ

- 256 バイトを超えるデータは、`[[u8; 256]; 4]`（`u8[4][256]`）のようなページ単位の配列として宣言します。コンパイラはページの先頭（アドレスの下位バイトが $00）に配置します。
- `&BUF` は配列全体の先頭（＝最初のページの先頭）のアドレス、`&BUF[k]` は k 番目のページの先頭のアドレスです。`&BUF` と `&BUF[0]` は同じ値で、型はどちらも `ptr<u8>` です。
- 行の長さが 2 のべき乗でない 2 次元配列（`[[u8; 40]; 24]` など）には、各行の先頭アドレスの表をコンパイラが自動で作り（下位・上位に分けて配置）、掛け算を使わずにアクセスします。表のメモリ使用量はレポートに出ます。

### 3.10 ポインタ

- ポインタ型は `ptr<T>` と書きます。ポインタ型の変数は自動でゼロページに置かれます。ゼロページの空きを超えたらコンパイルエラーです。
- ポインタでできる操作は、6502 で安く実行できるものに限ります。

| 操作 | 書き方 | 対応する命令 |
|---|---|---|
| 指す先を読み書き | `p[i]`（i は u8） | `lda (p),y`。i が 0 なら 65C02 の `lda (p)` |
| `#[packed]` 構造体のフィールド | `p.hp`（自動で指す先をたどる） | `ldy #位置` と `lda (p),y` |
| 次のページへ進める | `p.add_pages(1)` | `inc p+1` |
| 任意の数を足す | `p.add(n)` | 16ビットの足し算 |
| アドレスを代入 | `p = &TABLE;` | 下位・上位の2回の書き込み |
| 一致の比較 | `p == q` | 2バイトの比較 |

- `p.hp` のような `.` の後ろの名前は、`()` がなければ指す先のフィールド、`()` があればポインタのメソッドです。
- ヌルポインタはありません。標準のポインタは必ず有効な場所を指します。「指していないかもしれない」場合は `Option<ptr<T>>` を使います（3.11節）。
- ローカル変数のアドレスの扱いは 4.5 節のとおりです。

### 3.11 Option

- `Option<T>` は「値があるか、ないか」を表す型です（Rust と同じ）。値があるときは `Some(v)`、ないときは `None` です。
- 中身を使うには、`if let Some(v) = ...`、`match`、`?` 演算子のどれかで有無を確かめる必要があります。確かめずに使うとコンパイルエラーです。
- `?` 演算子は、値が `None` なら、その関数自身も `None` を返して抜けます（戻り値が `Option` の関数の中だけで使える）。

```
fn poll_key() -> Option<char> {         // キーが押されていれば文字を、なければ None を返す
    if KBDCR.contains(Kbd::Ready) { Some(KBD as char) } else { None }
}

fn read_cmd() -> Option<Cmd> {
    let c = poll_key()?;                // None ならここで None を返して抜ける
    Cmd::check(c as u8)
}

fn main_loop() {
    if let Some(c) = poll_key() {       // 値があれば c として受け取る
        putc(c);
    }
}
```

- `Option` を使わなければ、追加のコストはかかりません。使っても、値を包む処理は発生しません。
- 「ある・なし」の表し方はコンパイラが型ごとに選び、使える値の範囲は狭まりません。

| 場面 | 「ある・なし」の表し方 |
|---|---|
| 戻り値 | キャリーフラグ（値は通常どおり A などで返す） |
| 使われない値がある型（範囲型など）の変数 | 使われない値（$FF など）を「なし」に流用。追加のメモリなし |
| すべての値が有効な型（u8 など）の変数 | 「ある・なし」用にもう1バイト使う |

- 範囲型との役割の違い：範囲型は「値が決まった範囲に収まっているか」、`Option` は「値があるか、ないか」を表します。

### 3.12 演算

#### ビット演算とシフト

| 演算 | 書き方 | 対応する命令 |
|---|---|---|
| AND / OR / XOR | `a & b`、`a \| b`、`a ^ b` | `and`、`ora`、`eor` |
| ビット反転 | `!a`（Rust と同じ） | `eor #$FF` |
| 論理否定 | `!b`（`b` が `bool` のとき） | 分岐の向きを反転 |
| 定数回のシフト | `a << 3`、`a >> 3` | `asl` / `lsr` の繰り返し（符号付きの右シフトは符号を保つ） |
| 変数回のシフト | `a.shl(n)`、`a.shr(n)` | ループ（明示が必要） |
| キャリーを通したローテート | `a.rol()`、`a.ror()` | `rol`、`ror` |

- `<<` と `>>` の右側には定数だけを書けます。回数が変数の場合は `shl()` / `shr()` で明示します。
- 多バイトのシフトは、コンパイラが `asl` と `rol` などを組み合わせて作ります。
- `rol()` と `ror()` はキャリーを通して回す 6502 の命令で、Rust の `rotate_left` / `rotate_right`（キャリーを通さない）とは別のものです。

#### あふれの扱い

| 書き方 | 意味 |
|---|---|
| `a + b`、`a - b` | 一周して戻る（既定） |
| `a.checked_add(b)`、`a.checked_sub(b)` | あふれたら `None`（結果は `Option`。追加コストは分岐1つ） |
| `a.saturating_add(b)`、`a.saturating_sub(b)` | あふれたら最大値・最小値で止まる |

#### 多バイトの整数

- `u24`・`i24`・`u32`・`i32` は、明示的に書いたときだけ使える型です。キャリーのつなぎはコンパイラが作ります。
- 暗黙の変換をしない規則は、u16 と同じく適用します。

#### 10進演算（BCD）

- `bcd8`・`bcd16`・`bcd32` は、1バイトに10進2桁を入れる型です（$25 が「25」）。
- BCD の型のところに書いた10進の定数は、そのまま10進の値として BCD に変換します（`SCORE += 25;` の `25` は $25）。16進の定数を書くとコンパイルエラーです（`$25` が「25」なのか「37」なのか紛らわしいため）。範囲を超える定数（`bcd8` に `150` など）もコンパイルエラーです。
- 使える演算は足し算・引き算と大小比較だけです。`sed` と `cld` はコンパイラが前後に入れます。
- 他の整数型と混ぜた計算はエラーです。変換は `as` で明示します（割り算に近いコストがかかる）。
- `x.digits()` で1桁ずつ（上の桁から、0〜9 の `u8`）取り出せます。標準では全桁を結果領域に作ってから返します。`-Os`（15章）では、`for d in x.digits()` のように直接回す場合に限り、結果領域を作らずに展開します。
- 65C02 は割り込み時に自動で10進モードを解除します。NMOS では、割り込み処理の入口に `cld` を入れます（13章）。

#### 掛け算と割り算

- 定数の掛け算は、どんな定数でも `*` で書けます。コンパイラがシフトと足し算に展開し、命令数をレポートに出します。
- 割り算の演算子 `/` と `%` は、2のべき乗の定数だけに使えます（シフトと `and` になる）。
- それ以外の掛け算・割り算は、ライブラリの関数（`core::mul8`、`core::mul16`、`core::divmod8`、`core::divmod16` など）で明示します。
- 割り算の関数の結果は `Option` で、0で割った場合は `None` になります。
- メモリに余裕のあるターゲットでは、表を使った高速な掛け算のライブラリに切り替えられます（関数名と使い方は同じ）。

## 4. 変数と記憶域

### 4.1 記憶域の種類

| 書き方 | 置き場所 | 用途 |
|---|---|---|
| `static` / `static mut`（関数の外） | RAM の固定アドレス | グローバル変数 |
| `let` / `let mut`（関数の中） | RAM の固定アドレス（他の関数と重ねて使う） | ローカル変数 |
| `static mut`（関数の中） | RAM の固定アドレス（重ねない） | 呼び出しをまたいで値を保つ変数（Rust と同じ） |
| `#[zp]` を付けた `static` | ゼロページ | よく使う変数 |
| `const` | ROM（またはプログラム本体） | 表や文字列などの読み取り専用データ |
| `io(...)` | 指定したアドレス | I/O レジスタ（7章） |
| `shared(...)` | RAM（重ねない） | 割り込み処理とメインで共有する変数（8.5節） |
| `#[noinit]` を付けた `static mut` | RAM（重ねない） | 起動時に初期化しない変数 |

- `static`（`mut` なし）は、実行中に変わらない値ですが、`const` と違ってアドレスを持ちます（`&X` が使える）。
- `static mut` は、Rust と違って `unsafe` なしで読み書きできます。割り込みとの競合は、`shared` と `atomic` の規則（8章）で防ぎます。割り込み処理と通常の `static mut` を共有するとコンパイルエラーです（共有する変数は `shared` で宣言する）。

### 4.2 ゼロページ

- ポインタ型の変数は、自動でゼロページに置きます。
- それ以外の変数は、`#[zp]` を付けたものを必ずゼロページに置きます。
- `-O1` 以上（既定の `-O2` を含む）では、よく使う変数をコンパイラが自動でゼロページに移します。`-O0` では移しません。その際の規則は次のとおりです。
  - `#[zp]` の変数とポインタを置いた後の、残りの空きだけを使う（段階によってゼロページ不足のエラーが出ることはない）
  - `cycles()`・`io_span()` ブロックの中で使う変数は対象外
  - `io` 変数は対象外。`shared` 変数は `#[fixed]` を付ければ対象外にできる
  - インラインアセンブリから参照される変数は対象外（命令の長さとサイクル数が段階で変わらないようにするため）
  - 移した変数と、節約できる見込みのサイクル数・バイト数をレポートに出す

### 4.3 ローカル変数の重ね合わせ

- 再帰がないため、ローカル変数はスタックではなく固定アドレスに置きます。
- コンパイラは呼び出しグラフを解析し、同時に使われることのない関数同士のローカル変数を、同じアドレスに重ねて配置します。関数のローカル変数は、すべての呼び出し元のローカル変数の後ろに置かれます。
- 割り込み処理から呼ばれる関数のローカル変数は、メインの関数とは別の領域に置きます。
- 各関数のローカル変数の配置と合計の使用量をレポートに出します。メモリの合計がターゲット定義の RAM を超えたらコンパイルエラーです。

### 4.4 初期値

- `static` と `static mut` には、初期値の記述が必須です（`#[noinit]` を除く）。初期値は起動時に毎回設定し直します。これにより、RAM に読み込んだプログラムを2回実行しても、前回の値が残りません。
- `let` は、宣言のときに値を書かなくてもかまいません（`let mut buf: [u8; 8];`）。ただし、値を入れる前に読むとコンパイルエラーです（重ね合わせにより、他の関数が使っていた値が残っているため）。
- RAM に読み込んで実行する形と、ROM から実行する形の両方に対応し、ターゲット定義で切り替えます。ROM から実行する場合は、初期値を ROM に置き、起動時に RAM へコピーします。
- 初期値が 0 の変数は、元データを持たず、起動時に `stz` で 0 を書きます（連続した領域はループでまとめて書く）。元データを持つのは、初期値が 0 でない変数だけです。0 でない変数を元データからコピーするか、即値で書くかは、コンパイラが小さいほうを選びます。
- 起動時の初期化にかかるサイクル数とバイト数は、レポートに出します。

### 4.5 ローカル変数のアドレス

ローカル変数のアドレスは「下には貸せるが、外には出せない」とします。

- 呼び出し先の関数に渡すのは安全です（呼び出し先のローカル変数は、呼び出し元の領域と重ならないため）。
- 関数の戻り値として返す、`static` に保存する、といった、関数を抜けた後もアドレスが残る使い方はコンパイルエラーです。

## 5. 関数

### 5.1 関数の定義

```
fn damage(e: Eid, n: u8) -> bool {
    ENEMIES[e].hp = ENEMIES[e].hp.saturating_sub(n);
    ENEMIES[e].hp == 0                  // 最後の式が戻り値（return を省略）
}
```

- 関数とサブルーチンを区別せず、「入口と出口のデータを宣言したサブルーチン」として1つの仕組みにまとめます。引数も戻り値もない関数は、そのままサブルーチンとして使えます。
- `return` で途中から戻れます。最後の式（`;` のない式）は、`return` を書かなくても戻り値になります。
- 状態を書き換えない関数には `pure` を付けられます（`pure fn clamp(...)`）。`pure` な関数は、コンパイル時の計算にも使えます（10章）。
- 再帰呼び出し（直接・間接とも）はコンパイルエラーです。

### 5.2 引数の渡し方

- 引数は、呼び出し先が持つ固定アドレスの変数として扱います。
- 先頭から3バイト分は、A、X、Y の順に入れて渡します。u16 とポインタは A（下位）と X（上位）の2本を使います。呼び出し先は、後で使う値だけを自分の固定領域にしまいます。
- レジスタで受け取ったポインタは、呼び出し先が入口で自分のゼロページ領域に書きます（`(zp),Y` で使うため）。
- 4 バイトめ以降の引数（レジスタに入りきらないポインタを含む）は、呼び出し元が、呼び出し先専用の引数領域に直接書き込みます。ポインタの場合、その引数領域は呼び出し先のゼロページ領域です。

### 5.3 戻り値

戻り値は1つで、大きさによって返し方が決まります。

| 戻り値 | 返し方 |
|---|---|
| なし | 何も返さない |
| `bool` | キャリー |
| 1バイトの型（u8、i8、char、範囲型、列挙型、fnset の値など） | A |
| 2バイトの型（u16、i16、ポインタ） | A（下位）と X（上位） |
| 構造体 | すべてのフィールドを、呼び出し先の結果領域に置く |
| `Option<T>` | 有無をキャリーで返し、値は上の規則に従う |

- 構造体の結果領域は固定アドレスで、呼び出し元はコピーせずに直接読みます。同じ関数をもう一度呼ぶまで値は変わりません。古い結果を使い終わる前に同じ関数を呼ぶ場合だけ、コンパイラが自動でコピーを入れます。フィールドの数に制限はありません。
- 配列は直接は返せません。返したい場合は構造体に入れます。
- 結果を指すポインタを返す方式は採用しません。

### 5.4 レジスタの扱い

関数を呼ぶと A、X、Y は壊れる可能性がある、という前提にします。ただし、コンパイラはプログラム全体を解析し、呼び出し先が実際に壊すレジスタだけを、呼び出し元で退避します。

### 5.5 スタックの予算

- スタックに積まれるのは、`jsr` の戻り番地（2バイト）、割り込み時に CPU が積む戻り番地とフラグ（3バイト）、割り込み処理の入口でのレジスタ退避、コンパイラが入れる一時的な退避と `atomic` の `php` だけです。ローカル変数は積みません。
- コンパイラは、メイン・IRQ 処理・NMI 処理それぞれのすべての呼び出し経路について最大の使用量を求め、その合計がターゲット定義の予算を超えたら、原因の経路を示してコンパイルエラーにします。

```
エラー[E0301]：スタック予算超過（必要 140 バイト / 予算 128 バイト）
  メイン最深経路：main → update → draw_sprite → plot（112 バイト）
  IRQ：on_irq → read_kbd（16 バイト）
  NMI：on_nmi（12 バイト）
```

### 5.6 関数ポインタ（候補一覧）

```
fnset StateFn = { idle, walk, jump };       // 呼ぶ可能性のある関数の一覧（すべて同じ型）
static mut CURRENT: StateFn = idle;         // 一覧の中のどれかを指す変数（中身は番号）

fn update() {
    CURRENT();                              // CURRENT が指す関数を呼ぶ
    CURRENT = walk;                         // 一覧にある関数なら代入できる
}
```

- 候補一覧にない関数は代入できません。
- コンパイラは、呼び出しを「一覧のどれかを呼ぶもの」として呼び出しグラフに組み込みます。深さの計算と変数の重ね合わせはそのまま行えます。
- 65C02 では `jmp (表,x)` によるジャンプテーブルになります。NMOS では別の方法に切り替えます。

### 5.7 ROM ルーチンの宣言

```
extern fn rom_print(c: char in A)   // 引数 c を A で渡す
    @ $FFEF                         // ルーチンのアドレス
    clobbers(A, X, flags)           // 壊すもの
    stack(4);                       // 使うスタック（戻り番地を含む）
```

- コンパイラが中身を解析できないルーチンについて、引数のレジスタ、アドレス、壊すもの、スタック使用量を宣言します。
- 宣言の正しさはプログラマの責任です。

### 5.8 最適化に関わる指定

- 末尾呼び出し（`jsr` の直後が `rts`）は、常に `jmp` に置き換えます。
- `-O1` 以上では、関数ごとに引数の渡し方を変えてもかまいません。ただし、`extern` の関数と、アセンブリから呼ばれる関数は、常に標準の規則に従います。

| 属性 | 意味 |
|---|---|
| `#[inline]` | 展開してよい。`-O0` でも展開する |
| `#[inline(always)]` | 必ず展開する。展開できない場合はコンパイルエラー |
| `#[inline(never)]` | 決して展開しない |
| `#[cold]` | めったに呼ばれない関数であることを示す。`-Os` でも展開せず、何度も回るループの外に置く |

- 属性がない関数を展開するかどうかは、最適化の段階で決まります（15章）。
- `#[inline(always)]` と `#[inline(never)]` は、最適化の段階による判断より優先されます。
- 展開できない関数（`#[inline(always)]` を付けるとエラーになるもの）は、途中に `rts` がある `asm fn`、`unsafe asm` を含む関数、`extern` の関数、割り込み処理の関数です。
- `#[cold]` を用意するのは、ループの中でもめったに通らない枝で呼ばれる関数を、コンパイラが自分で見分けるのが難しいためです。こうした関数を展開すると、ループが大きくなってページ境界をまたぎ、かえって遅くなることがあります（meteor の比較で確認）。
- どの関数を展開したか、しなかったか、その理由をレポートに出します。

## 6. 制御構文

### 6.1 条件分岐

```
if hp == 0 { game_over(); } else if hp < 3 { warn(); }
let speed = if fast { 4 } else { 1 };       // if は値を返せる
```

- `if` の条件は `bool` だけです。条件を `( )` で囲む必要はありません（Rust と同じ）。
- `if` は式で、値を返せます。値を返す場合、`else` が必須で、両方の値は同じ型でなければなりません。
- `&&` と `||` は短絡評価です。
- 分岐命令が届かない遠くへの分岐は、コンパイラが自動で書き換えます。
- `if` の条件に、構造体の値をそのまま書くことはできません（Rust と同じ。`{` の意味が紛らわしくなるため）。

### 6.2 ループ

```
loop { ... }                        // 無限ループ
while cond { ... }                  // 条件が成り立つ間くり返す
#[max(100)] while cond { ... }      // 最大 100 回まで（上限に達したら抜ける）
for i in 0..10 { ... }              // 0〜9（終わりを含まない）
for i in 0..=255 { ... }            // 0〜255（終わりを含む）
for i in 0..n { ... }               // 終わりが変数でもよい
for e in Eid { ... }                // 範囲型・列挙型のすべての値
for e in Eid::range(a, b) { ... }   // 範囲型の一部（a から b の手前まで）
for i in (0..16).rev() { ... }      // 15 から 0 へ逆順
for c in "HELLO" { ... }            // 文字の配列の各要素
'outer: for y in 0..8 {             // 名前を付けたループ
    for x in 0..8 {
        if hit(x, y) { break 'outer; }
    }
}
```

- 範囲は、`..` が終わりを含まず、`..=` が終わりを含みます。言語のどこでも同じ意味です。
- 範囲の両端には変数も書けます。ループ変数の型は両端の型と同じです（両端の型が違う場合はエラー）。終わりが始まり以下なら、1回も実行しません。
- `Eid::range(a, b)` の `a`、`b` は `Eid` 型で、ループ変数も `Eid` 型になります。範囲型の配列の添字にそのまま使えます。
- `break`、`continue`、名前を付けた外側のループを抜ける `break 'name` を使えます。`goto` はありません。
- 逆順のループは `.rev()` で明示します。逆順にできそうなループには、コンパイラがレポートで助言を出します。`-O1` 以上では、順番に依存しないと証明できたループを、コンパイラが自動で逆順にします。証明の条件は、ループの中で I/O 変数・`shared` 変数に触れない、呼ぶ関数は `pure` だけ、各回で読み書きする配列要素がループ変数の位置だけ、ループ変数を外に保存・出力しない、の全部です。`cycles()` ブロックの中のループは対象外です。逆順にしたループはレポートに出します。
- 割り込み処理の中と、`cycles()`・`io_span()`・`max_cycles()` の中では、回数の上限がわかるループ（`for`、または `#[max(n)]` を付けた `while`）だけを使えます。両端が変数の `for` も、型から上限が決まるので使えます（u8 なら最大 256 回、u16 なら最大 65536 回として、サイクル数を見積もる）。

### 6.3 レジスタの割り当て

- ループカウンタなどを X や Y に置くかどうかは、コンパイラが自動で選び、レポートに出します。
- `#[reg(x)]` をループに付けて、プログラマがレジスタを指定することもできます。指定したレジスタが使えない場合（ループの中で呼ぶ関数がそのレジスタを壊すなど）はコンパイルエラーです。

```
#[reg(x)]
for m in Mid { METEORS[m].y = 0; }
```

### 6.4 match

```
match k {
    Key::Left  => move_left(),          // 右辺が式：後ろにカンマ
    Key::Right => { step(); step(); }   // 右辺がブロック：カンマは省略できる
    Key::Quit  => {}
}

match s {
    0     => idle(),
    1 | 2 => walk(),                    // | で複数の値をまとめる
    3..=9 => run(),                     // 範囲も書ける
    _     => stop(),                    // それ以外
}

let speed = match s { 0 => 0, 1 => 1, 2 => 2, _ => 4 };   // 値を返す match
```

- 腕の右辺には、式とブロックのどちらも書けます。式の後ろにはカンマが必要で、ブロックの後ろのカンマは省略できます。
- 値を返す `match` では、すべての腕の値（ブロックなら最後の式）が同じ型でなければなりません。
- 範囲型と列挙型では、すべての値を書いたかどうかを検査し、抜けがあればエラーにします。`u8` のように値の数が多い型では `_ =>`（それ以外）が必須です。
- `Option` には `Some(v) =>` と `None =>` で場合分けできます。
- 実装方法（比較を並べるか、ジャンプテーブルにするか）はコンパイラが選び、レポートに出します。`#[jump_table]` を付けて指定もできます。
- 各場合の結果が定数だけの `match` は、表引きに変換します。

## 7. I/O

```
io(in)  KBD:     u8  @ $D010;       // 読み込み専用
io(out) DSP:     u8  @ $D012;       // 書き込み専用
io      PORTB:   u8  @ $6000;       // 読み書き両方
io(rmw) DDRB:    u8  @ $6002;       // RMW 命令の使用を許可
io(in)  JOYPORT: Joy @ $6001;       // ビットフラグ型として宣言
```

- `io(in)` は読み込み専用、`io(out)` は書き込み専用です。逆の使い方はコンパイルエラーです。
- ソースに書いた読み書きは、それぞれ必ず1回のアクセスになり、省略も追加もしません。I/O 変数同士の読み書きの順序は、ソースの順のままです。
- I/O 変数の大きさは 1 バイトだけです。16 ビットのレジスタは、下位と上位を別々に宣言し、読み書きの順序をソースで明示します。
- RMW 命令（`inc`、`asl`、`tsb` など）は、内部でアクセスが2回以上起きるため、標準では I/O 変数に使いません。`io(rmw)` と宣言したレジスタにだけ使います。インデックス付きのアクセスで余分な読み込みが起きる場合も同じ扱いです。
- I/O 変数には `pub` を付けられません。I/O を操作できるのは宣言したモジュールだけです（11.5節）。
- 値を使わない読み込み（読むだけで状態が変わるレジスタを読む場合）は、`let _ = T1C_L;` と書きます（Rust と同じ書き方）。この読み込みは `bit` 命令で行います。読み込みは必ず1回行われ、A、X、Y は変わりません（フラグの N、V、Z だけが変わる）。

## 8. 割り込み

### 8.1 割り込み処理の宣言

```
#[interrupt(irq)]
fn on_irq() { ... }

#[interrupt(nmi)]
fn on_nmi() { ... }

#[interrupt(brk)]
fn on_brk() { ... }
```

- レジスタの退避と復帰、`rti` はコンパイラが作ります。退避するのは、割り込み処理の中で実際に使うレジスタだけです。
- 割り込み処理の関数は、引数と戻り値を持てません。
- `brk` 命令は IRQ と同じベクタを使うため、コンパイラが、スタック上のフラグの B ビットを調べて振り分けるコードを作ります。

### 8.2 割り込みベクタ

- ベクタの置き方は、ターゲット定義の `irq`・`nmi`（`hw`、`indirect(addr)`、`jump(addr)`）で指定します（2.4節）。

### 8.3 割り込み処理の制約

- 割り込み処理から呼べるのは、メインから呼ばれない関数だけです。両方から呼ばれる関数はコンパイルエラーです（ローカル変数が固定アドレスにあるため）。
- 割り込み処理の中での `cli`（`irq_enable()`）は禁止です（スタック予算が計算できなくなる、入れ子の実行でローカル変数が壊れる、割り込みの原因を消す前に許可すると無限に入れ子になる、の3つの理由による）。
- 割り込み処理の最長経路のサイクル数をレポートに出します。ターゲット定義に割り込みの間隔があれば、次の割り込みまでに終わらない場合をエラーにします。
- 割り込み処理の中のループには上限が必要です（6.2節）。

### 8.4 割り込みの許可と禁止

```
fn main() {
    ...                         // 準備（起動時から割り込みは止まっている）
    irq_enable();               // 割り込みを許可する
    loop { ... }
}
```

- 起動時は、すべての `init` が終わり、`main` が始まった時点でも割り込みは止まったままです（11.6節）。割り込みを使うプログラムは、`main` の中で `irq_enable()` を呼びます。
- 組み込み関数 `irq_enable()`（`cli` 1命令）と `irq_disable()`（`sei` 1命令）を用意します。
- `irq_enable()` を割り込み処理の中で呼ぶとコンパイルエラーです（8.3節）。
- `irq_enable()` を `atomic` の中で呼ぶとコンパイルエラーです（`atomic` の途中で割り込みが入るようになり、意味が壊れるため）。
- `irq_disable()` で割り込みを止めている間でも、`shared` 変数の操作には 8.5 節の規則がそのまま適用されます（割り込みを止めている範囲をコンパイラが追うと、検査が複雑になるため）。
- 割り込み処理を宣言していないプログラムで `irq_enable()` を呼ぶと警告を出します。

### 8.5 shared 変数

```
shared(irq)  KEYBUF: [u8; Kpos] = [0; Kpos];    // 書き込むのは割り込み処理だけ
shared(irq)  HEAD: Kpos = 0;                    // 書き込むのは割り込み処理だけ
shared(main) TAIL: Kpos = 0;                    // 書き込むのはメインだけ
shared       COUNT: u8 = 0;                     // どちらも書き込む
```

- `shared` は、割り込み処理とメインで共有する変数です。常に書き換えられる変数として扱い、`mut` は書きません。
- 書き込む側を `shared(irq)`、`shared(main)`、`shared(nmi)` で指定できます（Rust の `pub(crate)` と同じ形）。指定した側以外が書き込むとコンパイルエラーです。指定を省略した場合は両方が書き込めます。
- 1命令で済む操作（8 ビットの読み込み・書き込み、`inc`、`dec` など）は、どこでもそのまま書けます。
- 2命令以上になる操作（読んで計算して書き戻す、16 ビットの読み書きなど）は、次の規則に従います。

| 書く場所 | 共有の相手 | 2命令以上の操作 |
|---|---|---|
| メイン | IRQ 処理 | `atomic` が必要（下の「書き込む側が1つの場合の例外」を除く） |
| IRQ 処理の中 | メイン | `atomic` は不要 |
| NMI 処理の中 | メイン、IRQ 処理 | `atomic` は不要 |
| どこでも | NMI 処理 | エラー（NMI は止められないので、1命令の操作だけ） |

- 割り込み処理の中で `atomic` が要らないのは、6502 は IRQ でも NMI でも、割り込みが入るとすぐに I フラグを立てるので、割り込み処理の実行中には、メインも IRQ も割り込まないためです。

**書き込む側が1つの場合の例外**：書き込む側を指定した `shared` 変数では、次の操作に `atomic` は要りません。書き込む側が1つしかなければ、書き込む側が読む途中で値が変わることはなく、1バイトの書き込みは1命令で終わるため、読む側は必ず古い値か新しい値のどちらかを読むからです。

| 操作 | atomic |
|---|---|
| 書き込む側が、自分が書く変数を読む | 不要 |
| 書き込む側が書く。書き込みが1バイト（1命令）で終わる（読んで計算して書き戻す場合も含む） | 不要 |
| 書き込む側が書く。書き込みが2バイト以上 | 必要（読む側が、半分だけ書き換わった値を読みうる） |
| 読む側が、2バイト以上を読む | 必要 |
| 書き込む側を指定していない変数 | 必要 |

```
shared(irq) TICKS: u16 = 0;

#[interrupt(irq)]
fn on_irq() {
    TICKS += 1;                     // 割り込み処理の中なので atomic は不要
}

fn ticks() -> u16 {
    atomic { TICKS }                // メインの側で 16 ビットを読むので必要
}

fn next_tail() {
    TAIL = Kpos::wrap(TAIL + 1);    // 書き込むのはメインだけで、書き込みは1命令なので atomic は不要
}
```

- `shared` 変数同士の読み書きの順序は、ソースの順のままです。
- NMI 処理と共有する変数は、書き込む側の指定が必須で、1命令で済む操作しか使えません。

### 8.6 atomic

```
let t = atomic { TICKS };           // 割り込みを止めた状態で 16 ビットを読む
atomic {
    SPEED = v;                      // 割り込みを止めた状態で 16 ビットを書く
}
```

- `php` と `sei` で始まり、`plp` で終わります。
- ブロックの最後の式（`;` のない式）を、ブロックの値として返せます（Rust のブロック式と同じ）。値を読み終えてから `plp` を実行するので、読み込みの途中で割り込まれることはありません。
- 入れ子にできます。割り込み処理の中では何も生成しません（書かなくてもよく、書いても警告は出ません）。
- 最も長い `atomic` ブロックのサイクル数（割り込みが待たされる最大の時間）をレポートに出します。
- NMI は `sei` で止められないため、NMI と共有する変数を `atomic` の中で使うと警告を出します。

## 9. タイミング

| 形 | 意味 | 主な用途 |
|---|---|---|
| `cycles(n) { }` | ブロックの中の命令がちょうど n サイクル（足りない分は `nop` で埋める） | ビデオ表示のタイミングなど、処理全体の長さ |
| `io_span(n) { }` | ブロックの中の、最初の I/O の読み書きから最後の I/O の読み書きまでが、ちょうど n サイクル | パルスの幅など、I/O の間隔 |
| `max_cycles(n) { }` | n サイクル以内（超えたらエラー） | 時間内に終わらせたい処理 |
| `delay(n);` | 最低 n サイクル待つ（コンパイラが待ちループを作る） | 周辺チップの待ち時間 |

```
io_span(us(10)) {                   // ピンが 1 になってから 0 になるまで、ちょうど 10 マイクロ秒
    PORTB = 1;
    PORTB = 0;
}
```

- `cycles(n)` が数えるのは、ブロックの中の命令だけです（最初の命令の始まりから、ブロックの次の命令の始まりまで）。ブロックの外に書いた命令は含みません。
- `io_span(n)` は、各命令が実際にバスへ読み書きするサイクルで数えます。6502 では、`sta` などの書き込みは命令の最後のサイクルに行われるため、パルスの幅とブロックの中の命令の合計は一致しません。たとえば `sta PORTB`、`nop`、`nop`、`sta PORTB` のパルスの幅は、最初の `sta` の4サイクルを含まない 8 サイクルです。
- `io_span()` のブロックには、I/O の読み書きが2つ以上なければなりません。足りない分の `nop` は、最初と最後の I/O の読み書きの間に入れます。
- 時間は、コンパイル時の関数 `us()` で指定できます（`delay(us(40));`）。ターゲット定義のクロックからサイクル数を求め、ちょうどにならない場合は警告を出して切り上げます。
- `cycles()` と `io_span()` では、分岐の両方の経路のサイクル数を `nop` でそろえます。そろえられない場合はエラーです。ページ境界をまたぐことによるサイクルの増加は、コンパイラが配置で調整します。
- `cycles()` と `io_span()` のブロックは自動で `atomic` を兼ねます。ただし NMI は止められません。
- 中のループには上限が必要です（6.2節）。
- W65C02S のターゲットでは、割り込みが来るまで CPU を止める `wait_interrupt()`（`wai` 命令）を使えます。それ以外の CPU ではコンパイルエラーです。

## 10. コンパイル時の計算と条件コンパイル

### 10.1 コンパイル時に計算される場所

`const` と `static` の初期値、配列の長さ、範囲型の上限・下限、`cycles()`・`io_span()`・`max_cycles()`・`delay()` の引数、`@` のアドレス、`match` の場合の値は、必ずコンパイル時に計算されます。計算できない式はコンパイルエラーです。

### 10.2 pure 関数

- `pure fn` は、実行時にもコンパイル時にも呼べます（Rust の `const fn` に相当。ax65 では `const` を値の宣言だけに使うため、`pure` という名前にしている）。
- コンパイル時に計算しても、実行時と同じ型の規則（あふれは一周して戻るなど）で計算し、結果は実行時と一致します。

### 10.3 comptime 関数

```
comptime fn sine_at(i: int) -> i8 {
    let r: real = sin(i as real * 2.0 * PI / 256.0);
    round(r * 127.0) as i8              // 範囲外ならコンパイルエラー
}
```

- `comptime fn` はコンパイル時にしか呼べません。実行時のコードから呼ぶとエラーです。
- 中では、コンパイル時専用の型 `int`（大きさの制限なし）と `real`（倍精度の小数）、数学関数（`sin`、`cos`、`sqrt`、`round` など）を使えます。
- 結果を実行時の型に変換するとき、範囲を超えたらエラーにします（一周させない）。
- `us()` は、標準ライブラリ `core` の `comptime fn` として提供します。
- 1つの定数の計算に使える手順数に上限を設け、超えたらエラーにします（上限はオプションで変更可）。

### 10.4 表の生成

```
const SINE: [i8; 256] = [for i in 0..256 => sine_at(i)];
const ROW_ADDR: [u16; 24] = [for r in 0..24 => $0400 + r * 40];
```

- 配列の各要素を、添字から計算する式で書けます。
- 2次元配列の行の表の自動生成（3.9節）も、この仕組みを使います。

### 10.5 外部データの取り込み

```
const TILES: [u8; 256] = include_bin("tiles.bin", offset = 16);
```

- ファイルの中身をそのまま配列の初期値にします。大きさが配列の長さと合わなければコンパイルエラーです。

### 10.6 コンパイル時の検査と情報

```
comptime assert(size_of(Packet) == 4, "Packet は4バイトでなければならない");
```

- `comptime assert` で、プログラマが書いた条件をコンパイル時に検査します。
- `size_of(型)`、`a.len()`、`target.xxx`（ターゲット定義の値）、`build.xxx`（コンパイラのオプションで渡した値）を読めます。

### 10.7 条件コンパイル

```
fn idle() {
    comptime if target.cpu == Cpu::W65C02S {
        wait_interrupt();
    }
}

comptime if target.has(screen) {
    io SCREEN: [u8; 40] @ $0400;
}

comptime match target.cpu {
    Cpu::W65C02S => wait_interrupt(),
    _            => {}
}
```

- `comptime if` と `comptime match` は、関数の中（文）にも外（宣言）にも書けます。文字列を置き換えるプリプロセッサやマクロはありません。
- 条件に使えるのは、インターフェースが bind されているか（`target.has(screen)`）、CPU とクロック（`target.cpu`、`target.clock`）、ターゲット定義の定数（`target.SCREEN_WIDTH` など）、ビルドの設定（`ax65 -D debug` で渡す `build.debug` など）です。機種名による分岐はできません（マシンが育っても、ターゲット定義に bind を書き足すだけで済むようにするため）。
- `target.has()` に書けるのは既知のインターフェースの名前だけ、`target.名前` に書けるのはターゲット定義の定数の名前だけです。書き間違いはエラーです。
- 選ばれなかった側のコードはプログラムに含まれず、スタック・メモリ・呼び出しグラフの検査も、選ばれた側だけで行います。
- 選ばれなかった側は、構文だけを検査します。登録したすべてのターゲット定義で型まで検査するコマンド（`ax65 check --all-targets`）を別に用意します。

## 11. モジュールとライブラリ

### 11.1 モジュールと use

```
use math;                           // math.ax65 を読み込む
use hw::via;                        // hw/via.ax65 を読み込む
use console::{putc, poll};          // console の putc と poll を、名前だけで使えるようにする
use hw::via as v;                   // 別名を付ける
use hw::via as _;                   // init のためだけに読み込む（11.6節）
```

- 1つのファイルが1つのモジュールです。`use` で読み込みます（Rust の `mod` の宣言は不要で、`use` がファイルの読み込みを兼ねる）。
- 分割コンパイルとリンクは行いません。コンパイラは `use` をたどってすべてのファイルを読み込み、プログラム全体を1つとして解析します。
- モジュールの循環は許しますが、init の順序が決まらない場合はエラーです。

### 11.2 名前と公開範囲

- 他のモジュールの名前は `モジュール名::名前` で参照します（`via::init_ports()`）。
- `use` で取り込んだ名前が重なったらエラーです。
- 宣言は既定で非公開です。`pub` を付けたものだけを他のモジュールから使えます。

### 11.3 使われないコードの除去

- `main` と割り込み処理から呼び出しグラフをたどり、使われない関数・変数・表はプログラムに含めません。
- モジュールごとのメモリ使用量（コード、変数、ゼロページ）をレポートに出します。

### 11.4 インターフェースと実装

```
// std/console.ax65
interface console {
    fn putc(c: char);
    fn getc() -> char;
    fn poll() -> Option<char>;
}

// hw/acia_console.ax65
impl console {
    io(in)  STATUS: u8 @ $8001;
    io(out) DATA:   u8 @ $8000;
    pub fn putc(c: char) { ... }
    ...
}

// hw/wozmon_console.ax65（ROM ルーチンを実装にする例）
impl console {
    pub extern fn putc(c: char in A) @ $FFEF clobbers(flags) stack(2);
    ...
}
```

```
// ターゲット定義
bind console = hw::acia_console;
```

- インターフェースは関数と定数の形だけを宣言します。実装は `impl` で書き、どの実装を使うかはターゲット定義の `bind` で選びます。使う側はインターフェースの名前で `use` し、実装の名前は書きません。
- インターフェースはモジュールに対する仕組みで、Rust のトレイト（型に対する仕組み）とは別のものです。1つのターゲットで、1つのインターフェースに bind できる実装は1つだけです。
- 実装の過不足や型の違いはコンパイルエラーです。
- 実装はコンパイル時に決まるため、呼び出しは直接の `jsr` になり、実行時のコストはありません。
- bind されていないインターフェースも `use` はできますが、`comptime if target.has(...)` の外で使うとエラーです。
- 使い分け：どの機種にもあり中身が違う機能はインターフェース、機種によって有無が違う機能や小さな違いは `comptime if` を使います。

### 11.5 I/O の所有者

- I/O 変数は公開できません。他のモジュールは、所有モジュールの関数を通して使います。
- プログラム全体の I/O 変数のアドレスを集め、2つのモジュールが同じアドレスを宣言していたらエラーにします。チップ全体で共有するレジスタがある場合は、1つのモジュールにまとめます。

### 11.6 init と起動の順序

```
init {
    DDRB = $FF;
}
```

- モジュールごとに `init` ブロックを書けます。起動時の順序は、スタックポインタの設定、グローバル変数の初期値の設定、各モジュールの `init`（読み込まれる側が先）、`main` です。
- `init` は起動の手順の中に直接展開されます。`init` がなければコストは0です。
- `init` の実行中は割り込みが止まっています。`main` が `irq_enable()` で許可するまで割り込みは入りません。
- `use` されたモジュールの `init` は、そのモジュールを使っていなくても必ず実行します。`init` を実行させない方法はありません。
- 使っていないモジュールの `use` には警告を出します。`init` があるモジュールでは、起動時に実行されることも知らせます。`init` だけが目的の場合は `use hw::via as _;` と書くと警告が出ません（Rust の書き方と同じ）。`as _` で読み込んだモジュールの名前は使えません。
- すべての `init` の実行順、サイクル数、バイト数をレポートに出します。

### 11.7 標準ライブラリ（予定）

| モジュール | 内容 |
|---|---|
| `core` | `us()` などのコンパイル時の関数、`mul8`・`divmod8` などの算術 |
| `bcd` | BCD の桁の取り出し、表示用の変換 |
| `text` | 数値の文字列化、`strbuf` の操作 |
| `console` | 1文字の入出力のインターフェース |
| `timer` | 時間を測るインターフェース |

## 12. インラインアセンブリ

### 12.1 基本方針

コンパイラはインラインアセンブリを1命令ずつ解析し、壊すレジスタとフラグ、スタック使用量、サイクル数、呼び出しグラフを自動で求めます。プログラマがこれらを宣言する必要はなく、これまでの検査はインラインアセンブリの中でも続きます。

### 12.2 書き方

```
asm {
    lda {SCORE.lo}              ; 言語の変数は {名前} で参照する
    ...
}

asm (in A = v, out A -> r) {    ; 値をレジスタで受け渡す
    ...
}

asm fn bit_count(v: u8) -> u8 { ; 関数全体をアセンブリで書く（標準の呼び出し規約に従う）
    ...
    rts
}
```

- 言語の名前は `{名前}` で参照します（ラベルや数値と区別するため）。
- 2バイト以上の変数は `{W.lo}`、`{W.hi}` のように、どのバイトかを明示します。
- 参照した変数について、アドレッシングモード（間接参照はゼロページの変数だけ）、初期化前の読み込み、I/O の所有者・読み書きの方向・RMW の可否、`shared` 変数の2命令以上の操作を検査します。
- ラベルはブロックの中だけで有効です。数値は言語と同じく `$FF`、`0xFF`、`0b...` で書きます。

### 12.3 ブロックの決まり

- ブロックの入口と出口で、スタックの深さが同じでなければなりません。
- 分岐と `jmp` の飛び先は、ブロックの中のラベルかブロックの終わりだけです。
- `jsr {関数名}` で ax65 の関数を呼べます（呼び出しグラフに組み込まれる）。ROM ルーチンは `extern` で宣言したものだけを呼べ、数値のアドレスへの `jsr` はエラーです。
- ターゲットの CPU にない命令と、未定義命令はエラーです。
- 割り込み処理の中と `cycles()` などの中では、ループの回数の上限をコンパイラが求められる形でなければなりません。

### 12.4 unsafe asm

`txs`、`sei`、`cli`、`plp`、`rti`、`brk`、間接ジャンプ、数値のアドレスへの書き込みなど、検査の前提を崩す命令は、通常の `asm` では書けません。必要な場合は `unsafe asm` を使い、コンパイラが求められない性質を宣言します。

```
unsafe asm (clobbers(A), stack(1), cycles(12..=20), irq(disables)) {
    ...
}
```

- 宣言の正しさはプログラマの責任です（`extern` と同じ位置づけ）。
- `unsafe asm` の中でも、他のモジュールの I/O 変数や他の関数の変数のアドレスへの書き込みはエラーです。
- `unsafe asm` で使った数値のアドレスは、レポートに一覧で出します。
- 割り込みを止めるだけなら、`atomic { }` の中に通常の `asm` を書きます。

### 12.5 自己書き換えコード

```
asm {
    smc load: lda $1200,x       ; オペランドを書き換えてよい命令
}
```

- 書き換える命令には `smc` を付けます。宣言なしに命令の位置へ書き込むとエラーです。
- 書き換えられるのはオペランドだけで、オペコードは書き換えられません（サイクル数とスタックの解析を続けるため）。
- `run = rom` のターゲットでは、`smc` はエラーです。

## 13. CPU による違いの扱い

65C02 では、次の追加命令を活用します。

| 追加命令 | 主な用途 |
|---|---|
| `(zp)` | ポインタの指す先の読み書き（Y を使わない） |
| `phx` `phy` `plx` `ply` | 割り込み処理のレジスタ退避 |
| `inc a` `dec a` | A の ±1 |
| `stz` | 0 の書き込み |
| `bra` | 無条件の短い分岐 |
| `jmp (abs,x)` | ジャンプテーブル（関数ポインタ、match） |
| `tsb` `trb` | ビットの操作 |
| `wai`（W65C02S のみ） | 割り込み待ち |
| `rmb` `smb` `bbr` `bbs`（W65C02S など一部の品種のみ） | ゼロページのビット操作（品種をターゲット定義で区別する） |

NMOS 6502 のターゲットでは、コンパイラが次の点を自動で処理します。

- 割り込み処理の入口に `cld` を入れる（NMOS は割り込み時に 10 進モードを解除しないため）
- 間接ジャンプの格納先を $xxFF に置かない（`jmp (ind)` のページ境界のバグを避けるため）
- 10 進演算の後の N・Z フラグを判定に使わない
- 65C02 の追加命令を、同じ働きの命令の組み合わせに置き換える

未定義命令は、どの CPU でも使いません。

## 14. コンパイラの検査とレポート

### 14.1 主なコンパイルエラー

- 再帰呼び出し
- スタック予算の超過
- RAM・ゼロページの容量の超過
- 型の不一致（`u8` と `u16` の混在、符号の混在、範囲型・列挙型・変換表の違い、`[char; N]` と `str` の違いなど）
- 範囲外になりうる添字
- 値を入れる前のローカル変数の読み込み、`let`（`mut` なし）への再代入、`mut` のない引数への代入
- ローカル変数のアドレスの持ち出し
- `Option` の値の、有無を確かめない使用。戻り値が `Option` でない関数の中での `?`
- `match` の場合の抜け、値を返す `match`・`if` の腕の型の違い、値を返す `if` の `else` の抜け
- 割り込み処理とメインの両方から呼ばれる関数
- 割り込み処理の中と `atomic` の中での `irq_enable()`
- 割り込み処理と通常の `static mut` の共有
- BCD の型への16進の定数、範囲外の定数
- `shared` 変数への、規則（8.5節）に反する2命令以上の操作、指定外の側からの書き込み、NMI と共有する変数への2命令以上の操作
- I/O 変数の、読み込み専用・書き込み専用に反する使用
- 割り込み処理と `cycles()` などの中の、上限のないループ
- `cycles()`・`io_span()` のサイクル数の超過、分岐のサイクル数がそろえられない場合、I/O の読み書きが2つ未満の `io_span()`
- 変換表にない文字、変換表の中の同じ文字の重複、範囲の両側の個数の違い
- 構造体の値でのフィールドの書き忘れ、配列の値の個数の違い
- `#[reg(x)]` で指定したレジスタが使えない場合
- `#[inline(always)]` を付けた関数を展開できない場合
- ターゲットの CPU にない機能の使用（`wait_interrupt()` など）
- コンパイル時に計算できない式を、定数が必要な場所に書いた場合
- `comptime fn` の実行時の呼び出し、実行時の型への変換での範囲超過、手順数の上限超過
- `include_bin` のファイルの大きさと配列の長さの不一致
- `comptime assert` の条件が成り立たない場合
- `target.has()` や `target.名前` の知らない名前
- 実装（`impl`）のインターフェースに対する過不足・型の違い、bind の誤り
- bind されていないインターフェースの、`comptime if` の外での使用
- `use` で取り込んだ名前の重なり、非公開の名前の使用、I/O 変数への `pub`
- 複数のモジュールによる同じ I/O アドレスの宣言
- init の順序が決まらないモジュールの循環
- インラインアセンブリ：スタックの不釣り合い、ブロック外への分岐、未宣言の数値アドレスへの `jsr`、CPU にない命令・未定義命令、通常の `asm` での検査できない命令、変数のバイトの未指定、宣言のない命令の書き換え、ROM ターゲットでの `smc`

### 14.2 主な警告

- `us()` の時間がちょうどのサイクル数にならない
- NMI と共有する変数を `atomic` の中で使っている
- 割り込み処理を宣言していないプログラムでの `irq_enable()`
- 使っていない `use`（init がある場合は、起動時に実行されることも示す）
- 名前の慣習（`CamelCase`、`snake_case`、`UPPER_CASE`）に合わない名前
- 書き換えていない `let mut`

警告は `#[allow(警告の名前)]` で、その場所だけ止められます（`#[allow(unused_imports)]` など。Rust と同じ）。

### 14.3 レポートの内容

- 変数の配置（アドレス、ゼロページ、レジスタ）
- 各関数のローカル変数の重ね合わせの結果と、合計のメモリ使用量
- スタックの最大使用量と、その経路
- 割り込み処理の最長サイクル数、最も長い `atomic` ブロックのサイクル数
- `match` の実装方法
- 自動で作った表（2 次元配列の行の表、`match` の表など）のメモリ使用量
- 最適化で行った変更（ゼロページへの移動、インライン化、逆順化など）と、使った最適化の段階
- 逆順にできそうなループの助言
- 区画ごと・モジュールごとのメモリ使用量、`init` の実行順・サイクル数・バイト数、`unsafe asm` で使った数値のアドレス
- 起動時の初期化のサイクル数・バイト数（4.4節）
- ループの配置の結果（ページ境界をそろえるために入れた空きのバイト数、そろえられなかったループ）（15.2節）
- 展開した関数・しなかった関数と、その理由（5.8節）

レポートは1つのファイル（`.report`）にまとめます。

### 14.4 エラーメッセージの書式

```
エラー[E0412]：ENEMIES の添字に u8 は使えません
  --> src/main.ax65:24:13
   |
24 |     ENEMIES[n].hp = 0;
   |             ^ n は u8 型で、0〜255 のどれでもありえます
   |
補足：ENEMIES の添字の型は Eid（0..16）です
候補：Eid::check(n) で範囲を確かめてください
```

- 場所、番号、内容、補足、直し方の候補の順に示します（Rust のコンパイラと同じ形）。
- エラーと警告には番号を付け、`ax65 explain E0412` で詳しい説明と例を表示できます。
- `-W error` で警告をエラーとして扱えます。
- エラーメッセージとレポートは、人が読む形式が標準です。`--json` で同じ内容を JSON で出力できます。

### 14.5 出力形式

| 形式 | 拡張子 | 用途 |
|---|---|---|
| バイナリ | `.bin` | 読み込み先から始まる生のバイト列 |
| Wozmon 形式 | `.woz` | `0300: A9 00 ...` の16進テキスト（1行の長さ、最後の `300R` の有無を選べる） |
| Intel HEX | `.hex` | ROM ライタ向け |
| ROM イメージ | `.rom` | ROM の大きさちょうど。空きは $FF、ベクタを含む |
| KIM-1 紙テープ形式 | `.ptp` | KIM-1 のモニタ向け |
| シンボル | `.sym` | 関数・変数・ラベルのアドレスの一覧 |
| リスティング | `.lst` | ソースの行と、アドレス・バイト列・サイクル数・命令・命令の説明を並べた一覧 |

- 複数の形式を同時に出力できます。既定はターゲット定義の `output`、コマンドラインでは `--emit bin,lst` で指定します。
- リスティングの命令の説明は、`--lst-plain` で省けます。

```
                         ; main.ax65:12   if hp == 0 {
0310  AD 40 02    4      lda HP          ; HP を A に読む
0313  D0 03       2/3    bne $0318       ; 0 でなければ if の中を飛ばす
                         ; main.ax65:13       game_over();
0315  20 80 04    6      jsr game_over   ; game_over を呼ぶ
```

## 15. 最適化の段階

最適化は次の4段階です。どの段階でも、プログラムの意味は変わりません。

| 段階 | 方針 | 位置づけ |
|---|---|---|
| `-O0` | 最適化をしない。配置と命令が最も予測しやすい | デバッグや、生成されたコードを確かめたいとき |
| `-O1` | 速さと大きさの釣り合いを取る、版0.1 の最適化 | 初期の仕様 |
| `-O2` | 大きさを優先する最適化。6502 では命令を小さくすることが速さにもつながるため、多くの場合、速さも最もよくなる | **既定** |
| `-Os` | `-O2` に加えて、コードが大きくなっても速さを優先する | 速さが足りないとき |

何も指定しなければ `-O2` になります。`-O2` を既定にしたのは、meteor の比較で、`-O2` が手書きのアセンブリとの差 2 % まで速く、4 つの段階の中で最も小さかったためです（`bench/comparison.md`）。

なお、GCC などでは `-Os` は大きさ優先の意味で使われますが、ax65 では速さ優先（speed）の意味です。

### 15.1 `-O1` で行うこと（版0.1 の最適化）

- ゼロページへの自動配置（4.2節）
- 関数のインライン化（1 か所からしか呼ばれない関数と、小さな関数を展開する）（5.8節）
- 関数ごとの引数の渡し方の変更（5.8節）
- 構造体の戻り値の最初のフィールドをレジスタでも返す
- 順番に依存しないループの自動の逆順化（6.2節）

### 15.2 `-O2` で行うこと（既定）

- ゼロページへの自動配置（4.2節）
- **インライン化**：1 か所からしか呼ばれない関数と、`#[inline]` を付けた関数だけを展開する。2 か所以上から呼ばれる関数は展開しない（5.8節）
- 関数ごとの引数の渡し方の変更（5.8節）
- **不要な書き込みの削除**：後で読まれずに上書きされるだけの書き込みを消す。ループをまたぐ場合（すべての要素を書くループの後に、すべての要素を書き直すループがある場合など）も対象とする
- **共通部分のくくり出し**：同じ形の命令の並びが複数あれば、小さなサブルーチンにまとめる。何度も回るループの中の並びは対象外とする
- 構造体の戻り値の最初のフィールドをレジスタでも返す
- 順番に依存しないループの自動の逆順化（6.2節）
- **何度も回るループの配置**：ループの中の分岐が、ページ境界をまたがないように、関数やコードの並び順を入れ替える。6502 では、分岐がページ境界をまたいで飛ぶと 1 サイクル余分にかかるため。空きのバイトは入れない。そろえられなかったループはレポートに出す

### 15.3 `-Os` で行うこと（速さ優先）

- `-O2` のすべて。ただし共通部分のくくり出しは行わない（呼び出しのコストがかかるため）
- **インライン化の拡大**：2 か所以上から呼ばれる小さな関数も、ループの中で呼ばれていれば展開する。`#[cold]` を付けた関数は展開しない
- `for` で直接回す `digits()` の展開（3.12節）
- **ループの配置**：並び順の入れ替えでそろえられない場合は、空きのバイトを入れてでもページ境界をそろえる。入れたバイト数はレポートに出す

`cycles()`・`io_span()` ブロックの中のページ境界の調整は、段階にかかわらず常に行います（9章）。

### 15.4 段階にかかわらず常に行うこと

- 末尾呼び出しの置き換え（5.8節）
- 値を使わない I/O の読み込みに `bit` を使う（7章）
- 初期値が 0 の変数を `stz` で初期化する（4.4節）

これらは、コードが大きくならず、配置や命令の予測しやすさも損なわないため、既定の動作とします。

## 付録A 仕様検討時の Q&A

この付録は、仕様を検討した過程の質問と回答の記録です。コード例は検討した時点の書き方のままで、第2版の文法とは異なります。第2版での書き方は、付録B の対応表を参照してください。章番号は第1版以降の番号です。


この付録は、言語仕様を検討する過程で出た質問と、その回答・結論をまとめたものです。仕様の各規則が「なぜそうなっているのか」を確認するための資料として位置づけます。

本文中のコード例の構文は検討時点の仮のものです。最終的な構文は本編の仕様に従います。

対象CPUは 65C02 を基本とし、NMOS 6502 はターゲット定義で選択できるものとします。

### A. 全体方針

#### Q A-1. ハードウェアの制約を、言語の制約で抑えることはできるか。たとえば、関数の呼び出しが深くなったらエラーにする、スタック変数を複数定義したらエラーにする、など。

**回答**

可能です。方針は「6502で高くつく操作は書けないようにするか、高くつくことが見える形でしか書けないようにし、その判定をすべてコンパイル時に行う」です。

関数の深さ制限は採用します。再帰を禁止すれば、呼び出し関係は閉路のないグラフになり、コンパイラは最も深い呼び出し経路のスタック使用量を正確に計算できます。予算を超えたらコンパイルエラーにします。

スタック変数の個数制限は、別の形にします。再帰を禁止すると、ローカル変数をスタックに置く必要自体がなくなるためです。コンパイラは呼び出しグラフを解析し、同時に使われない関数同士のローカル変数を同じ固定アドレスに重ねて配置します。制限すべきなのは変数の個数ではなく、重ね合わせた後の合計メモリ量で、これもコンパイル時に検査します。

**結論**：再帰禁止、深さ（スタック使用量）の予算検査、ローカル変数の静的な重ね合わせ、合計メモリ量の検査を採用。

#### Q A-2. Rust のように、言語仕様でハードウェアの制約をカバーすることは可能か。

**回答**

可能です。しかも、この言語の対象は Rust よりも条件が良いと言えます。Rust が難しいのは、ヒープ、複数スレッド、分割コンパイルを相手に安全性を証明しなければならないためです。この言語は、プログラム全体が 64KB 以内、ヒープなし、スレッドなし（並行して動くのは割り込みだけ）、プログラム全体を一度に解析できる、という条件なので、徹底した静的検査が現実的です。

Rust の考え方を 6502 に当てはめたものは次のとおりです。

| Rust の考え方 | この言語での対応 |
|---|---|
| Send / Sync（スレッド間の共有の安全性） | 割り込みとメインで共有する変数を `shared` と宣言。16ビット以上の値は `atomic { }` の中でしか読み書きできない（`php` / `sei` / `plp` に変換） |
| ライフタイム | ローカル変数のアドレスは、呼び出し先には渡せるが、関数の外には持ち出せない |
| 組み込み向けの周辺機器の所有権・型状態 | I/O の所有モジュールの宣言や、入力に設定したポートへの書き込みの禁止 |
| const fn | 表（サイン波、画面の行アドレスなど）をコンパイル時に計算してROMに置く |
| （Rust にもない） | `cycles(n) { }` ブロックで、実行サイクル数をコンパイラが数えて保証する |

静的に検査できないものもあります。ループが必ず終わるかどうか（回数の上限を書かせれば検査可能）、外部機器の振る舞い、割り込みの頻度（ターゲット定義に書けば一部検査可能）などです。

**結論**：Rust 流の「危険な書き方はコンパイルを通さず、検査のコストは実行時に払わない」を言語の基本方針とする。

### B. 型と演算

#### Q B-1. 負の数を使うのはどういう場面か。

**回答**

自作マシンの用途では、次のような場面です。

- 変化量や速度（左に1ドット動く dx = -1、跳ね返った後の速度など）
- 相対的な位置（マス目の隣、表の中の何個前など）
- 差の計算（2つの値のどちらが大きいか、基準より高いか低いか）
- 直線描画のアルゴリズム（ブレゼンハム法の誤差項）
- 音のデータ（0を中心に正負に振れる波形）
- 自作ツール（6502 の分岐命令の飛び先は -128〜+127 の相対値）

座標そのもの、個数、文字コード、アドレスには不要です。

6502 では、足し算と引き算は符号付きでも符号なしでも同じ命令で計算できます（2の補数表現のため）。符号によってコストが増えるのは、大小比較、8ビットから16ビットへの拡張、右シフト、割り算と表示の4つだけです。

**結論**：`i8` と `i16` を `u8`・`u16` とは別の型として用意する。符号付きと符号なしの混在は、明示的な変換がない限りエラー。例外として、`u8 + i8 → u8`（位置に変化量を足す）は明示的な変換なしで許可する。

#### Q B-2. 8ビットの値があふれたときは、一周して戻る扱いで良いか（C もそうだったはず）。

**回答**

一周して戻る扱いにします。補足として、C で一周して戻るのは符号なしの型だけで、符号付きのあふれは未定義動作です。この言語では、符号付きも符号なしも一周して戻ると定義します。6502 の `ADC` / `SBC` はどちらでも同じ動作なので、ハードウェアの振る舞いをそのまま仕様として保証でき、C より単純になります。

**結論**：符号付き・符号なしとも、あふれは一周して戻る（定義された動作）。

### C. 変数と記憶域

#### Q C-1. ゼロページに置く変数（ポインタ以外）の決め方は、オプションで指定し、デフォルトでは明示のみ、とするのはどうか。たとえば最適化オプションとして。

**回答**

採用します。普段は配置が完全に予測でき、速さが必要なときだけコンパイラに任せられます。オプションの有無で動作が変わらないよう、自動配置には次のルールを設けます。

- 自動配置は、`zp` と明示した変数とポインタを置いた後の残りの空きだけを使う（オプションを付けたことでゼロページ不足のエラーが出ることはない）
- `cycles()` ブロック内で使う変数は対象外（サイクル数が変わるため）
- `io` 変数は対象外。`shared` 変数は `fixed` 指定で除外できる
- どの変数を移したか、どれだけ節約できる見込みかをレポートに出す
- インラインアセンブリから参照される変数の扱いは、インラインアセンブリの議題で決める

**結論**：ポインタは自動でゼロページ。それ以外の変数は、既定では `zp` の明示のみ。最適化オプションを付けたときだけ自動配置する。

#### Q C-2. グローバル変数の初期値と、プログラムの実行場所をどう扱うか。

**回答**

プログラムを RAM に読み込んで実行する場合、2回目の実行では前回書き換わった値が残ってしまいます。これを防ぐため、起動時に毎回初期値を設定し直します。

**結論**：グローバル変数は初期値の記述を必須とし、起動時に毎回設定する（`noinit` は例外）。ローカル変数は、代入前に読むとエラー。RAM に読み込んで実行する形と ROM から実行する形の両方に対応し、ターゲット定義で切り替える。

### D. 関数と呼び出し規約

#### Q D-1. 引数3つを A・X・Y に入れて渡しても、関数内で処理する場合は退避処理が必要になってしまう。根本的に考え方を変える必要はないか。

**回答**

引数の使われ方は「受け取ってすぐ使う」と「後で使う」の2種類です。

すぐ使う場合（例：1文字出力の関数が、受け取った文字をそのまま I/O に書く）は、レジスタ渡しなら書き込みも読み込みも不要です。

後で使う場合は、呼び出し先の入口で自分の固定領域にしまう処理（ご指摘の「退避」）が必要です。ただし、固定領域で渡す方式でも、呼び出し元が同じ場所に書き込んでいます。書き込む場所は同じで、誰が書くかが違うだけです。

| 引数の使われ方 | 固定領域で渡す | レジスタで渡す |
|---|---|---|
| すぐ使う | 呼び出し元で書き、呼び出し先で読む | どちらも不要 |
| 後で使う | 呼び出し元で書く（呼び出し箇所ごとに） | 呼び出し先で1回書く |

どちらの場合もレジスタ渡しは損をせず、呼び出し箇所が多いほどコードが小さくなります。

考え方としては、「引数は呼び出し先が持つ、名前付きの固定アドレスの変数であり、レジスタはそこへ届けるための近道」と捉えます。

**結論**：引数は呼び出し先の固定アドレスの変数として扱う。先頭3バイトは A・X・Y で届け、後で使う値は呼び出し先がしまう。ポインタと4バイトめ以降は、呼び出し元が固定領域に直接書く。

#### Q D-2. 複数の値を返す場合も、抜けた先で退避が必要になる。関数というものの定義を考えたほうがよいのでは。サブルーチンという考え方もあるが、関数のほうがよいのか。呼び出し先が壊すレジスタだけを退避する仕様があるから問題ないのか。

**回答**

一般に、関数は「入力を受け取って結果を返すもの」、サブルーチンは「状態の書き換えや I/O を行う処理のまとまり」と区別されます。6502 のプログラムではサブルーチン型が中心になります。

この言語では2つを分けず、「関数＝入口と出口のデータを宣言したサブルーチン」として1つにまとめます。引数のない関数はそのままサブルーチンとして使えます。状態を書き換えない関数には `pure` を付けられ、コンパイル時の計算に使えます。

「壊すレジスタだけを退避する仕様があるから問題ないか」については、半分はそのとおりです。この仕様が解決するのは、呼び出し元がレジスタに持っている値を、関数呼び出しをまたいで保つ問題です。一方、レジスタが本当に別の用途に必要になる場合は、どこかへの書き込みがどうしても必要で、これはどの方式でも消せません。前者の無駄な退避を消すのがこの仕様で、後者の本質的な書き込みを1回で済ませるのが結果領域（Q D-5）です。

**結論**：関数とサブルーチンを分けず、1つの仕組みにまとめる。状態を書き換えないものには `pure` を付けられる。

#### Q D-3. スタックの深さの予算について、もう少し詳しく説明してほしい。

**回答**

ローカル変数をスタックに置かないため、スタックに積まれるのは次のものだけです。

- `jsr` の戻り番地（2バイト）
- 割り込み時に CPU が積む戻り番地とフラグ（3バイト）
- 割り込み処理の入口での A・X・Y の退避（3バイト）
- コンパイラが入れる一時的な退避と、`atomic` の `php`（各1バイト）

コンパイラは、メイン・IRQ処理・NMI処理それぞれのすべての呼び出し経路について最大の使用量を計算し、合計します（NMI は IRQ 処理の最中にも入るため、上に積み重なる）。再帰がないので、経路は有限で必ず計算できます。

予算が必要な理由は、6502 のスタックがページ $01 の 256 バイトしかなく、使い切るとスタックポインタが一周して最も古いデータ（戻り番地）を黙って上書きするためです。不具合はその場では出ず、後で戻り先を失って暴走します。予算を 256 バイト全部にしないのは、ROM ルーチンが使う分や、ページ $01 を他の用途に使う機種があるためで、使用可能な範囲はターゲット定義で指定します。

ローカル変数を積まないため、実際の使用量は小さく、呼び出しが20段深くても40バイト程度です。

**結論**：メイン・IRQ・NMI の最深経路の合計が予算を超えたら、原因の経路を示してエラーにする。割り込み処理の中での割り込み許可（`cli`）は禁止。

#### Q D-4. ROM ルーチンの呼び出しについて、もう少し詳しく説明してほしい。

**回答**

モニタの ROM にあるルーチン（1文字出力、キー入力など）は、この言語のコンパイラが作ったものではないため、コンパイラには引数のレジスタ、壊すレジスタ、スタック使用量がわかりません。たとえば、X をループカウンタに使っているループの中で、X を壊す ROM ルーチンを呼ぶと、カウンタが狂います。

そこで、これらの性質を宣言させます。

```
extern fn rom_print(u8 c in A)  // 引数 c を A で渡す
    @ $FFEF                     // ルーチンのアドレス
    clobbers(A, X, flags)       // 壊すもの
    stack(4);                   // 使うスタック（戻り番地を含む）
```

宣言があれば、コンパイラはカウンタに別のレジスタを使うか、前後で退避するかを判断でき、スタックの予算にも反映できます。

宣言が実際の動作と違っていても、コンパイラは検出できません。ここはプログラマが正しさに責任を持つ部分で、Rust の `unsafe` と同じく、検査できない部分を1か所に閉じ込める仕組みです。将来の拡張として、エミュレータで実測して宣言と照合するツールが考えられます。

**結論**：ROM ルーチンは `extern` で、引数のレジスタ・アドレス・壊すもの・スタック使用量を宣言する。

#### Q D-5. 戻り値は C のように1つ、というのはいまいちなのか。A に値を返すか、ゼロページにポインタを返すような形は。

**回答**

戻り値を1つにすること自体は問題ありません。ただし、複数の値を返すためにポインタを返す方式は、6502 ではいまいちです。

理由の1つめは、ポインタの指す先を用意する場所がないことです。毎回違う場所なら確保が必要ですが、ヒープはなく、ローカル変数のアドレスを返すことも禁止しています。毎回同じ場所なら、呼び出し元はそこを直接読めばよく、ポインタにする意味がありません。

理由の2つめは、遅いことです。ポインタ経由の読み込みは `(zp),Y` になり、読むたびに Y を使い、サイクルも余分にかかります。呼び出し先にもポインタを書き込む処理が毎回必要です。C で定番の「書き込み先のポインタを引数で渡す」方式も同じ理由で遅くなります。

代わりに、構造体を値として返せるようにします。構造体のフィールドは呼び出し先の結果領域（固定アドレス）に置かれ、呼び出し元はコピーせずに直接読みます。結果領域の値は、同じ関数をもう一度呼ぶまで変わりません。古い結果を使い終わる前に同じ関数を呼ぶ場合だけ、コンパイラが自動でコピーを入れます。

**結論**：戻り値は1つ。複数の値は構造体にまとめて返す。ポインタで結果を返す方式は採用しない。

#### Q D-6. その構造体は2つまでしか値を持てないのか。正確には2つまではレジスタ、3つ以上はメモリ、ということか。

**回答**

いいえ。構造体で返す場合はレジスタを使わず、すべてのフィールドを結果領域に置きます。フィールドの数に制限はありません。

結果領域は固定アドレスなので、呼び出し元は普通の変数と同じように直接読めます（ポインタ経由ではないので、余分なレジスタも使いません）。レジスタで返す場合と比べて余分にかかるのは、呼び出し先での書き込み（1フィールドにつき3〜4サイクル）だけです。

最適化オプションを付けた場合は、最初のフィールドだけレジスタでも返す、といった改善をコンパイラに任せられます。

**結論**：構造体の戻り値は、全フィールドを結果領域に置く。個数の制限なし。

#### Q D-7. 関数の戻り値は u8、i8、u16、i16、bool、構造体しか持てない、という理解で合っているか。

**回答**

ほぼ合っています。加えて、ポインタ、関数ポインタの候補一覧（`fnset`）の値、戻り値なしがあります。将来の型の追加に備え、型の一覧ではなく大きさで返し方を決めます。

| 戻り値 | 返し方 |
|---|---|
| なし | 何も返さない |
| bool | キャリー |
| 1バイトの型（u8、i8、fnset の値など） | A |
| 2バイトの型（u16、i16、ポインタ） | A（下位）と X（上位） |
| 構造体 | すべてのフィールドを結果領域に置く |

配列は直接は返せず、返したい場合は構造体に入れます。大きなデータを返していることが、構造体の宣言として目に見えるようにするためです。

**結論**：上の表のとおり、戻り値の返し方は大きさで決まる。

### E. 配列とポインタ

#### Q E-1. 構造体の配列と u16 の配列の並べ方について、メリット・デメリットと仕組みを教えてほしい。

**回答**

6502 のインデックス付きの読み込み `lda 基点,x` は「命令に埋め込んだ定数の基点＋X」を読むので、X には「基点から何バイト先か」を入れる必要があります。C と同じく1要素を連続して並べると、X に入れる値が「番号×構造体の大きさ」になり、掛け算が毎回必要です。フィールドごとに別の配列にすると、番号がそのままバイト位置になります。

| | フィールドごとの配列 | C と同じ並べ方 |
|---|---|---|
| 1要素の読み書き | 番号を X に入れて1命令 | 番号×大きさの計算が毎回必要 |
| ループ | `inx` / `dex` で次へ | X に大きさを足す処理が必要 |
| 要素数の上限 | 256 | 256 ÷ 構造体の大きさ |
| メモリ使用量 | 同じ | 同じ |
| 1要素を指すポインタ | 作れない | 作れる |
| 1要素をバイト列として扱う | できない | できる |
| モニタでのメモリの見え方 | 1要素が散らばる | 1要素が並ぶ |

全要素の1フィールドを更新するループでは、1要素あたり 12 サイクル対 20 サイクル程度の差が出ます。

フィールドごとの配列のデメリットは、どれも「1要素が連続したバイト列でない」ことに起因します。困るのは、外部との受け渡し（ディスク、シリアル）、ハードウェアが決めた形式（ビデオチップのスプライト表など）、メモリダンプでのデバッグ（コンパイラがアドレスの一覧を出力することで補う）です。1要素を指すポインタが作れない点は、番号を X で渡すほうが `(zp),Y` より速いため、ほとんど不利になりません。

u16 とポインタの配列を下位バイトの配列と上位バイトの配列に分ける方式も、仕組み、メリット、デメリットは同じです。

**結論**：構造体の配列はフィールドごと、u16 とポインタの配列は下位・上位ごとに分けるのを標準とする。連続したバイト列が必要な場合だけ `packed` で明示する。

#### Q E-2. 配列の添字の範囲を守る方法について、もう少し説明してほしい。

**回答**

6502 には範囲外のメモリアクセスを止める仕組みがなく、長さ16の配列に添字20を使うと、隣の配列のデータを黙って読み書きします。

方式は3つあります。毎回実行時に検査する方式は安全ですが、アクセスのたびに比較と分岐が入り遅くなります。検査しない方式は最速ですが、不具合を防げません。この言語では、範囲を型で保証する方式を採用します。

範囲型は「この値は決まった範囲に収まることが確かめ済み」という印の付いた u8 です。生成されるコードの中では普通の u8 で、印はコンパイル時にしか存在しないため、実行時のコストはありません。範囲型の値は、範囲を必ず守れる次の方法でしか作れません。

| 作り方 | 実行時のコスト |
|---|---|
| 配列を回す for | なし |
| 定数（範囲外ならコンパイルエラー） | なし |
| 範囲を確かめる変換（`check()`、結果は `?` 付き） | 比較と分岐の2命令 |
| 下位ビットだけを取る変換（長さが2のべき乗のとき） | `and` の1命令 |

範囲型の値に演算をすると、結果は印のない u8 に戻ります。外から来た値は入口で1回だけ確かめ、以降は範囲型として受け渡すため、検査は外とのつなぎ目に集まります。

**結論**：添字には範囲型を使う。

#### Q E-3. 範囲型を受け取るはずの関数の引数を u8 にしたらどうなるのか。検査の要・不要の記述はプログラマの責任なのか。

```
fn damage(u8 e) {
    enemies[e].hp -= 1;
}
```

**回答**

関数の中の `enemies[e]` がコンパイルエラーになります。範囲型の値を u8 の引数に渡すこと自体は、安全な方向の変換なので許可されますが、関数の中では e は 0〜255 のどれかとしか扱えないため、配列に使う時点で止まります。

検査が必要かどうかを判断するのはコンパイラで、プログラマの責任ではありません。プログラマが決めるのは、検査をどこで行うか（引数を範囲型にして呼び出し元で検査するか、関数の中で検査するか）だけで、検査がどこにもない状態ではコンパイルが通りません。

例外として、検査なしで範囲型の印を付ける `unchecked()` を用意します。ハードウェアの仕様上、範囲内であることがわかっている値などに使うもので、ここだけはプログラマの責任になります（Rust の `unsafe` に相当）。名前で検索できるので、不具合の調査対象を絞り込めます。

**結論**：検査の要否はコンパイラが型で判断する。プログラマの責任になるのは `unchecked()` を使った箇所だけ。

#### Q E-4. 「指していないかもしれないポインタ」なんて発生するのか。

**回答**

この言語では、ほとんど発生しません。

| 一般の言語でヌルが生まれる場面 | この言語では |
|---|---|
| 初期化していないポインタ変数 | 初期化前の使用はエラーなので発生しない |
| ヒープの確保に失敗した | ヒープがないので発生しない |
| リスト構造の最後 | ヒープがないのでまれ。配列と添字で書くのが普通 |
| 検索して見つからなかった | 発生しうる |

残る「見つからなかった」は、ポインタに限らず添字や数値でも起きる問題です。そこで、ヌルという特別な値は言語に入れず、「値があるかないか」を表す `?` 付きの型を、どの型にも使えるようにします。

**結論**：ヌルポインタは作らない。代わりに、どの型にも使える `?` 付きの型を用意する。

#### Q E-5. `?` 付きの型を使うと、コストはどのくらい増えるのか。`?` を付けなければ追加のコストはかからないのか。

**回答**

`?` を付けなければ、追加のコストは一切かかりません。付けた場合のコストは次のとおりです。

| 使い方 | 追加のコスト |
|---|---|
| 戻り値をすぐ分岐に使う | 4〜5サイクル（呼び出し先の `sec` / `clc` と、呼び出し元の `bcc` / `bcs`） |
| 使われない値がある型（範囲型など）を変数に保存 | 追加のメモリなし（使われない値を「なし」に流用）。確認に5〜7サイクル |
| すべての値が有効な型（u8 など）を変数に保存 | 追加で1バイト。確認に5〜7サイクル |

戻り値の場合、昔ながらの「見つからなければ $FF を返す」方式（呼び出し元で比較と分岐が必要）と同じか安く済み、C のヌルポインタの確認（2バイトを調べる）より安く済みます。

**結論**：`?` は使った場所にだけコストがかかり、そのコストは従来の方法と同等以下。

#### Q E-6. `?` 付きの型は、不定値（ユーザー入力など）を取りうる場合に使うイメージか。Optional のようなものか。

**回答**

Swift や Java の Optional、Rust の Option と同じものです。

ただし、使う場面は「どんな値でもありうる」ではなく、「値があるかないか」が問題になる場面です。範囲型とは役割が異なります。

| 仕組み | 表すこと | 例 |
|---|---|---|
| 範囲型 | 値が決まった範囲に収まっているか | 敵の番号は 0〜15 |
| `?` 付きの型 | 値があるか、ないか | 探したが見つからなかった |

ユーザー入力そのものは、値は必ずあるので普通の u8 で表します。`?` を使うのは、検索の結果、待たずに戻るキー入力の確認（押されていなければ「なし」）、文字から数値への変換（変換できない文字なら「なし」）、範囲の確認（`check()` の結果）などです。

**結論**：`?` 付きの型は Optional であり、「値の有無」を表す。値の範囲の保証は範囲型が担う。

#### Q E-7. `let e = enemies.index(n)` の e は enemies.idx 型ということか。文法上どのように定義されたのかがピンと来ない。

**回答**

検討時点の書き方では、配列の宣言から添字の型が暗黙に作られ、`if let` の左辺の型も省略されていたため、型の出どころが見えにくくなっていました。

そこで、Pascal や Ada の範囲型にならい、添字の型を先に名前を付けて宣言し、それを添字にして配列を宣言する書き方を標準とします。

```
type eid = 0..15;               // 0〜15 の値だけを取る型
enemy enemies[eid];             // eid を添字に使う配列（長さ16）
u8 enemy_score[eid];            // 同じ eid を添字に使う別の配列

fn on_key() {
    u8 n = read_key();          // 0〜255 のどれでもありうる値
    eid? r = eid.check(n);      // 範囲内なら eid の値、範囲外なら「なし」
    if let e = r {              // 値があれば、e（eid 型）として受け取る
        enemies[e].hp -= 1;
    }
}
```

型の名前がソースに書かれるので、値の型を追えます。また、同じ添字を使う複数の配列で1つの型を共有できます。手軽さのため、`u8 table[16];` のように長さを数字で書く宣言も残し、その場合は `table.idx` という型が自動で作られます。

**結論**：範囲型を `type 名前 = 下限..上限;` で宣言し、配列の添字に使う。数字で長さを書いた配列には `配列名.idx` 型が自動で作られる。

#### Q E-8. `type eid = table.idx;` は合法か。また、同じ範囲の型を2回宣言した場合はどうなるか。

**回答**

`type eid = table.idx;` は合法とし、「table.idx の別名」として同じ型を表します。

同じ範囲を書いて2回宣言した型（`type eid = 0..15;` と `type iid = 0..15;`）は、別の型として扱い、混用はエラーにします。範囲が同じでも意味が違う値はよくあり、同じ型とみなすと、後で片方の範囲を変えたときに、それまで通っていたコードの意味が黙って変わり、不具合になるためです（仕様検討者の判断による）。型の同一性を範囲ではなく宣言で決めておけば、そうした変更はコンパイルエラーとして表に出ます。

**結論**：範囲型は宣言ごとに別の型とする（名前による型の区別）。共有したい場合は別名で明示する。

#### Q E-9. `?` を使うということは、255 は使えなくなるということか。

**回答**

いいえ。「ある・なし」の表し方はコンパイラが型ごとに選ぶため、プログラマが使える値は減りません。

| 場面 | 「ある・なし」の表し方 | 255 |
|---|---|---|
| 戻り値（`u8?`） | キャリーフラグ。値は A | 使える |
| 変数に保存（`u8?`） | 「ある・なし」用にもう1バイト使う | 使える |
| 変数に保存（範囲型 `eid?`） | 使われない値の $FF を「なし」にする | もともと eid の値ではない |

「なしを $FF で表すので 255 が使えない」というのは、`?` を使わない従来の方法の欠点で、`?` 付きの型はそれを解消する仕組みです。

**結論**：`?` を付けても、その型の値の範囲は狭まらない。

### F. I/O と割り込み

#### Q F-1. 割り込み処理の中で `cli` を禁止するのはなぜか。

**回答**

IRQ が入ると、CPU は自動で I フラグを立て、割り込み処理が終わる（`rti` でフラグが戻る）まで次の IRQ を待たせます。割り込み処理の中で `cli` を実行すると、処理の途中で次の IRQ が入り、割り込み処理が入れ子で動きます。これを禁止する理由は3つあります。

1つめは、スタックの予算が計算できなくなることです。入れ子が何段重なるかは割り込みの頻度で決まり、コンパイル時にはわかりません。

2つめは、ローカル変数が壊れることです。ローカル変数は固定アドレスにあるため、入れ子で動いた内側の実行が、外側の実行のローカル変数を上書きします。入れ子の割り込みは実質的に再帰呼び出しであり、再帰を禁止したのと同じ理由で許可できません。

3つめは、無限の入れ子の危険です。6502 の IRQ は、信号が出ている間ずっと割り込みを要求し続けます。割り込みの原因になったチップのフラグを消す前に `cli` すると、すぐにまた割り込まれ、スタックが一周して暴走します。

長い割り込み処理の最中に急ぎの割り込みを受け付けたい場合は、割り込み処理を短くして時間のかかる処理をメインに任せるか（リングバッファなど）、急ぎの処理を NMI にします。NMI は1段しか重ならないため、スタックの予算も計算できます。

**結論**：割り込み処理の中での `cli` は禁止。

#### Q F-2. `cycles()` で、周波数（時間）によるサイクル指定もあると便利か。なくてもよいなら不要。

**回答**

あると便利です。KIM-1 級から Apple II 級へ育てる過程でクロックを変える可能性があり、周辺チップのデータシートの待ち時間は「40 マイクロ秒以上」のように時間で書かれているためです。サイクル数だけで書いていると、クロックを上げたときに待ち時間が黙って短くなり、動かなくなります。時間で書いておけば、ターゲット定義のクロックを書き換えるだけで、コンパイラがサイクル数を計算し直します。

専用の文法は不要で、時間をサイクル数に変換するコンパイル時の関数 `us()` を標準で用意すれば済みます。時間がちょうどのサイクル数にならない場合は、警告を出したうえで切り上げます。

また、時間で考えると、データシートの待ち時間の多くは「ちょうど」でも「上限」でもなく「最低これだけ待つ」という下限であることから、サイクル数を扱う形を次の3つにします。

| 形 | 意味 | 主な用途 |
|---|---|---|
| `cycles(n) { }` | ちょうど n サイクル（足りない分は `nop` で埋める） | パルスの幅、ビデオ表示のタイミング |
| `max_cycles(n) { }` | n サイクル以内（超えたらエラー） | 時間内に終わらせたい処理 |
| `delay(n);` | 最低 n サイクル待つ（コンパイラが待ちループを作る） | 周辺チップの待ち時間 |

どれも `delay(us(40));` のように時間で書けます。

**結論**：`cycles`・`max_cycles`・`delay` の3つの形を用意し、時間指定はコンパイル時の関数 `us()` で行う。


#### Q F-3. 割り込み処理の中で atomic を省略できる場面を、例で見たい。

**回答**

6502 では、IRQ でも NMI でも、割り込みが入るとすぐに CPU が I フラグを立てます。そのため、割り込み処理の実行中は、メインも IRQ も割り込みません。`atomic` が必要なのは割り込まれる側（メイン）だけで、割り込む側（割り込み処理）には不要です。

- 割り込み処理の中で 16 ビットの `TICKS` を増やす：省略できる（メインの側で読むときは `atomic` が必要）
- メインが書いた 16 ビットの値を、割り込み処理の中で読む：省略できる（メインの側で書くときは `atomic` が必要）
- NMI 処理の中で、メインや IRQ 処理と共有する変数を操作する：省略できる（NMI の実行中も I フラグが立っているため）
- NMI と共有する変数：省略できない。NMI は IRQ 処理の途中でも入り、`atomic` でも止められないため、1 命令の操作だけに限る（これまでの規則どおり）

**結論**：割り込み処理の中では `atomic` を省略できる（書いても何も生成せず、警告も出さない）。NMI と共有する変数は除く。あわせて、`atomic` はブロックの最後の式を値として返せるようにする（本編 8.5節、8.6節）。

### G. 列挙型と文字・文字列

#### Q G-1. 何も付けない `""` は、長さも終端も付けない、という仕様はいまいちか。

**回答**

いまいちではなく、この言語の方針に合った良い仕様です。

何も付けない `"HELLO"` の型を、長さがコンパイル時に決まっている文字の配列 `char[5]` にします（Rust の `b"..."` と同じ考え方）。長さは型が持っているため、実行時に長さや終端を持たなくても、`for` で回すなどの処理は問題なく書けます。

長さ付きの文字列 `str` を受け取る関数に、何も付けない文字列を渡すとコンパイルエラーになります。形式を書き忘れても黙って別の形式になることはなく、型の不一致として必ず検出されます。代わりに、長さ付きの文字列を使うたびに `p` を書く手間が増えます。

| 書き方 | 中身（"HI" の場合） | 型 |
|---|---|---|
| `"HI"` | `48 49` | `char[2]`（長さは型が持つ） |
| `p"HI"` | `02 48 49` | `str`（長さ付き） |
| `z"HI"` | `48 49 00` | 0終端の文字列 |
| `hi"HI"` | `48 C9` | 最上位ビット終端の文字列 |

**結論**：何も付けない `""` は、長さも終端もない `char[N]` とする。長さ付きの文字列は `p""` で明示する。

#### Q G-2. `@screen` を付けたときの仕様のイメージがつかない。

**回答**

`@screen` は、「この文字列を、画面メモリに直接書き込めるバイトに、コンパイル時に変換しておく」という指定です。

たとえば Apple II 級の画面では、画面メモリに $C1 を書くと普通の `A` が表示され、ASCII の `A`（$41）を書くと点滅する `A` になります。ASCII のままの文字列を画面メモリにコピーすると、表示がおかしくなります。

変換表は、ターゲット定義の中で文字の範囲と値の範囲の対応として書きます。

```
encoding screen {
    ' '..='?' => $A0..=$BF;     // 空白から '?' まで：ASCII に $80 を足した値
    '@'..='_' => $C0..=$DF;     // '@' から '_' まで（大文字を含む）：同上
}
```

ソースに `p"HI"@screen` と書くと、コンパイラはこの表で変換し、プログラムに `02 C8 C9` を置きます。表にない文字（この例では小文字）はコンパイルエラーです。実行時には変換の処理はなく、画面メモリへのコピーだけで正しく表示されます。

変換表は自由に定義できるため、7セグメント LED の点灯パターン（`'0' => $3F` など）のように、文字以外のバイトへの変換にも使えます。

さらに、変換表ごとに文字と文字列を別の型（`char@screen`、`str@screen`）にします。ASCII の文字列を受け取る関数に画面用の文字列を渡すとコンパイルエラーになり、取り違えを防げます。

**結論**：`@変換表` は、ターゲット定義の変換表によるコンパイル時の変換。変換表ごとに別の型とする。指定がなければ ASCII。

### H. モジュールとライブラリ

#### Q H-1. インターフェースと実装を分けて bind で選ぶなら、ターゲット定義の機能の一覧（screen、keyboard など）も bind にまとめてよいのではないか。困ることはあるか。

**回答**

まとめるのが良い案です。「機能がある」を「その機能のインターフェースに実装が bind されている」と定義すれば、機能の一覧と bind の食い違い（一覧に書いたのに実装がない、など）が原理的に起きなくなります。`target.has(screen)` は「screen が bind されているか」を意味します。

困る点は、コードを伴わない性質（拡張 RAM の有無、画面の幅など）を bind で表せないことです。これらはターゲット定義に名前付きの定数として書き、`target.名前` で読めるようにします。

その結果、ターゲット定義に書くのは、CPU とクロック、bind、定数の3種類になり、`features = [...]` の一覧は廃止します。

**結論**：機能の有無は bind で表す。コードを伴わない性質はターゲット定義の定数で表す。

#### Q H-2. 機能を bind で表す方式について、コンパイル引数、設定ファイル、ソースの書き方を詳しく説明してほしい。

**回答**

関わるファイルは、プロジェクトファイル（`ax65.proj`：入口、import の探索場所、対応ターゲットの一覧、既定のターゲット）、ターゲット定義ファイル（`*.target`：CPU、クロック、メモリ、bind、定数）、ソースの3種類です。

ターゲット定義は ax65 と同じ文法で書き、式や bind のモジュール名を検査できるようにします。マシンの成長に合わせて `target v3 extends v2 { ... }` のように前の構成を引き継げます。

コマンドラインでは、`-t` でターゲットを、`-D` でビルドの設定を、`--bind` で bind の一時的な差し替え（エミュレータでの試験など）を指定できます。`ax65 check --all-targets` で、プロジェクトのすべてのターゲットについて型まで検査します。

ソースでは、標準ライブラリなどがインターフェース（`interface screen { ... }`）を宣言し、マシンごとの実装（`impl screen { ... }`）を別のファイルに書きます。使う側はインターフェースの名前で `import` し、bind されていないターゲットで使う部分は `const if target.has(screen)` で囲みます。囲まずに使うとエラーです。

具体的な書き方は本編 2章と 11章を参照してください。

**結論**：プロジェクトファイル、`extends` 付きのターゲット定義、`interface` / `impl` / `bind` の組み合わせで機種の違いを表す。

#### Q H-3. init がないモジュールのコストは0と考えてよいか。

**回答**

はい。`init` を書かなければ、起動時のコードは何も作られません。書いた場合も、`init` は1回しか実行されないため、起動の手順の中に中身を直接展開し、`jsr` / `rts` のコストはかかりません。

**結論**：`init` がなければコストは0。ある場合も中身の命令の分だけ。

#### Q H-4. 使っていないモジュールの init が実行されることについて、警告を出したり、明示的に抑制したりする方法がほしい。

**回答**

import したモジュールの公開されたものを1つも使っていない場合に警告を出し、そのモジュールに `init` があれば起動時に実行されることも示します。`init` だけが目的の場合は `import hw.via for init;` と書くと警告が出ません。`for init` を付けたモジュールの関数を使った場合は、意図とコードの食い違いとして警告を出します。

一方、import したモジュールの `init` を実行させない方法は用意しません。モジュールの関数は `init` が済んでいることを前提に書かれているため、飛ばすと誤動作の原因になるからです。

**結論**：使っていない import には警告を出し、`for init` で抑制できる。`init` を止める方法は用意しない。

### I. 最適化（サンプル meteor の性能比較から）

#### Q I-1. 比較で示された「コード量」は、アセンブリのソースの量か。

**回答**

いいえ。アセンブルした後の機械語のバイト数で、6502 のメモリに実際に読み込まれる大きさです。たとえば `lda M_WAIT,x` は機械語の `BD 9F 05` の 3 バイトになります。6502 の命令は 1〜3 バイトなので、バイト数と命令の数は比例しません。変数をゼロページに置くと、3 バイトの命令の多くが 2 バイトになります。

**結論**：コードの大きさは、機械語のバイト数で比べる。

#### Q I-2. 関数のインライン化を明示する仕組みはあったか。

**回答**

`inline` の明示（議題13 の清書案では `#[inline]`）がありました。比較の結果、めったに通らない枝で呼ばれる関数を展開すると、ループが大きくなってページ境界をまたぎ、かえって遅くなることがわかったため、「展開しない」指定も加えます。

| 属性 | 意味 |
|---|---|
| `#[inline]` | 展開してよい。最適化オプションがなくても展開する |
| `#[inline(always)]` | 必ず展開する。できなければコンパイルエラー |
| `#[inline(never)]` | 決して展開しない |
| `#[cold]` | めったに呼ばれない関数。`-O speed` でも展開せず、ループの外に置く |

**結論**：インライン化の指定は上の 4 つの属性とする（本編 5.8節）。

#### Q I-3. -O は大きさ優先を既定にしてよいのではないか。それが大きさと速さの両方に最も効くのだから。

**回答**

そのとおりです。meteor の比較では、大きさを優先した版が、-O より 10 % 小さく、速さも最も速い版とほぼ同じでした。6502 では、命令を小さくすること（ゼロページの使用、呼び出しの削減、ループを小さく保つこと）が、そのまま速さにつながるためです。

そこで、`-O` を大きさ優先の標準の最適化とし、コードが大きくなっても速さを優先したい場合のために `-O speed` を残します。`-O size` という別のオプションは作りません。

あわせて、ポインタの引数も A と X で渡すことを標準の規則にしました（呼び出しのたびに 4 バイト小さくなる）。文字列の表、文字列の後ろの共有、データの圧縮は、プログラマが必要に応じて行うものとし、言語の仕様には入れません。中間コードによる圧縮は、将来の拡張として余地だけを残します。

**結論**：最適化オプションは、なし／`-O`（大きさ優先）／`-O speed`（速さ優先）の 3 段階とする（本編 15章）。（Q I-4 で段階の名前と既定を変更）

#### Q I-4. 最適化の段階を -O0、-O1（初期仕様）、-O2（今回仕様）、-Os（速度優先）とし、既定を -O2 にしてほしい。

**回答**

そのように変更します。

| 段階 | 内容 |
|---|---|
| `-O0` | 最適化をしない |
| `-O1` | 版0.1 の最適化（小さな関数も展開する） |
| `-O2` | 大きさを優先する最適化（**既定**） |
| `-Os` | `-O2` に加えて速さを優先する |

既定が `-O2` になったため、ゼロページへの自動配置は、何も指定しなければ行われることになります（Q C-1 では「既定は明示のみ、最適化オプションで自動配置」としていた）。配置を完全に予測したい場合は `-O0` を使います。サイクル数を保証するブロックとインラインアセンブリが参照する変数は、どの段階でも自動配置の対象外のままです。

なお、GCC などでは `-Os` は大きさ優先を意味しますが、ax65 では速さ優先の意味になる点を、仕様書に明記しました。

**結論**：最適化は `-O0`／`-O1`／`-O2`（既定）／`-Os` の 4 段階とする（本編 15章）。

### J. 古い版で書いたソースから見つかった点

古い版の仕様でソースを書いたときに見つかった、仕様の抜けと、その決定です。

#### Q J-1. 書き込む側が1つの shared は、更新にも atomic が必要か。

**回答**：書き込む側が1つしかなければ、書き込む側が読む途中で値が変わることはありません。また、1バイトの書き込みは1命令で終わるので、読む側は古い値か新しい値のどちらかを読みます。そこで、書き込む側の読み込みと、1バイトの書き込み（読んで計算して書き戻す場合も含む）には `atomic` を不要とします。2バイト以上の書き込みと、読む側の2バイト以上の読み込みには、これまでどおり必要です。

**結論**：書き込む側が1つの `shared` に例外を設ける（本編 8.5節）。

#### Q J-2. cycles(n) は、ブロックの外の命令（I/O への書き込みなど）を含めて数えるのか。

**回答**：6502 の書き込みは命令の最後のサイクルに行われるため、パルスの幅と、ブロックの中の命令の合計は一致しません。そこで2つの形に分けます。`cycles(n)` はブロックの中の命令の合計だけを数えます。パルスの幅のような I/O の間隔は、新しく設ける `io_span(n)` で、ブロックの中の最初と最後の I/O の読み書きの間隔として書きます。

**結論**：`cycles(n)` はブロックの中の合計、I/O の間隔は `io_span(n)`（本編 9章）。

#### Q J-3. 配列や構造体の初期値はどう書くか。

**回答**：Rust と揃えます。配列は `[1, 2, 3]`、`[v; N]`、構造体は `name { field: value, ... }`（すべてのフィールドを書く）と、構造体更新構文 `name { hp: 3, ..BASE }` です。「全バイトが 0」を表す特別な値は用意しません。値がすべて 0 の部分は、コンパイラが `stz` で初期化します。

**結論**：配列と構造体の値は Rust と同じ書き方とする（本編 3.8節）。

#### Q J-4. u8 から char へは変換できるか。

**結論**：`n as char` で変換できる。`char` は1バイトで 0〜255 のどの値も持てる。変換表付きの文字型への変換（`as char@screen`）も同様（本編 3.6節）。

#### Q J-5. for の範囲の終わりに変数を書けるか。

**結論**：書ける。ループ変数の型は両端の型と同じ。u8 なら上限が 256 回と型から決まるので、割り込み処理の中などでも使える。範囲型のまま一部を回すときは `eid::range(a, b)` を使う（本編 6.2節）。

#### Q J-6. ページ単位の配列の &buf は何を指すか。

**結論**：配列全体の先頭（＝最初のページの先頭）。`&buf[k]` は k 番目のページの先頭。型はどちらも `ptr<u8>`（本編 3.9節）。

#### Q J-7. match の腕の右辺には、式とブロックのどちらを書くのか。

**結論**：Rust と同じく両方書ける。式の後ろにはカンマが必要で、ブロックの後ろでは省略できる（本編 6.4節）。

#### Q J-8. 変換表の「1文字 → 1値」はどう書くか。

**回答**：「1文字 => 1値」（`'\r' => $8D;`）と「文字の範囲 => 値の範囲」（`'A'..='Z' => $C1..=$DA;`）の2つの形にします。範囲は、`..` の規則（終わりを含まない）と食い違わないように `..=` で書きます（これまでの例の `' '..'?'` も直しました）。あわせて、文字のエスケープ（`'\n'`、`'\r'`、`'\x41'` など）を言語全体で使えるようにします。

**結論**：変換表は2つの形で書き、範囲は `..=`（本編 3.6節）。
